# 项目级 AI 上下文建设哲学与体系原理

> 文档来源：基于 `AGENTS.md`、`.ai/README.md`、`.qoder/rules/`及各 Skill 文件综合提取 适用对象：供其他大模型分析本项目 AI 上下文的设计思想与运行原理

------

## 一、总体设计哲学

### 1.1 核心分层原则：「决策」与「事实」分离

本项目 AI 上下文采用严格的**职责分离**架构：

| 目录      | 回答的问题                 | 内容性质                                     | 类比               |
| --------- | -------------------------- | -------------------------------------------- | ------------------ |
| `.ai/`    | **应该怎么做、不能做什么** | 决策、约束、规范、坑点、设计决策             | 「交通规则」       |
| `.qoder/` | **事实是什么、如何执行**   | 代码基线、接口签名、技术栈详情、可复用 Skill | 「地图与驾驶手册」 |

> 核心口诀：`.ai` 管「决策约束」，`.qoder` 管「事实执行」。

### 1.2 三层递进加载：由浅入深、按需下沉

AI 会话按以下三层递进加载上下文，禁止一次性全量灌入：

1. **入口层（`AGENTS.md`）**：环境常量、目录排除、快速跳转导航
2. **决策约束层（`.ai/`）**：任务状态、模块边界、开发约定、已知问题、设计决策
3. **事实技能层（`.qoder/`）**：repowiki 代码事实、AI 行为硬卡点、可复用 Skill

**设计意图**：避免大模型上下文窗口被无关事实淹没，确保每次加载的都是当前场景最相关的约束与知识。

------

## 二、文档体系架构（L1/L2/L3）

`.ai/` 内部采用三层文档体系，明确区分「当前任务」与「项目知识」：

| 层级          | 目录/文件                                                    | 用途                                               | 读取时机                             |
| ------------- | ------------------------------------------------------------ | -------------------------------------------------- | ------------------------------------ |
| **L1 任务层** | `11-workspaces/tasks/*.md`、`current-state.md`               | 记录当前激活任务的目标、方案、进度、风险           | **每次会话开始时必须先读**           |
| **L2 核心层** | `README.md`、`02-rules/`、`04-knowledge/modules/`、`05-decisions/`、`06-known-issues/` | 项目级规则、模块边界、开发约定、设计决策、已知问题 | 分析代码、拆分任务、做技术决策时     |
| **L3 参考层** | `04-knowledge/public/`、`09-prompts/`、`.qoder/repowiki/`    | 外部接口文档、数据样例、代码结构详情、Prompt 模板  | 涉及外部对接、代码详情时**按需查阅** |

**关键约束**：

- L1 未确认前，**禁止修改任何代码**（硬卡点）。
- 同一信息只在一处权威文档详述，其他地方通过引用指向，避免重复膨胀。

## 三、AI 行为约束体系（硬卡点）

`.qoder/rules/` 定义了 AI 自身的行为硬卡点，而非项目代码规范。这是本体系区别于普通文档库的核心特征：

### 3.1 会话启动强制 Checklist（`01-session-bootstrap.md`）

任何新会话或新任务，**未完成以下 Checklist 前禁止读取或修改代码**：

1. **L1 任务确认**：读取 `11-workspaces/current-state.md`，确认当前激活任务
2. **分支确认**：仅允许在 `feature/*`、`hotfix/*` 上修改；禁止在 `develop`/`master`/`release/*` 上直接修改
3. **分支一致性校验**：以任务文件中 `branch` 字段为唯一目标分支，不一致则必须先切换
4. **审计状态确认**：发现已合并但未审计的代码，主动提示用户
5. **场景路由**：按 `README.md` 路由表进入对应文档

完成以上 Checklist 后，自动执行**会话启动扫描**：扫描未提交变更、配置变更、字段语义变更、已知问题关联等，并主动提示用户。

### 3.2 代码修改行为约束（`02-code-modification.md`）

| 场景     | 强制使用工具                   | 禁止使用工具            |
| -------- | ------------------------------ | ----------------------- |
| 修改文件 | `SearchReplace`                | Bash（sed/awk/findstr） |
| 创建文件 | `Write`                        | Bash（echo/重定向）     |
| 删除文件 | `DeleteFile`                   | Bash（rm/del）          |
| 读取文件 | `Read`                         | Bash（cat/type）        |
| 批量搜索 | `SearchCodebase` / `grep_code` | Bash（grep/findstr）    |

- 文件修改**必须串行执行**，禁止并行调用多个文件编辑工具
- Bash 工具**仅用于**：git 查询、`mvn`/`gradle` 构建、进程操作
- AI **禁止代替执行任何 git 写操作**（commit/push/merge），仅允许只读查询

### 3.3 环境感知约束

| 环境事实               | AI 行为约束                                                  |
| ---------------------- | ------------------------------------------------------------ |
| Windows（无 WSL）      | 禁止执行 `grep` / `rm -rf` / `cp` / `mv`等类 Unix 命令       |
| IDEA 终端使用 Git Bash | Git Bash 支持 `mvn` / `gradle`，路径用 Unix 风格；git 查询附加 `--no-pager` |
| 可用 `mvn`/ `gradle`   | 构建验证优先使用 `mvn validate -Pcheckstyle -pl {模块}`      |

## 四、知识管理哲学

### 4.1 L2 回流机制（对话 -> 项目知识）

**原则**：任务归档时，AI **必须主动提示** L2 回流检查，但**禁止自动写入**，需等待用户确认。

| 内容类型                 | 目标文档                                |
| ------------------------ | --------------------------------------- |
| 已确认的新架构决策       | `.ai/05-decisions/decisions.md`         |
| 已确认的新规范或规范变更 | `.ai/02-rules/conventions.md`           |
| 已验证的坑点             | `.ai/06-known-issues/known-issues.md`   |
| 新增/变更的外部接口文档  | `.ai/04-knowledge/public/dependencies/` |
| 新增表数据样例           | `.ai/04-knowledge/data/`                |

### 4.2 实时知识沉淀信号

对话中识别到以下信号时，标记为「待沉淀知识」，会话结束时输出提醒清单：

| 信号类型 | 关键词/模式                                           | 目标文档                   |
| -------- | ----------------------------------------------------- | -------------------------- |
| 坑点信号 | "又踩坑了"、"规避..."、"workaround"、"临时方案"       | `known-issues.md`          |
| 规范信号 | "统一..."、"规范..."、"约定..."、"禁止..."、"必须..." | `conventions.md`           |
| 决策信号 | "决定用 A 不用 B"、"最终方案..."、"选型..."           | `decisions.md`             |
| 边界信号 | "不能调..."、"模块职责..."、"属于 XX 模块的事"        | `boundaries.md`            |
| 依赖信号 | "依赖了 XX 系统"、"对接 XX 接口"                      | `public/dependencies/*.md` |

### 4.3 文档健康检查（防膨胀）

每次修改 `.ai/` 文档时顺手执行实时检查：

| 检查维度   | 判定标准                              | 动作                          |
| ---------- | ------------------------------------- | ----------------------------- |
| 行数膨胀   | 单文件超过 300 行                     | 提示拆分；超过 500 行必须拆分 |
| 条目膨胀   | `known-issues.md` 超过 20 条          | 提示按模块拆分                |
| 重复内容   | 同一知识点出现 2 次及以上             | 提示合并或抽取到 L3           |
| 过时内容   | 标记"已修复"/"已废弃"超过 3 个月      | 提示归档或删除                |
| 结构退化   | 新增内容破坏原有章节逻辑              | 提示重新排序                  |
| 职责污染   | 文档/目录中出现不属于其职责范围的内容 | 提示迁移到正确位置            |
| 元信息缺失 | 新文档缺少 YAML frontmatter           | 提示补充                      |

## 五、Skill 体系：可复用的 AI 任务工作流

`.qoder/skills/` 下定义了 5 个核心 Skill，覆盖任务全生命周期：

| Skill            | 触发词                                   | 职责                                                         | 状态交互                      |
| ---------------- | ---------------------------------------- | ------------------------------------------------------------ | ----------------------------- |
| `task-init`      | "新建任务"、"feature开发"、"技术调研"    | 分支确认 -> 上下文加载 -> 方案设计 -> 用户确认               | 创建 task，初始 `in-progress` |
| `task-resume`    | "继续之前的"、"回到任务X"                | 读取 task 文件 -> 恢复上下文 -> 进入执行                     | 读取状态，不修改              |
| `task-status`    | "查看进度"、"下一步做什么"               | 定位 task -> 汇总进展 -> 下一步建议                          | 读取状态，不修改              |
| `task-review`    | "帮我看一下"、"review一下"、"能提交了吗" | 检查当前改动 -> 修复循环 -> 输出审查报告                     | **不管理状态**，仅审查        |
| `release-review` | "ship it"、"发版审核"、"release review"  | 变更范围识别 -> 代码差异分析 -> 风险评估 -> 发布 Checklist -> 审核报告 | 归档时标记 `done`             |

**核心原则**：状态流转由用户意图自动触发，**不绑定特定 Skill**。`task-review` 仅负责审查，不负责状态管理。

## 六、任务状态与 Git 流程协同

### 6.1 状态定义

| 状态          | 含义                   | 使用阶段                            |
| ------------- | ---------------------- | ----------------------------------- |
| `in-progress` | 开发中                 | feature/hotfix 分支，默认初始状态   |
| `in-test`     | 已合入 develop，测试中 | feature/hotfix 分支，提交时自动流转 |
| `done`        | 已完成                 | 仅用于归档文件（`archived/` 目录）  |

### 6.2 流转规则

- **R1**：用户在 `feature/*` 或 `hotfix/*` 分支执行"提交"，且状态为 `in-progress` -> 自动更新为 `in-test`
- **R2**：用户在 `feature/*` 或 `hotfix/*` 分支继续提交，状态已为 `in-test` -> 保持 `in-test`，仅同步文档内容
- **R3**：**硬卡点** - AI 禁止在 `develop` / `release` / `master` 分支修改任何代码文件（含 task 文件）

### 6.3 合并前置检查

| 阶段                      | 前置条件                  |
| ------------------------- | ------------------------- |
| feature/hotfix -> develop | `task-review` 检查通过    |
| release/* -> master       | `release-review` 审核通过 |

## 七、审查机制：轻重两级

### 7.1 task-review（轻量：规范拦截）

- **触发**："帮我看一下"、"review一下"、"能提交了吗"
- **范围**：当前工作区变更（默认）或分支全部变更（`--full`）
- **工具层**：`mvn validate -Pcheckstyle`、`mvn spotbugs:check`、`mvn pmd:check`
- **AI 层**：代码规范扫描（Controller/Service 分层、Result<T> 泛型、Feign 路径、Mapper XML 绑定、防御性编程、日志脱敏、Javadoc）
- **Checkstyle 分层**：diff 范围内的 violation 为"本次引入"必须修复；diff 范围外的为"历史遗留"标注但不阻断

### 7.2 release-review（全量：风险评估）

- **触发**："ship it"、"发版"、"发布"、"release review"、当前分支为 `release/*`
- **基线**：必须以 `master` 为对比基线（生产环境当前代码），禁止以 develop 为基线
- **硬卡点**：
  - 卡点一：release 分支包含未完成的 feature -> 阻断发布
  - 卡点二：高风险项无回滚预案 -> 阻断发布
  - 卡点三：配置类审查时仅依赖 diff 判断 `@RefreshScope` -> 必须读取完整源文件
- **输出**：按模板产出 `release_YYYYMMDD.md` 审核报告（控制在 2 页内），含变更摘要、配置变更汇总、外部依赖、横向能力影响、历史数据兼容性、风险评估与分级、发布 Checklist、审核结论

## 八、RepoWiki：代码事实基线

`.qoder/repowiki/` 是代码的「事实基线」，与 `.ai/`形成互补：

| 维度     | `.qoder/repowiki/`                                     | `.ai/04-knowledge/modules/`                           |
| -------- | ------------------------------------------------------ | ----------------------------------------------------- |
| 定位     | 代码事实（类列表、接口签名、架构设计、技术栈完整说明） | 协作上下文（风险、决策、AI 注意事项、坑点、废弃标记） |
| 粒度     | 按 Maven 聚合工程组织                                  | 按具体模块拆分                                        |
| 更新频率 | 随代码变更同步更新                                     | 随认知沉淀更新                                        |

**阅读顺序建议**：

1. 先读 `.ai/04-knowledge/modules/module-xxx.md`的「当前风险」和「AI 注意事项」
2. 再读 `.qoder/repowiki/` 对应模块的「架构设计.md」和「技术栈.md」获取代码事实
3. 编码时按需查阅 `.qoder/repowiki/` 的「编码规范.md」和「特殊配置与命令.md」

## 九、关键设计决策总结

| 决策点                | 选择                                                | 理由                                                         |
| --------------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| `.ai` vs `.qoder`分离 | 决策约束 vs 事实执行分离                            | 避免 AI 在「应该做什么」和「事实是什么」之间混淆，提升上下文加载效率 |
| AI 行为约束独立成规则 | `.qoder/rules/`专门约束 AI 自身                     | 项目代码规范（`.ai/02-rules/`）与 AI 行为约束（`.qoder/rules/`）职责分离 |
| 硬卡点 vs 软提示      | 关键节点硬阻断（分支、审查、合并）                  | 防止 AI 在关键流程上「猜测执行」，降低风险                   |
| 知识回流不自动写入    | AI 主动提醒，用户确认后才写入                       | 避免 AI 将未验证的假设或讨论结论写入项目知识库，保证知识质量 |
| 状态与 Skill 解耦     | 状态流转由通用行为触发，Skill 只负责业务逻辑        | 避免 Skill 之间状态管理冲突，提升体系可扩展性                |
| 环境感知内嵌          | `AGENTS.md` 中声明环境事实与行为约束映射            | 让 AI 在不同环境（Windows/Linux、不同 IDE）下自动调整行为    |
| 审查轻重分离          | task-review（规范拦截）+ release-review（全量风险） | feature -> develop 阶段轻量快速，release -> master 阶段全面审慎 |

## 十、体系自洽性要点

1. **入口唯一**：`AGENTS.md` 是 AI 项目上下文的唯一入口，轻量级导航，不承载详细规则。
2. **Checklist 前置**：任何代码操作前必须完成 L1 确认 + 分支确认 + 场景路由。
3. **工具即约束**：通过强制指定工具（SearchReplace/Write/DeleteFile）约束 AI 行为，而非仅靠文本提示。
4. **双向引用**：`.ai/` 文档通过 Front Matter 的 `dependencies`/`impacts` 字段建立依赖图谱，`.qoder/repowiki/` 通过索引建立路由。
5. **防膨胀机制**：行数/条目/重复/过时四维检查，确保文档体系可持续维护。
6. **发布即回流**：以 release 发布为唯一节点触发 L2 知识回流，保证知识沉淀的节奏感与一致性。

## 十一、演进愿景：从静态文档到活的知识图谱

当前 `.ai/` 目录采用编号分层结构（`01-workflows/`、`02-rules/`、`04-knowledge/` 等），这是体系早期的组织方式。项目的长期演进目标是将 `.ai/` 从**静态文档仓库**升级为**活的知识图谱**，核心思路如下：

### 11.1 设计理念：文件即节点，元数据即边

借鉴 Linux 哲学——"一切都是文件"，每个 `.ai/` 文档既是可读文本，也是知识图谱中的一个**自描述节点**：

- **自描述**：Front Matter 承载文件的类型、状态、优先级、所有者、标签等元信息
- **自约束**：`_directory.md` 定义本目录下文件的命名规范、必需字段、允许类型
- **显式依赖**：`dependencies` 字段声明"我依赖谁"，`impacts` 字段声明"谁受影响"

通过 `dependencies` / `impacts` 实现类似 `ldd` / `lsof`的依赖可视化与影响分析：修改某个决策文档时，可向上游追溯所有受影响的工作流和 Skill。

### 11.2 目录扁平化方向

长期目标是精简当前 `01-11` 编号目录结构，转向**扁平化前缀命名 + Front Matter 元数据驱动**：

| 当前结构                                | 未来方向                     | 元数据区分        |
| --------------------------------------- | ---------------------------- | ----------------- |
| `01-workflows/task-lifecycle.md`        | `workflow-task-lifecycle.md` | `type: workflow`  |
| `02-rules/boundaries.md`                | `rule-boundaries.md`         | `type: rule`      |
| `04-knowledge/modules/module-record.md` | `knowledge-module-record.md` | `type: knowledge` |
| `05-decisions/decisions.md`             | `decision-architecture.md`   | `type: decision`  |
| `08-reviewers/skill-reviewer.md`        | `reviewer-skill.md`          | `type: reviewer`  |

**好处**：

- 减少目录层级，降低文件定位成本
- 文件名即携带类型信息，无需依赖目录名判断
- 前置编号不再成为扩展瓶颈（新增类别无需重新编号）
- 检索和过滤完全由 Front Matter 驱动，文件名仅保证人类可读性

### 11.3 三阶段演进路线

| 阶段                         | 目标                                                      | 关键动作                                                     |
| ---------------------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| **一期：约束内聚**           | 在现有编号目录内推广 `_directory.md`约束文件              | 定义 `_directory.md`通用 schema；在 `08-reviewers/` 等小范围实验；更新审核路由速查表 |
| **二期：依赖显式化**         | 让 Front Matter 的 `dependencies`/ `impacts` 成为标准实践 | 全目录推广 `_directory.md`；改造结构审查器为完全约束驱动；要求新增文档必须声明依赖 |
| **三期：图谱化与扁平化评估** | 生成 `_index.md` 依赖图谱，评估目录扁平化可行性           | 基于 Front Matter 生成全局依赖图谱；评估 `01-11` 编号目录是否转为前缀命名；验证扁平化后检索效率是否可接受 |

### 11.4 与现有体系的兼容性

扁平化是**长期演进方向**，而非立即重构。当前阶段的核心策略是：

- **先规范元数据**：无论目录是否扁平化，强制要求每个 `.ai/` 文档具备完整的 Front Matter（含 `dependencies` / `impacts`）
- **先内聚约束**：通过 `_directory.md` 让编号目录内部先实现自约束
- **后评估结构**：当元数据质量足够高、依赖图谱可自动生成后，再评估是否值得做物理目录的扁平化迁移

> 这一愿景的本质是：让 `.ai/` 目录从"人找文档"进化为"文档自组织"，最终让 AI 在打开项目的第一时间就能通过文件的元数据网络，自动构建出项目的完整知识拓扑。
