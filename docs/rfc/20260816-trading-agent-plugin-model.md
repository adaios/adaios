## 〇、三阶段模型（用户原话整理）

| 阶段 | 形态 | 能力 | 有没有行情数据 | 有没有交易规则 |
|:----:|:-----|:-----|:-------------:|:-------------:|
| 一 | 直接对接大模型问答 | 通用问答 | ❌ 很可能没有 | ❌ |
| 二 | + websearch / webfetch / api 拿数据 | 有数据的问答 | ✅（行情插件接入）| ❌ |
| 三 | + 自己的交易规则插件化注入上下文 | 按我的纪律出建议 | ✅ | ✅（交易系统插件接入）|

用户原话关键句：
- 「第一阶段，直接对接大模型，进行问答（但很可能没有股市行情数据）」
- 「第二阶段，通过 websearch, webfetch 或者 api 可以拿到具体数据」
- 「第三阶段，我有自己的交易规则，插件化引入后，再给大模型的上下文中就可以给出我的具体规则」

## 一、核心原则（用户确认）

1. **行情服务跟着插件走** —— 行情是**数据载体插件**，不是全局基础服务。「没配置插件代码就没用了」的真正含义：数据是插件层，跟着插件的启用走。
2. **交易知识 + 决策 = 抽象层（jar）** —— 规则、纪律、策略、复盘方法论，是交易系统插件的**内容**。
3. **数据 = 具体载体（jar）** —— 行情、持仓、逐笔流水，是**数据插件**的**内容**。
4. **两者都是插件** —— 抽象层 jar 与载体 jar 分开，按用户叠加。
5. **一个用户有没有行情插件、有没有交易系统插件，是不一样的** —— 能力差异 = 插件组合差异。

## 二、能力叠加矩阵

```
 用户           行情插件   交易插件   交易 Agent 能力
 ─────────────────────────────────────────────────────────────
 阶段一用户        ✗         ✗      通用问答：问「什么是均线」能答，
                                   但「京东方现在该不该买」无据可答
 阶段二用户        ✓         ✗      有数据：能查现价/涨跌/K线，
                                   但回答不带纪律（无止损/仓位规则）
 阶段三用户        ✓         ✓      完整形态：有数据 + 按 R1-R120 出建议，
                                   止损硬判定、仓位超限、买点对照
```

**关键**：阶段不是「产品版本」，是**用户的插件组合**——同一套代码，不同用户落在不同阶段。

## 四、行情插件与交易插件的关系

```
┌───────────────────────────────────────────────────┐
│  交易 Agent（按用户组合）                            │
│  ┌─────────────┐   ┌───────────────────────────┐  │
│  │ 大模型       │   │ 交易规则插件（抽象层 jar）   │  │
│  │ 分析引擎      │◄──│ rules / strategy / mistakes│  │
│  │（框架内置）    │   │ 止损/仓位/买点/复盘纪律      │  │
│  └──────┬──────┘   └───────────────────────────┘  │
│         │ 上下文注入                                │
│  ┌──────▼──────┐                                  │
│  │ 行情插件     │◄── websearch / webfetch / api    │
│  │ 数据载体 jar │    TencentMarketDataSource       │
│  │ 现价/K线/涨跌 │                                  │
│  └─────────────┘                                  │
└───────────────────────────────────────────────────┘
```

**抽象层与载体的边界**（jar 概念）：

| 维度 | 交易规则插件（抽象层）| 行情插件（数据载体）|
|:-----|:---------------------|:-------------------|
| 内容 | 规则/纪律/策略/教训 | 行情/持仓/流水 |
| 变化频率 | 慢（你审核沉淀）| 快（每秒波动）|
| 所有权 | adai 私有 | 可第三方提供 |
| 谁注入 | Context Engine（知识）| 数据源（查询时）|
| 例子 | R66 止损硬约束、R81 仓位上限、B1 买点 | 腾讯行情、websearch 结果、券商 api |

## 五、输出形态（复用 trading-engine 三形态）

```
一个内核，三种出口（trading-engine build-engine 已定义）：
  ① 阿呆插件    —— 现状延续（Context 注入 + /advice 端点）
  ② 独立 Agent  —— Skill / Coze / Dify（人设+技能+记忆）
  ③ REST/MCP   —— Python FastMCP（行情生态强）供其他应用调
```

平台建议：扣子 Coze（快速体验，股票插件，发布豆包/微信）/ Dify 自托管（数据自主）/ 自建（完全可控）。交易 Agent 规则明确，用最简栈：Python + FastMCP + 行情 API + 规则引擎，不引入 LangChain 重型框架。

## 七、边界

- **不建议引擎 = 记账工具**：建议是输出（最多建议减仓/清仓），不是执行按钮，人做决策。
- **规则插件不开放**：交易规则 jar = adai 私有（沿用 20260814 D2）。
- **行情插件可第三方**：数据载体无私有性，未来可接任何源（websearch/券商/开源行情）。
- **阶段二 ≠ 阶段三**：有行情无规则，只能「查」，不能「按纪律建议」——这是用户能力差异，不是缺陷。
