# 交易 App 端形态重做——「一句判断 + 一行持仓」与截图入账三条主线

> **触发来源**：2026-09-24 用户（原话）——「**目前我对 app 端的交易插件还是不满意，web 端目前还行**」，
> 并给出关键判断依据：「**结合 Shopify 上周宣布移动版放弃 React Native，改用 Swift 和 Kotlin 新闻，
> 我就感觉 app 和 web 是两个角度，所以 UI/UX 等方面其实是完全不一样的**」，
> 以及方法要求：「**我希望你整理几个问题，我来选择，通过问题，你知道我的问题焦点，然后去整理布局功能等**」。
> 范围澄清（同轮，用户原话）：「**你说的是交易插件的主页吧，我不改阿呆的主页**」。
>
> **本 RFC 的定位**：2026-09-18 那件（`20260918-trading-app-restructure.md`）定的是**结构分层**
> （记录 → 对账 → 照见 + 两条铁律）；本件定的是**形态与主线**——首屏长什么样、
> 每天走的那条路（截图入账 → 确认 → 看账）怎么变顺，以及哪些事**明确不做**。
> 两者不冲突：本件承接前件的三层与铁律，把「首屏」与「截图入账」具体化；前件的 A1/A2/B/C 批次并入本件 §七。
>
> **实施边界**：本文为**文档先行件**（用户 2026-09-24「先成文档吧，今天不搞了」授权的产物就是这份文档本身）。
> **获批前不改任何代码、不动任何 `data/` 数据**；获批后按 §七 分批开工。

## 二、七问与拍板（2026-09-24）

| # | 问题 | 用户选择 | 落到设计上的含义 |
|:--|:--|:--|:--|
| 1 | 「还是不满意」最接近哪几条 | **c 主线不顺 · b 没有主心骨 · e 太常规**（未选 a 形态不像 App、未选 d 数字不敢信） | 问题在**形态**不在功能齐不齐；数字信任另案（见 §5.3） |
| 2 | 主要在什么时候用 | **不固定**（碎片时间） | 不能有「盘中模式 / 盘后模式」假设——**进来 3 秒必须自解释**；首屏不依赖「现在几点」 |
| 3 | 首屏主位 | **持仓与判断**（我拿着什么、阿呆怎么说） | 主心骨只有一件事：**这个仓现在什么状态、要不要动** |
| 4 | 结构骨架 | 「你说的是交易插件的主页吧，**我不改阿呆的主页**」 | 骨架题在「不动 app 导航」的前提下重问 → 收敛为本件的**页内分层**（§四），不是全 app 级 Tab 重构 |
| 5 | app 与 web 分工 | **app 管随身那一半**（看 + 记 + 收通知），深度管理留 web | 不把 web 的导入/规则/案例/历史搬上来——**不做第二个 web** |
| 6 | Shopify 那条新闻的意思 | **先定设计再谈换栈** | 本件只出设计；技术栈另立件 |
| 7 | 哪些能力「动了我会生气」 | **7 项全选**：截图入账 · 一句话记录 · 持仓卡+阿呆说 · 推送 · 对账与口径提示 · 复盘 · 收益日历+资金转入转出 | **一个都不删。** 这条最硬——所以解法只能是「分层，不分家」（§四） |

**由此产生的核心张力（本件的出发点）**：
**「7 样都不能删」×「不能是常规卡片堆叠」×「要有主心骨」——三条同时成立，唯一解法是分层，但不分家**：
功能全留、入口不减，但**首屏只放两样**（判断 + 入账 + 持仓 = 主心骨一件事的三种面貌），
其余按**时机**出现（今天区）或**下沉**为二级页。用户要的不是「排得更好看的 15 个区块」，
是「**什么时刻该看见什么**」。

## 三、现状事实（钉到行号 / 实测）

### F1 · 页面仍是单列区块流

`trading_page.dart` 的 `build`（`:1110`）内 `ListView` 顺序（`:1158-1242`）：

```
隐私条(:1158) → 行情横幅(:1164) → 账实横幅(:1171) → 每日入账(:1175)
→ 精确表单(:1182) → 上传在途(:1187) → 候选卡(:1192) → 逐笔回执(:1197)
→ 未记行(:1202) → 持仓区(:1219) → 复盘横幅(:1223)
→ 折叠区「资金与配置」(:1227，含快照卡:1231 / 资金:1233 / 活跃市值:1237)
→ 折叠区「今天的操作」(:1242)
```

2026-09-18 首次重排（RFC 20260918 §3.2/A2）已把「每日入账 + 持仓」提前、金额打码，
但**形态未变**：仍是长单列，两类横幅各占一张卡，账户 6 个指标行仍在。

### F2 · 生产写操作分布（用户真实用法，全期实测）

来源 `REVIEW.md` P2-交易59（`api-access.log` 全期写操作）：

| 动作 | 次数 | 备注 |
|:--|--:|:--|
| 截图入账链路合计 | **56** | `trades/parse` 13 · `screenshots` 12 · `trade-log/date` 16 · `trade-log/confirm` 10 · `DELETE trade-log` 5 |
| 要建议 | 17 | 点持仓卡弹「阿呆说」 |
| 导入（web 侧） | 23 | — |
| 忽略推送 | 12 | — |
| AI 复盘 | 2 | — |
| 案例库标注/匹配 · 16 项规则参数 · 三维打分 | **0** | 分析层无人使用 → 该层已砍（用户拍板 B） |

**结论**：app 的真实用法高度集中在**截图入账 + 看建议 + 看推送**三处。
用户选「c 主线不顺」且第一张截图链路就是最大头——**这条线不顺，等于 app 一半的日常不顺**。

### F3 · 三个焦点的物理成因

| 用户焦点 | 物理成因（可验证） |
|:--|:--|
| **b 没有主心骨** | 首屏没有「结论」。持仓是**卡片列表**（`_buildPositionCards` `:2480`）——5 只票每只一张卡 ≈ 2~3 屏；用户要自己读完 5 张卡才知道「我现在什么情况」。账户卡 6 个指标行（`_buildSnapshotCard` `:2135`）同样只给数字、不给结论 |
| **c 主线不顺** | 见 F4 三条 |
| **e 太常规** | 暗色底 + 卡片 + 指标行 + 大字号盈亏 = 任何一个券商 App 的形状；「阿呆」只剩一个弹层（`_AdviceSheet` `:3081`），页面上没有它的声音。与 B1 铁律「我和阿呆的自然对话」相比，**形态上没有体现阿呆** |

### F4 · 三条卡点的实现证据（用户 2026-09-24 亲选）

| 卡点 | 证据 |
|:--|:--|
| **① 选图后等太久** | `POST /trading/screenshots`（`TradingController.java:1170`）是**同步**接口：一次 multipart（1-3 张）在服务端跑完所有图的 VLM 才返回。代码注释自陈「**VLM 最坏 90 秒（3 张 × 单图 28s）**」（`trading_page.dart:1380`）。2026-09-18 实测后果：用户 10:34、10:35 **连传两次**同一批成交（生产日志两次各 6 笔） |
| **② 候选逐笔确认太啰嗦** | 候选卡（`_buildCandidatesCard` `:1444`）逐笔渲染，每笔独立「确认/丢弃/补日期」；已加保护（丢弃有确认弹窗 `:774`、在途占位卡 `:1382`、逐笔回执 `:1536`、未记行 `:1574`）——**但形态仍是「每笔都要你过一遍」** |
| **③ 落完账跟持仓/资金对不上** | 回执（`_buildConfirmReceipt` `:1536`）只说「记上了哪几笔」，**不说「这次改变了什么」**（持仓 N→M、现金 ±X）。账实横幅（`_buildIntegrityBanner` `:361`）只在**进页时**拉一次，入账后不重算。现金/本金口径：后端 P2-交易69 已出 `cashDate`/`cashNote`（2026-09-23），**app 未接**。而 09-23 对账的硬结论是——现金在两次资金查询之间会漂（曾漂成 **−6,093.97**），总盈亏真值 **106,180.86 − 150,000 = −43,819.14**（系统当时显示 −20,132.99），本金 15 万系用户手填、2025-04 以来历史出入金零记录（P2-交易64/66） |

## 四、目标形态

### 4.1 首屏（回答三个问题：我现在什么状态 / 有没有事等我 / 我该不该动）

```
① 一句判断 —— 先说结论（用户拍板「先说结论」）
   「5 只 · 不用动。」                          ← 常态，就这一句
   「5 只 · 有 1 只破了止损：云南锗业 88.1」      ← 有事时换成这句
   小字仅在有事时出现：账对不上 / 行情没取到 / N 笔待入账
② 入账   [ 📷 截图入账 ]        [ 一句话 ]
③ 持仓 —— 一行 + 就地展开（用户拍板形态）
   云南锗业   +12.4%   +1.1%   止损 88.1  ⚠  ⌄
     └ 就地展开三条：成本与仓位 · 批次 · 这只票阿呆怎么说
   点整行 → 该票全貌（批次明细 / 历次回合 / 改止损）
④ 今天（时态区：有事才出现，无事零占位）
   待确认的推送 · 账实与现金口径提示 · 今日复盘
   深处入口（常在一行）：收益日历 · 资金 · 推送设置 · 复盘历史
```

**关于①的成本纪律**：那句判断**不是新加一次 LLM 调用**，而是把既有确定性数据汇成一句——
持仓盈亏 + 规则引擎硬判定（R66 破止损 / R81 超仓位）+ 待入账数 + 账实与行情状态。
渲染逻辑复用早盘/尾盘推送的 `TradingDecisionNarrator`（RFC 20260922，已有「先结论、带四要素」口径）。
LLM 只在需要成句时才碰；**取不到数据就说取不到，不编**（与前件两条铁律一致）。

### 4.2 三处关键取舍

| 现状 | 改为 | 理由 |
|:--|:--|:--|
| 账户 6 个指标行（资产/可用/可取/市值/当日/本金）常驻 | **收成一行可展开** | 用户 09-18 原话「总资产堆积太多东西了」+ 本轮 7 项全选（不能删）→ **保留、折叠** |
| 行情横幅 + 账实横幅各占一张卡 | **并入①那句判断** | 无事连一行都不给（现状是两张卡占位）；有事才说话 |
| 推送 / 复盘 / 对账 常驻区块 | **移入④「今天」时态区** | 不是每天都用，但每天都要能一眼看到「今天有没有事」 |

## 五、三条卡点的解法（含代价，不粉饰）

### 5.1 · 选图后等太久

根因：`/trading/screenshots` 同步跑完 1-3 张图的 VLM 才返回，客户端除了转圈无事可做。

| 路线 | 做法 | 代价 / 前提 |
|:--|:--|:--|
| **A（推荐）** | app 侧**一张一张提交**（3 张 = 3 次单图请求），28 秒出第一笔候选，进度 1/3 → 2/3 → 3/3 | 后端现有**跨截图去重（`sameTrade`）会失效**（同一笔出现在两张图里可能出重复候选）→ 需在客户端按「方向 + 代码 + 价 + 量 + 日期」指纹补去重（与 2026-09-15 防重复入账同一口径）。**不动后端契约** |
| B | 后端改异步任务：提交即返 jobId，逐图落结果，app 轮询 | 更干净，但要动后端 + `api-spec.md`，跨批（本件范围外，需另议） |
| 最小解法 | 提交方式不动，只给**进度条 + 已认出 N 笔** | 若 90 秒本身可忍、只是想「知道还要多久」，这条最省 |

**待用户点选**（decided-by 已标注为未决）。三选一，不由 AI 自行拍板。

### 5.2 · 候选逐笔确认太啰嗦

改为**默认全信、异常才叫你**：

- 识别正常的一笔：**默认勾上**，底部一个「都记上（3 笔）」；
- 可疑项**摘出来单独醒目**，其余折叠成一行「另外 2 笔看着没问题」。

**可疑判据（地基，不是装饰）**——前端按已有字段即可判定，无需改后端：

| 判据 | 依据字段 |
|:--|:--|
| 缺成交日期 | `tradeTime` 为空（现有「补日期」流程 `PUT /trade-log/date`） |
| 价格 / 数量异常 | price ≤ 0 或 volume ≤ 0 |
| 方向不明 | direction 空或非法 |
| 与持仓矛盾 | 卖出超持仓 / 卖出未持有 |
| 疑似重复 | 指纹（同标的 + 同方向 + 同价 + 同量 + 同成交日）命中既有流水或同批候选 |
| （可选增强）低置信 | 需后端补置信度字段——**本期不做**，如实留白 |

**红线**：这个位置出过事——2026-09-13 漏一行等于静默删一只持仓；2026-09-15 同一张截图重复提交把 600536 记成 1000 股（真实 800）。
因此「少问一次」必须建立在「异常一定认得出来」上。取舍明确：**宁可多标可疑（多问几次），不可放过一笔**。
若某类判据做不到可靠，该项目**留在必看列表**，不进折叠区。

### 5.3 · 落完账跟持仓/资金对不上

先说清楚：**这条不全是 UI 问题**（§F4 ③ 的数据是硬的）。app 本轮做三件：

1. **入账回执升级**：不只「记上了」，而是「**这次改变了什么**」——持仓 N→M 股、现金 ±X、落了第几笔流水；
   「只补流水、未回放持仓/现金」的行**如实标注**（`trading-features.md` §八 注意点 8 的口径）。
2. **入账后立刻跑一次对账自检**（`GET /trading/integrity`），差异当场说（差多少、哪几只），
   不再让用户回电脑才发现。失败静默降级、绝不说「没问题」（沿用 P2-交易39 的分支）。
3. **现金与本金带上日期和置信度**：接后端 `cashDate` / `cashNote`（P2-交易69，双端同文案、单一真相源在后端）；
   本金标注「这是你填的数」。

**app 不做的（诚实边界）**：历史出入金补录、锚定日修史、通达信文件导入。
**app 的职责是让你立刻知道「对不上、差多少」，不是让你在手机上修好**——这正对应「app 管随身那一半」。

## 六、本轮明确不做（免得跑偏）

1. 不把 web 的导入 / 规则参数 / 案例库 / 三维打分 / 交易历史搬上 app（用户拍板：app 管随身那一半）；
2. 不动阿呆主页 Feed、Launcher、底部导航（用户原话：「我不改阿呆的主页」）；
3. 不换技术栈（Flutter → Swift 原生另立件；用户拍板「先定设计再谈换栈」）；
4. 不加任何下单 / 平仓 / 减仓执行按钮；
5. 不新增 AI 调用来做首屏那句判断（复用确定性数据 + 既有渲染器）；
6. 不改后端契约（除 §5.1 若选路线 B）。
