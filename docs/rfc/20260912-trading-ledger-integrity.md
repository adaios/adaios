# 交易账本完整性——快照锚点 fail-closed + 幂等统一 + 卖超可见

> **一句话**：2026-09-12 生产实测——一次「历史成交导入」把**已经含在券商快照里的成交又重放了一遍**，持仓与现金双计（现金被算成 **-26666.85**，正确值 ≈ **1381.93**），同时 **3 笔真实卖出被静默丢弃**、**4 笔流水重复落账**，导致「券商快照 / 逐笔流水 / 派生持仓」三条真源互相矛盾。本 RFC 定义**账本完整性契约**：快照锚点 **fail-closed**、append 与 replay **同一套幂等判定**、卖超**永不丢数据**、账实不符**当天可见**（自检端点 + deploy-gate 门禁），并把「已修」的判据从「代码改过」升级为「存量回填 + 运行时自检 + 失败可见」。

## 一、目标与验收

| 层 | 交付 | 验收标准 |
|---|---|---|
| P1 锚点 fail-closed | 锚点状态读不到时**禁止**任何改动持仓/现金的动作 | 锚点未知 + 存在需重放的行 + `mode != append` → **400**（人话 + 两条逃生路径）；**无任何文件被写**；绝不静默重放 |
| P2 派生量口径 | 持仓/现金 = **锚点快照 + 锚点之后事件净变化** | `entryDate ≤ 锚定日` 的行只补流水（持仓/现金零变化）；`> 锚定日` 才重放；09-12 场景回放得 002428 400 / 600206 900 / 600601 100 / 603113 0 / 其余 0 |
| P3 幂等统一 | 一个 intake、一个键空间：所有来源共用同一判定 | 重复导入不新增行（`new = 0`、`merged ≥ 1`）；orderId 与指纹**双键都判**，与旧行有无 orderId 无关 |
| P4 卖超可见 | 真实成交永不因系统状态不准而丢弃 | 卖超/未持有 → **流水照落** + `rejected` 行级明细 + ERROR 日志 + 计入账实缺口；不再出现「WARN 后消失」 |
| 对账闸门 | 账实不符**当天可见**（替代肉眼发现） | `GET /trading/integrity` 的 `derived = 锚点快照数量 + 锚点后流水净增减`；`drift` 非空或 `anchor.known=false` → deploy-gate **显式告警** |
| 存量自愈 | 无锚点的老环境可显式回填 | `PUT /trading/anchor` 写入锚点（日期**只前进**、不自动改数据）；回填后 fail-open 窗口关闭 |
| 回归 | 不破坏既有 lot / 清仓 / 推送 / 复盘口径 | 后端全量测试全绿 + §九 用例 R1~R12 全绿 |

## 二、现状核对（2026-09-12 生产实测）

### 2.1 三条真源（先立口径）

| # | 真源 | 载体 | 语义 | 实测现状 |
|---|---|---|---|---|
| ① | **券商快照** | 导入的「持仓股」/「资金股份查询」→ `positions.md` + `account.json` | 券商**当下真相**（已含此前全部成交结果） | 最后一份 = **2026-09-09**（持仓 600206 600 / 600601 900 / 603113 1900 / 002428 300；余额 2278.16） |
| ② | **逐笔流水** | `data/{userId}/trading/trades/YYYY-MM.json` | 每笔成交的**事实记录**（唯一可审计层） | **缺 3 笔卖出、多 4 笔重复** |
| ③ | **派生持仓** | `positions.md` 数量/成本 + `account.json` 现金 | 应为「① 最近锚点快照 **+** ② 锚点之后事件净变化」 | 与 ①② **均不一致**（002428 300/真实 400、600206 1500/真实 900、600601 整行消失/真实 100、603113 1900 幽灵/真实 0） |

**契约核心**：③ 必须恒等于「① + ②（锚点日之后）」。三者互斥 = 故障；本文所有条款都为这条等式服务。

### 2.2 三层故障结构

| 层 | 故障 | 证据（2026-09-12 核对） | 为什么长期没人发现 |
|---|---|---|---|
| **机制层** | **fail-open**：锚点文件读不到 → 返回空锚点 → 「券商快照锚定防重」（P2-交易34）**静默失效并继续重放** | 生产 `/opt/adaios/data/adai/trading/` 下**根本没有 `snapshot-anchor.json`**；锚定日恒为 `null` → 全部近日成交走 replay | 「读不到」被当作「新用户/无锚点」，无 ERROR、无告警；连日志都没有 |
| **流程层** | P2-交易34 在 REVIEW 标「**已修**」，但**无存量回填、无运行时自检、无可见性** | 该机制代码 2026-09-10 08:18 才部署；最后一次「持仓 replace / 资金股份」导入是 **2026-09-09 21:23（早于部署）** → 锚点从未写入，也无人回填 | 「已修」的判据是「代码已改 + 单测绿」，不是「生产状态正确」 |

## 三、目标行为

### 3.1 四条原则（不可协商）

| # | 原则 | 含义 | 今天怎么违反的 | 实现判据 |
|---|---|---|---|---|
| P1 | **快照锚点 fail-closed** | 锚点状态**读不到**时，禁止执行任何会改动持仓/现金的动作；要么报错指路，要么显式降级为 append | 读不到 → 空锚点 → 继续重放 | 锚点未知 + 存在需重放的行 + `mode != append` → **400** |
| P2 | **持仓/现金是派生量** | `③ = ① 最近锚点快照 + ② 锚点日之后事件净变化`；锚点日**及之前**的成交只补流水、不再入账 | 09-08/09-09 行被重放，与快照重复计 | `entryDate ≤ 锚定日` → append-only；`> 锚定日` → replay |
| P3 | **一个 intake、一个键空间** | 历史成交导入 / 截图归集 / 记录归集 / 手动记录共用**同一套幂等判定** | append 对有 orderId 的行不查指纹（replay 才查）→ 同笔两落 | 两模式走**同一函数**；orderId 与指纹双键都判 |
| P4 | **真实成交永不因系统状态不准而丢弃** | 系统状态不准是**系统的问题**，不是丢用户成交的理由 | 「未持有/卖超」→ 该笔直接消失 | 卖超 → 落流水 + `rejected` + ERROR + 计入缺口 |

### 3.2 锚点拆分规则（`mode=auto`）

| 行的 `entryDate` | 处理 | 是否改持仓/现金 |
|---|---|---|
| `≤ 锚定日`（`anchorDate = max(positionsReplace, cashImport)`） | 只补流水（append-only） | ❌ 不动（快照已含） |
| `> 锚定日` | 重放（replay） | ✅ 持仓 + 现金 |
| 为空的行 | 视同 `≤ 锚定日`（只补流水） | ❌ |

**`mode=append`**：所有行只补流水，不重放任何行、不动持仓/现金（锚点缺失时的安全模式）。

### 3.3 fail-closed 触发与逃生路径

| 触发条件 | 行为 |
|---|---|
| 锚点未知（文件缺失，或 `positionsReplace` 与 `cashImport` 皆空）**且**存在需重放的行 **且** `mode != append` | **400**，人话：**「还没建立券商快照锚点，我不能猜着改持仓和现金——请先导入一份『持仓股』或『资金股份』快照（我会把当天记为锚点），或者明确用 append 模式只补流水」** |
| 锚点已知 | 按 §3.2 拆分 |
| `mode=append` | 跳过锚点校验（不重放即无需锚点）；响应 `anchor.known=false` 时附提示但**不报错** |

> **禁止**：任何路径下「锚点缺失 → 静默按 replay 继续」（今天的故障即此）。

### 3.4 幂等统一判定（append 与 replay 同一套，按序执行）

| 序 | 条件 | 动作 | 计数 |
|---|---|---|---|
| 1 | `orderId` 命中既有流水 | 旧行缺 `tradeTime` / `fee` / `orderId` 的字段 → **合并回填**（只补空字段，不覆盖非空值） | `merged`（无字段可补 → `skipped`） |
| 2 | **指纹**命中：`symbol\|direction\|entryDate\|price\|volume`（**与旧行有无 orderId 无关**）**且成交时间一致**（都为空或相等） | **不新增行**；合并回填 `orderId` / `fee` / `tradeTime` | `merged` |
| 2′ | 指纹命中**但成交时间不一致** | **不得合并**——可能是同日同价同量的**两笔真实成交** → 按新行处理 | 落到 3 |
| 3 | 两者都不命中 | **新增**流水 | `new` |

- 指纹字符串固定 `symbol + "|" + direction + "|" + entryDate + "|" + price(stripTrailingZeros) + "|" + volume`（与既有实现同格式，便于存量比对）。
- **今天的漏洞必须闭合**：原 append 只在「无 orderId」分支查指纹 → 有 orderId 的行**绕过指纹检查**，正是 §2.5 四笔重复的成因。
- 数量 0 的资金事件（股息/红利税）走独立分支：股息类记账、其余计入 `nonTrades`（语义不变）。

### 3.5 卖超不丢数据

| 场景 | 行为 |
|---|---|
| replay 行卖出量 **> 当前持仓**，或该标的**未持有** | ① **流水照落**（记事实）；② **持仓/现金不动**；③ 进响应 `rejected`（行级 reason）；④ **ERROR** 日志（含 symbol/volume/持仓数/成交日期）；⑤ 计入 `GET /trading/integrity` 的 `gaps` |
| 同一行后续重传 | 走 §3.4 幂等：orderId 命中 → 已在流水 → `merged`/`skipped`，**不再重复报 `rejected`**；`rejected` 只描述「流水在、持仓未动」这一状态 |

> **禁止**：`WARN` 之后该笔从结果里消失；也禁止为了「让卖出成功」而伪造持仓。

### 3.6 锚点快照与日期单向

- 持仓 **replace** 导入成功 → 写 `positionsReplace`（当天）+ `holdings`（该次快照持仓）；资金股份导入成功 → 写 `cashImport`（**不动 `holdings`**）。
- 两个日期字段都取 `max(旧值, 新值)`：**只前进不后退**（乱序补导老快照不得把锚点往回拨，否则重新打开双计窗口）。
- 写失败：fail-visible（ERROR 日志 + 响应 `anchor.known=false` 如实反映），不静默。

## 四、数据与契约改动

### 4.1 `POST /api/v1/trading/trades/import`

**请求**：body 仍为 `{"content":"..."}`（通达信「历史成交查询」导出全文，GBK→UTF-8 已在上传层处理）；**新增 query 参数**：

| 参数 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `mode` | `auto` \| `append` | `auto` | `auto`＝按 §3.2 拆分；`append`＝全部只补流水，不动持仓/现金 |
| `dryRun` | boolean | `false` | `true`＝只回**计划**，**不写任何文件**（不落流水、不动持仓/现金、不留存导入文件） |

**响应（新增字段，原字段保留）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `imported` / `updated` / `skipped` / `nonTrades` | int | 保留；**语义收窄**：`skipped` **只表示幂等命中**，不再混入失败（失败进 `rejected`） |
| `merged` | int | **新增**：命中去重但做了字段回填的笔数 |
| `rejected` | array | **新增**，行级：`{symbol, name, direction, volume, price, entryDate, reason}`；`reason` 人话（如「卖出数量超过当前持仓（持有 N 股）」）。**语义：该笔已落流水、未入持仓/现金** |
| `anchor` | object | **新增**：`{positionsReplace, cashImport, known, anchorDate}` |
| `plan` | object | **仅 `dryRun=true`**：`{new, merged, skipped, nonTrades, wouldReject, anchorKnown, lines:[{symbol, direction, volume, price, entryDate, action, reason}]}`，`action ∈ new\|merged\|skipped\|nonTrade\|reject` |
| `lines` / `syncMode` / `summary` | 原样 | 对账行 / 模式 / 每日操作总结（`dryRun` 时 `summary` 为 null） |

### 4.2 `GET /api/v1/trading/integrity`（账实自检，只读）

```json
{
  "anchor": {"positionsReplace": "2026-09-09", "cashImport": "2026-09-09", "known": true, "anchorDate": "2026-09-09"},
  "drift": [
    {"symbol": "600206", "name": "有研新材", "snapshotQty": 600, "ledgerDelta": 300,
     "derived": 900, "holdings": 1500, "diff": 600, "note": "派生值与当前持仓不一致：多计 600 股"}
  ],
  "gaps": [
    {"symbol": "000776", "name": "广发证券", "kind": "rejected-sell",
     "detail": "09-04 卖出 600 未入持仓/现金（快照已归零，重放被拒）", "entryDate": "2026-09-04", "volume": 600}
  ]
}
```

| 字段 | 定义 |
|---|---|
| `derived` | **`锚点快照数量 + 锚点日之后流水净增减`**（`ledgerDelta` = 锚点日之后该标的买入量 − 卖出量） |
| `holdings` | 当前 `positions.md` 该标的数量 |
| `diff` | `holdings − derived`；**`diff != 0` 即 drift**（该标的进 `drift` 数组） |
| `snapshotQty` | 锚点 `holdings` 里的数量（缺 = 0，`note` 标注） |
| `gaps` | 未闭合的成交缺口：被拒卖出（§3.5）、锚点日之前有流水但快照无数量、负持仓等 |
| `anchor.known=false` | 视为**不健康**（drift 不可判定 → 响应带 `note`，deploy-gate 按失败处理） |

### 4.3 `PUT /api/v1/trading/anchor`（存量自愈回填）

| 项 | 契约 |
|---|---|
| body | `{"positionsReplace":"2026-09-09","cashImport":"2026-09-09","holdings":[{"symbol":"600206","name":"有研新材","quantity":600}]}`；`holdings` 可省 |
| 语义 | **用户/管理员显式动作**，用于存量环境补写锚点；**不自动改数据、不在导入路径里偷偷调用** |
| 规则 | 日期**只前进不后退**（同 §3.6）；非法日期 400 人话；成功返回最新 `anchor` |

### 4.4 `trading/snapshot-anchor.json`（锚点文件）

```json
{
  "positionsReplace": "2026-09-09",
  "cashImport": "2026-09-09",
  "holdings": [
    {"symbol": "600206", "name": "有研新材", "quantity": 600},
    {"symbol": "600601", "name": "方正科技", "quantity": 900},
    {"symbol": "603113", "name": "金能科技", "quantity": 1900},
    {"symbol": "002428", "name": "云南锗业", "quantity": 300}
  ]
}
```

- `holdings` 与 `positionsReplace` **同源同刻**，仅 replace 时整体覆盖；`cashImport` 不触碰。
- 文件缺失 = 锚点未知（**不是**「无锚点即重放」，按 §3.3 fail-closed）。

### 4.5 前端表现（web / app）

## 五、相邻机制与红线自查

- **与 P2-交易34 的关系**：该条即本 RFC 的病灶条目——原「锚定防重」机制**保留**（语义正确），本次补的是 **fail-closed + 存量回填 + 自检 + 可见性**四个缺口，不推翻原设计。
- **与 lot / 批次**：`TradingLotService.derive` 的「流水卖出超过买入批次」WARN 是**同一类静默降级**的表面；本 RFC 不重写 lot 推导，但负持仓必须进 `integrity.gaps`（把 WARN 变可见）。
- **与清仓（sold.json）**：清仓收录依赖「持仓卖到 0」这一状态；派生持仓错则清仓漏记（本次 603113 全卖未收录即实例）。本 RFC 只修账本口径，不改清仓判定逻辑，两者在修好口径后自然对齐。
- **与推送 / 复盘**：当日盈亏、收盘小结、复盘现金口径都读 `account.json`；现金错 → 这些全错。修好锚点后由既有链路自然恢复，**不新增口径**。
- **不自动改数据（B7 口径）**：本文档只定义契约；存量修正（补 3 笔卖出、去 4 笔重复、清负持仓）走**显式动作**（导快照 / `PUT /anchor` / 重新导入），不在导入路径里偷偷补齐。
- **B1 无第三视角**：`rejected` 与 drift 提示的用户可见文案都是「我和阿呆」的自然对话，不出现「系统/校验失败」等系统口径。
- **B3 隐私红线（硬约束）**：§九 的 golden 夹具**必须用合成数据**（虚构代码/名称/价格/编号），**不得把用户真实成交文件（`data/**`、生产导出 txt）放进 git**；本文保留真实**持仓数量与价格**作为复现证据，但不含任何真实身份信息（账号、股东代码等一律不出现）。
- **B8 外向动作**：本文档不含部署/外发动作；`PUT /trading/anchor` 是**用户显式调用**的写入口，不自动触发。
- **单实例约束**：锚点在**文件**里（多进程可读），本契约不引入新的进程内状态；沿用现有单实例约束。
- **多实例 / 并发**：`snapshot-anchor.json` 读写沿用 per-user 条带锁 + 原子写（既有约定），日期取 max 需在锁内完成。
