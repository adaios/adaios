# 产品内容消化（D 形态）：app/web 喂入 → 服务端抓取 → 结构化留存

> **方向 RFC**：用户在 **app/web** 丢一个链接（B站视频/文章）或一张图，说「整理这个」→ **服务端自己抓取**（元数据/字幕/正文）→ AI 按 learn 卡片模板结构化 → 落 `data/{userId}/learn/` → 对话流回一份结构化卡片。**本质是 A 形态（会话技能 `learn-digest`）的能力下沉到产品**——A 已跑通、模板已被认可，D 不重新设计内容形态，只补「产品入口 + 服务端抓取」两块。

---

## 一、背景（现状与问题，实测证据）

| # | 现状 | 问题 |
|:-:|:-----|:-----|
| A | **A 形态（DSH 会话技能）能力齐全**：抓元数据 → 字幕/正文/转写 → 六段结构化 → 落盘 `data/adai/learn/{type}/{topic}/` + `_raw/` 留痕 → 概念追踪（`ai-engineering/skills/learn-digest.md`，2026-09-06 首例 9 篇跑通） | **只在 DSH 会话内可用**：需要 Mac + DSH 在跑。**手机上、网页上没有任何入口** |
| B | **B 形态（产品内 learn 插件）已下架**（RFC 20260829 §九，2026-09-12）：投入 15 主代码文件 / 7 测试类 ~123 用例 / 13 端点 / 双端各 3 文件，**真实使用为 0** | 失败根因见 §二 1：**入口形态是对的，能力是错的**——要求用户自己搞到字幕再粘贴（≤50000 字），把最费力的一步留给用户 |

## 二、问题（病灶/缺口清单）

| # | 缺口 | 证据/影响 |
|:-:|:-----|:----------|
| 1 | **能力错位：该做抓取却没做**（B 的真实死因） | B 的喂入要求用户粘贴 ≤50000 字素材；而 learn 场景里最累的一步恰恰是「拿到字幕/原文」（B站字幕需工具、YouTube 需 yt-dlp、文章有反爬）。用户原话「B 太麻烦了，失去了意义」= **要我自己搬运，那我为什么不在浏览器里直接看** |
| 2 | **A 的能力锁在 Mac 上** | A 是「存在 DSH 技能文档里的一份操作规程」，不是产品能力。出门在外看到好视频 → 无入口 |
| 3 | **服务端无抓取能力**（本次要新建的核心） | 后端从未抓取过第三方内容页（现有主动外发只有行情 API/分红/Bark 推送）；抓取须新增平台适配 + 授权与配额策略（B8） |
| 4 | **异步授权难题** | 云端转写（fun-asr）要花钱且把音频发给第三方，B8 要求「先经人确认」；但产品内是异步流程，无法逐次弹确认 → 需要**预授权/配额制**（§四 决策点 3） |
| 5 | **产物契约可能分叉** | D 落地后同一目录会有两个写入方（DSH 技能 A / 产品 D）→ 必须共用同一产物契约（模板/`_raw/` 规则/幂等键），否则资产格式分裂 |
| 6 | **范围膨胀风险（B 的前车之鉴）** | B 除喂入外还堆了复习推送、复习流转、卡片编辑、交易候选反哺——**用户一次都没用过**。D 必须带明确「不做」清单 |

## 三、方案

### 3.1 一句话

**在 app/web 加一条内容消化通道：用户丢链接/图 + 说「整理这个」→ 服务端抓取（元数据/字幕/正文，无字幕走云端转写）→ AI 结构化 → 落 `data/{userId}/learn/{type}/{topic}/`（含 `_raw/` 留痕）→ 对话流回一份结构化卡片；想看全文时在对话里说「打开那篇」。**

### 3.2 与 A / B 的关系（形态三方对照）

| 形态 | 入口 | 抓取 | 内容形态 | 现状 |
|:-----|:-----|:-----|:---------|:-----|
| **A** 会话技能 | DSH（Mac） | ✅ 自动 | 六段模板 + topic 目录 + `_raw/` | ✅ 可用（操作规程，非产品能力）|
| **B** 产品插件 | app/web | ❌ **不做**（要用户粘素材）| 单源单卡平铺 | ⛔ 已下架 |
| **D**（本 RFC） | **app/web** | ✅ **自动** | **沿用 A 的产物契约** | 🚧 本方向 |

- **D 不复活 B**：B 的代码不整体复用（其卡片平铺结构、复习/编辑/候选链路均不复用）；**D 复用 A 的操作规程**——`ai-engineering/skills/learn-digest.md` 就是 D 的实现蓝图（抓取路径、六段模板、`_raw/` 留痕、归并规则全部现成）。
- **B 里可能被复用的少量部件**（待 §四 决策点定）：读全文/列表端点、`LearnKnowledgeSource` 问答召回（「问上次整理的那篇说了什么」）。若决定复用，§9.4 删除清单须相应调整（**不是全删**）——该决策在 D 设计定稿前不阻塞 B 的删除批次。

### 3.3 核心原则

1. **抓取进服务端**——这是 B 的死因，**第一天就必须有**，否则重蹈覆辙。
2. **产物契约唯一**：沿用 A 的 `data/{userId}/learn/{type}/{topic}/` + `NN-{slug}.md` + `README.md` + `_raw/`（原图/原音频/原 PDF/原文全文/转写稿必留痕）；A 与 D 写同一份契约，不建第二套结构。
3. **入口显式，不做隐式分流**（learn 与会话边界判据，见技能文档触发条件）：说「整理这个」才进 learn；否则走会话记录，且进 learn 后不再另建记录。
4. **范围克制**：只做「喂入 → 抓取 → 结构化 → 落盘 → 回执 → 查看」；**明确不做**复习推送/复习流转/卡片编辑/交易候选反哺（B 的失败教训）。
5. **无第三视角（B1）**：呈现是「我和阿呆」的自然对话，无系统标签。
6. **多用户按 `data/{userId}/`**（架构对齐 trading）。
7. **抓取失败 fail-visible**：保留原链接与已抓到的素材，人话提示可重试；**绝不落半成品**。

### 3.4 入口方案（**已拍板 2026-09-12**：② 为基线前提 + ① 为增强；③ 后置；④ 不做）

> **用户拍板**（2026-09-12）：「最完美的是两个入口，**独立页面是前提**，如果**集成到会话里就更好了**，理论上插件作用就是这样的；如果**直接分享给阿呆就更好，这个可以先不做**。」
> → **基线 = ② 独立页面**（必须先有：资产全景浏览 + 页内喂入的主入口）；**增强 = ① 对话流集成**（在 app/web 对话里说「整理这个」跑同一流水线，回结构化卡片）；**③ iOS 分享扩展后置**（先不做）；**④ 剪贴板识别不做**（隐式触发，与 §3.3 原则 3 冲突）。
> ⚠️ **连带影响**：② 需要「列表 + 读全文」后端支撑 → §四 决策点 5（是否复用 B 的读层端点）**建议改为复用**，B 删除批次相应调整为「删喂入/消化/复习/编辑/候选，留读层」。

| # | 方案 | 优势 | 代价 | 拍板 |
|:-:|:-----|:-----|:-----|:----:|
| ① | **对话流内触发**：app/web 对话里粘链接或发图 + 说「整理这个」→ 阿呆回结构化卡片；查看全文说「打开那篇」 | 最符合第一原则（无第三视角）；复用现有对话通道与流式/轮询能力 | 长文阅读体验弱于专页；多篇资产全景浏览不佳 | ✅ **增强（更好）** |
| ② | **独立页面**（B 的资产页形态）：导航「学习」→ 目录树 + 全文渲染，页内喂入 | 长文/多篇浏览体验最好；资产全景 | 新页面 + 门控 + 双端工作量 | ✅ **基线（前提）** |
| ③ | **iOS 分享扩展**：在 B站 App 内「分享 → 阿呆」直达 | 手机端最顺（看到即丢） | iOS 工程量大（Share Extension + 免费签名 7 天限制） | ⏸ **后置（先不做）** |
| ④ | **剪贴板/截图识别**：复制链接后打开阿呆自动识别 | 少一步操作 | **隐式触发**，与原则 3 冲突；易误判为记录 | ❌ 不做 |

> 阶段划分对应：**阶段 1 = ② 独立页面 + 服务端抓取**；**阶段 2 = ① 对话流集成**（同一流水线，加一层入口）。

### 3.5 服务端抓取能力（本次核心新建）

| 源 | 服务端路径 | 障碍与对策 |
|:---|:-----------|:-----------|
| **B站视频** | 元数据 `api.bilibili.com/x/web-interface/view?bvid=` + 字幕接口（按 cid 取字幕列表/内容） | 部分视频无字幕 → 走转写；接口可能限流 → 退避重试 |
| **文章 URL** | curl 抓 HTML → 去 script/style/nav 转纯文本 | 反爬/Cloudflare 403 → Web Archive 兜底；仍失败 → 请用户粘正文 |
| **图片** | 复用现有图片上传通道 + VLM/OCR（项目已用 GLM 视觉） | 无 |
| **音频** | ffmpeg 转 16k wav → **云端转写 fun-asr**（2026-09-12 拍板：实测**基本视频都没有字幕**，转写是必经路径，不设"仅支持有字幕视频"的降级）| 费用与可控策略见 §3.8；**服务器 2核4G 不建议本地跑 whisper**（37min 音频会打满 CPU） |
| **YouTube** | 需 yt-dlp/第三方 | ⚠️ **生产服务器在北京腾讯云**，直连 YouTube 大概率不可达，需代理——**首期建议不做或明确评估** |
| **社交平台**（公众号/知乎/小红书/X）| 反爬与登录墙多 | **首期不做自动抓取**：引导用户粘正文或截图（走图片源），不强行绕过 |

**B8 授权边界（须定义）**：抓取域名白名单（仅内容页，不含登录态接口）｜单用户配额（如每日 N 次抓取 / 转写分钟数上限）｜超限人话提示｜不绕过付费墙与登录墙｜版权边界沿用 A（个人消化留存，不公开传播、不对外分发）。

### 3.6 处理流水线（下沉 A 的 9 步，服务端版）

```
① 收（对话流） 链接/图/文本 + 「整理这个」→ 提交式受理，立即返回 status（对齐复盘 submitReview、learn V1 digest/status 先例）
② 判源类型   视频/文章/图片/音频/文本 → type（ai|trading|other）
③ 抓         服务端抓元数据 + 字幕/正文（§3.5）；无字幕 → 转写（受配额/预授权约束）
④ 质控       术语误差修正、关键数字核对、存疑标注
⑤ 结构化     A 的六段模板（基本信息/核心观点/关键内容详解/金句/与主题概念关系/我的疑问）
⑥ 落盘       data/{userId}/learn/{type}/{topic}/ + README.md + _raw/（源必留痕）
⑦ 回执       对话流回结构化卡片（无第三视角）；失败 → 人话 + 可重试 + 素材不丢
⑧ 查看       「打开那篇」读全文；「问上次整理的那篇」→ 问答召回（若复用 §3.2 部件）
⑨ 概念追踪   （后置，非首期）时效性内容查最新进展
```

**异步与轮询**：抓取 + LLM 结构化 + 转写都是分钟级 → 提交式受理 + 状态轮询（已有两处现成模式可抄）。

### 3.7 端点草案（轮廓，实施时定稿）

| 端点 | 说明 |
|:-----|:-----|
| `POST /api/v1/learn/digest` | 提交式受理：`{url \| content \| imageIds, type?, note?}` → `{status: pending\|running}`；同用户 inflight 去重（连点只烧一次 AI）|
| `GET /api/v1/learn/digest/status` | 轮询：`idle / running / done{type,topic,title} / failed{message}` |
| `GET /api/v1/learn/content?path=` | 读全文（「打开那篇」用）|
| `GET /api/v1/learn/topics` | 主题列表（若方案②独立页面则需要；方案①可不要）|

> 全部需**登录态**（AuthFilter 已覆盖）；插件门控是否需要——**待定**（B 曾用 learn 插件门控，D 若走对话流可考虑不另设插件开关，减少一层门控）。

### 3.8 转写费用控制（2026-09-12 拍板：对接必然，费用须可控）

**实据**（2026-09-12 核实）：

| 项 | 数据 | 来源 |
|:---|:-----|:-----|
| 阿里云语音识别（Paraformer，同族模型）单价 | **0.00008 元/秒 ≈ 0.288 元/小时** | [阿里云 ISI 计量计费](https://help.aliyun.com/zh/isi/developer-reference/metering-and-billing) |
| 免费额度 | **每主账号每月 36,000 秒（10 小时）**，每月 1 日 0 点重置 | 同上 |
| 计费口径 | **仅对语音内容时长计费**（静音不计费）→ 实际低于音频总时长 | 同上 |
| fun-asr 实测 | 2026-09-06 首例 37:24 视频转写**实付 0 元**（免费额度内）；技能文档记录单次上限约 0.5 元 | 本项目首例实践 |
| fun-asr 精确单价 | 以百炼控制台账单为准（页面需登录，本次未能核验）| — |

**量级估算**（按真实使用频率）：

| 使用强度 | 月音频量 | 月费用 | 年费用 |
|:---------|:---------|:-------|:-------|
| 每月 10 个视频（30min/个）| 5 小时 | **0 元**（免费额度内）| **0 元** |
| 每月 30 个视频 | 15 小时 | 超 5 小时 ≈ **1.4 元** | ≈ **17 元** |
| 每天 1 个视频（极端，不太可能）| 182 小时 | 超 172 小时 ≈ **50 元** | ≈ **600 元** |

> **结论**：按正常使用强度，**年成本在 0 ~ 几十元量级**，不是需要担心的支出；真正要防的是「**不可预测**」而非「贵」。

**费用可控六条（实施时必须落地）**：

1. **字幕优先（免费）**：抓取时**先试 B站字幕接口，取到就不转写**——B站部分视频有 AI 字幕，命中一次白省一次（用户反馈"基本没字幕"，故这是节省项而非依赖项）。
2. **同一素材只转写一次**：转写稿落 `_raw/` 永久留存 → 重复整理同一视频**零费用**（「源必留痕」的附带收益）。
3. **只在你明确发话时花钱**：显式触发，**绝不批量/后台自动转写**——费用随你的意图走，不被定时任务烧掉。
4. **月度硬闸 + 记账**：设月度转写配额（建议先按免费额度 10 小时/月，或更低）；接近上限**提示而非默默花钱**；累计费用可查（复用 `guard-cost.sh` 思路或产品内记账）。
5. **单次可预期**：抓到无字幕视频时，先回一条「该视频 37 分钟，需转写，预计约 0.2 元（本月剩余免费额度 X 小时）」→ 你确认后再转写（异步流程中的前置提示，满足 B8「先经人确认」）。
6. **备选更便宜通道**（留口子不首期实现）：硅基流动 SenseVoiceSmall（国内直连、注册送额度、部分模型免费，[SmartSub 配置文档](https://raw.githubusercontent.com/buxuku/SmartSub/main/docs/docs/guides/cloud-asr/siliconflow.md)）可作 fun-asr 平替/兜底，仅在费用超预期时启用。

## 四、决策点（需用户拍板）

| # | 决策 | 拍板结果（2026-09-12）| 说明 |
|:-:|:-----|:----------------------|:-----|
| 1 | **入口形态** | ✅ **② 独立页面为基线前提 + ① 对话流集成为增强**；③ iOS 分享扩展**后置**；④ 剪贴板识别**不做** | 用户原话「两个入口，独立页面是前提，集成到会话里更好，分享给阿呆先不做」；阶段 1 落地 ②，阶段 2 加 ① |

### 10.3 偏离 RFC 的一处（重要，请知悉）

RFC §3.3 原则 2 要求**产物契约唯一**（A 的 `{type}/{topic}/NN-{slug}.md` + README + `_raw/`），本批**未做契约迁移**，新卡仍落既有 `{type}/{yyyy-MM-dd}_{title}.md`。理由：
1. 契约迁移会改写已部署的读路径（列表/单篇/编辑/流转全部按 `type+title` 定位），而 **RFC 20260829 §九 的 B 下架批次尚未决断**——先迁移等于对可能被删的代码做一次大改造，属双重风险；

### 11.2 关键设计取舍（可回溯）

- **归属判定用 `origin: product` + 路径形态，而不是「路径算得对不对」**：同一个主题目录里可能同时有技能卡与产品卡，靠路径无法区分；用 frontmatter 标记 + 老式扁平路径两条判据，既让别处整理的卡**只读**（不注入产品模板段），又让老产品卡**原地可写**（不强制搬家）。
- **主题由文件所在目录决定，frontmatter 的 `topic` 只是同步显示**：位置是真相，避免「frontmatter 说 A、文件在 B」的错乱（`update` 也据此强制对齐）。
- **README 只追加不重写**：主题 README 是用户资产（技能侧手写目录），产品只在末尾追加带标记的自动段。
- **重名不删不加戏**：本产品同名仍 400（防改错卡），别处同名不再拦（两者是不同文件），命中多张时按「本产品优先」消解。
- **图片走「忠实提取」而不是「直接结构化」**：图 → 文本（可留痕、可复用）→ 文本模型结构化，与链接/文章共用一条下游，OCR 与摘要职责分离。
