# AI 工程层：从「文档子目录」到「一等公民」

> **方向 RFC（已批准）**：把阿呆的 AI 协作体系从 `docs/ai/`（代码工程的附属文档）提升为与代码工程并列的 **AI 工程层**——资产 + 工作流 + 状态三层结构，补齐缺失资产（ADR/已知坑/边界/代码规范），闭合工作流（讨论→方案→开发→审核→验收）。本草案只定形态与边界，不动代码。

---

## 〇、一句话定位

**代码工程是结果集，AI 工程是驱动层。** 本 RFC 把阿呆已有的零散成果（AGENTS.md / docs/ai/ / guard-meta）提升为一个有传统、可继承、可校验的工程层。

## 一、背景：为什么需要

### 1.1 现状盘点（都有实测证据）

| 资产 | 现状 | 缺口 |
|:-----|:-----|:-----|
| 入口 | `AGENTS.md` + `docs/ai/README.md` | ✅ 已工具无关化 |
| 审查体系 | 8 官 roles + audit/review 流程 + 9 个 checklists | ✅ 完整 |
| 收尾闭环 | `process/ship.md`（guard-meta 门禁）| ✅ 已接入 |
| 元治理 | `guard-meta.sh`（图谱/lines/孤儿 + `--fix`）| ✅ 完整 |
| 目录治理 | 全 docs/ 子目录 `_index.md` | ✅ 完整 |
| **决策记录** | RFC 有 27 篇，但**无 ADR 归集**；RFC 历史决策散落各处，无「为什么这么定」的索引 | ⚠️ **缺** |
| **已知坑** | 坑散在 checklists「上次发现」列 + REVIEW 历史 + change-log | ⚠️ **缺独立成体系** |
| **边界** | 散在 VISION §6 + 各 RFC「不做什么」+ 代码分层规则 | ⚠️ **缺集中声明** |
| **讨论→方案** | 无登记机制（RFC 20260815 已列 D4 待办）| ⚠️ **空** |
| **跨项目复用** | 方法论散在仓库内，无独立承载 | ⚠️ **缺** |

### 1.2 根本问题

每次 agent 会话都是**全新上下文**——它不记得上次，只能靠文本继承历史。当前体系能回答「现在怎么做」（流程/清单），但回答不了：
- **为什么这么定**（ADR）
- **别踩什么**（已知坑）
- **边界在哪**（不做什么）
- **哪些讨论值得沉淀**（决策过滤器）

这些恰好是 AI 理解「项目效果历史」的唯一通道。

## 二、核心模型：意图层 vs 投影层（不是分层，是循环）

```
意图/决策（AI 工程）  ←→  投影/现状（代码工程）
   资产：规范/ADR/坑/边界        代码 = 意图的投影
   工作流：讨论→方案→开发→审核    现状 = 下一步决策的输入
   状态：完成度/测试数/未修项
```

- **不是谁在上谁在下**：互为输入输出（解释学循环）
- **与阿呆自身架构同构**：Record（源真相）↔ Timeline（投影，反哺下一步）——AI 工程↔代码工程 就是同一模式的系统级复现

## 三、目标结构：三层模型

| 层 | 内容 | 现状 | 本次动作 |
|:---|:-----|:-----|:---------|
| **资产**（静态知识）| 规范 / 边界 / ADR / 已知坑 / 架构 | 散落 | **补齐 + 归集** |
| **工作流**（过程定义）| 讨论→方案→开发→审核→验收 | 只到审核/收尾 | **补讨论→方案段** |
| **状态**（动态真相）| status.md / REVIEW.md / change-log | 已有 | **命名归位**（明确属于 AI 工程）|

## 四、具体形态（草案）

### 4.1 位置：仓库内一等公民

```
ai-engineering/            ← 新顶层目录（与 services/ apps/ os/ 平级）
  _index.md                目录治理（沿用 guard-meta）
  README.md                AI 工程入口（承接 AGENTS.md 指向）
  assets/
    adr/                   决策记录索引（ADR-001 起，链接 RFC/会话）
    pitfalls.md            已知坑（从 checklists「上次发现」归集，按域分组）
    boundaries.md          边界声明（不做什么：原则级 + 功能级）
    conventions.md         代码规范（分层/命名/提交/文档规则归集）
  workflow/
    discuss.md             讨论登记（想法→ideas/ 或 RFC 前身）
    design.md              方案（RFC 骨架：问题→方案→决策点→验收）
    develop.md             开发（现状：直接改代码，保留）
    review.md              审核（现有 docs/ai/process/review.md 迁入）
    ship.md                收尾（现有 docs/ai/process/ship.md 迁入）
    audit.md               走查（现有 docs/ai/process/audit.md 迁入）
  state/
    status.md              测试数/端点数（现有 reference/status.md 指针化）
    REVIEW.md              未修项（现有 review/REVIEW.md 指针化）
    change-log.md          批次历史（现有 reference/change-log.md 指针化）
```

### 4.2 迁移原则：指针化，不搬内容

- 现有 docs/ai/ 内容**物理不动**，`ai-engineering/` 作为**统一入口层**，内部用指针指向现有文件
- 避免 3 天前的教训：文档搬迁 → 断链 → guard-meta 报错（D10/D30）
- 或者：一次性物理迁移 + guard-meta 范围更新（二选一，见 §六决策点）

### 4.3 补齐资产（本次新增）

| 资产 | 形态 | 来源 |
|:-----|:-----|:-----|
| `adr/` | ADR-001 起，每篇：决策 / 背景 / 备选 / 结论 / 代价；链接对应 RFC | 从 27 篇 RFC 关键决策提炼（首批 5-10 条）+ 新决策即时登记 |
| `pitfalls.md` | 按域分组（存储/并发/AI 集成/前端状态/门控），每条：症状/根因/修复/复发信号 | 从 checklists「上次发现」列归集（B/K/F 系列约 30+ 条）|
| `boundaries.md` | 原则级（第一原则「无第三视角」/File First/不提前微服务化）+ 功能级（不做什么）| VISION §6 + 各 RFC「不做什么」归集 |
| `conventions.md` | 分层规则/命名/异常/注入方式/提交规范 | 根 CLAUDE.md 代码约定归集 + docs/ai 文档约定 |

### 4.4 工作流闭环（补讨论→方案段）

```
讨论 discuss → 方案 design（RFC）→ 开发 develop → 审核 review/audit → 验收 ship
   │              │                                        │
   ▼              ▼                                        ▼
 ideas/ 登记   决策入 ADR（验收时）                      guard-meta 门禁
```

- **discuss.md**：讨论登记过滤器（什么值得沉淀/什么是一次性对话；想法入 `docs/ideas/`）
- **design.md**：RFC 骨架标准化（问题→方案→决策点→验收标准）
- **决策沉淀规则**：方案通过 → 关键决策入 `adr/`；踩坑修复 → 入 `pitfalls.md`；验收 → 更新 state

### 4.5 跨项目分层（关键边界）

| 层 | 内容 | 可跨项目？ |
|:---|:-----|:----------|
| **方法论**（如何建 AI 工程）| 三层模型 / 资产模板 / 工作流骨架 / 过滤器 | ✅ 是（仓库外 `ai-engineering-method/` 或 ai-context-research/ 同级）|
| **工程实例**（阿呆的 AI 工程）| ADR / 坑 / 边界 / 规范 / 状态 | ❌ 否（项目土壤里长出来的，不可搬运）|
| **代码工程**（services/ apps/）| 结果集 | ❌ 否 |

**真正该跨项目的不是「AI 工程本身」，是「如何建 AI 工程」。**

## 六、决策（2026-08-15 已定稿）

| # | 决策 | 结论 |
|:-:|:-----|:-----|
| 1 | 形态 | 仓库内 `ai-engineering/` 顶层目录（一等公民）|
| 2 | 迁移方式 | **物理迁移**（docs/ai/ → ai-engineering/，guard-meta 范围更新，单一事实源）|
| 3 | ADR 与 RFC 关系 | ADR = RFC 的**决策索引**（ADR 链接 RFC，不重复内容）|
| 4 | 跨项目方法论 | **同步立**——阿呆既是想法实现，也是 AI 开发体系研究实践场；目标可落地、可复制 |
| 5 | 沉淀过滤器 | **由 AI 主动发现**（开发/审核中识别值得沉淀的决策与坑，提请入 ADR/pitfalls，人确认）|

**人向命名原则**：AI 工程层内「给人看」的文档命名 **README.md**（工具无关），不沿用 CLAUDE.md（工具绑定）；AI 执行入口维持 AGENTS.md。

## 七、风险与对策

| 风险 | 对策 |
|:-----|:-----|
| AI 工程资产膨胀 → 自身成维护负担 | 沉淀过滤器 + guard-meta 校验 + `_index.md` 过期判断 |
| 物理迁移断链 | 迁移当批即跑 guard-meta（M1 断链检测兜底）|
| 双读者问题（人/AI）| 保持 AGENTS.md（AI）/CLAUDE.md（人）分离，不合并 |
| 资产与代码漂移 | pitfalls/conventions 由 ship 门禁强制「修复即沉淀」|

## 八、验收标准（总）

1. `ai-engineering/` 存在且 guard-meta 覆盖，PASS
2. 工作流六段（讨论→方案→开发→审核→验收）都有定义文件，无空段
3. `pitfalls.md` 覆盖 checklists 全部「上次发现」；`adr/` 首批 5-10 条
4. 跨项目方法论边界明确（哪些可跨/哪些不跨）
5. 任一功能从「想法」到「验收」可循完整工作流，且有决策痕迹（ADR/坑）
