## 二、瓶颈分析

### 瓶颈 1：表象诊断 vs 根本诊断

典型案例 — **#7 AI 称呼问题**：

```
第1步：发现 AI 叫"阿呆" → 想到"name 在 profile 里" → 改名"小王"
第2步：AI 开始叫"小王" → 想到"prompt 里有 name" → 调整系统提示词
第3步：用户说"不要叫名字，直接回答问题" → 才意识到要"删除 context 中的称呼"
```

三步才到根因。每一步都在正确方向上前进，但每一步都只解了当前层的问题，没继续往下挖。

### 瓶颈 2：跨模块连锁效应

典型案例 — **#8 删除问题**：

```
RecordController.deleteRecord()
  → 只删了 RecordFileRepository（假设 ID=rec_xxx 只在 records/ 目录）
  → 但 endConversation 流程把文件保存到 cards/ 目录
  → 导致删不完
```

单个文件的"存储在哪里"取决于上游流程（endConversation），删除时没考虑到所有写入路径。本质是对**数据流的全链路**没有完整认知。

### 瓶颈 3：修改前没跑完整场景

典型案例 — **#9 分页数据丢失**：

```
FeedAppService 分页实现：
  → page 0 = subList(0, 5) → 最早 5 条
  → ListView(reverse: true) + cards.reversed → 最早 5 条在视觉底部
  → totalToday > 5 时，最新记录不可见

谁的问题？ 代码逻辑本身一致，但和 UI 需求不匹配。
```

这个在代码层面"没错"——page 0 返回 subList(0, 5) 合逻辑。但放在 reverse ListView 的上下文中就错了。**代码正确不代表场景正确。**

### 瓶颈 4：沟通中的"我以为"

| 我说了什么 | 用户理解了什么 | 实际想要什么 |
|:-----------|:---------------|:-------------|
| "分页 page/size 实现好了" | page 0 应该看到最新内容 | 对，因为 reverse ListView |
| "删了 Collections.reverse()" | 排序恢复原样 | 原样=升序+reverse→最新在底部 |
| "分页方向修复" | page 0 = 最新 | 对，但要确认不改变排序 |

## 三、本质问题归类

### 3.1 工作流层面

| 问题 | 建议 |
|:-----|:------|
| 修 Bug 时只改表面层，不追数据流全链路 | 修改前先画数据流：数据从哪来→经过哪些转换→最终落在哪 |
| 没有完整的"验收场景"清单 | 改之前写 2-3 条验收标准（Given/When/Then），改完逐条验证 |
| 没有区分"修复"和"优化" | 修复只做最小改动，优化单独立项。混在一起两边都没做好 |

### 3.2 技术层面

| 问题 | 建议 |
|:-----|:------|
| 测试覆盖了"代码逻辑"但没覆盖"场景" | 测试不仅要测接口返回什么，还要测"用户看到什么" |
| 分页/排序/过滤的交互测试缺失 | widget test 覆盖 ListView 的渲染顺序（对 Flutter 较难，优先后端场景测试） |
| 跨模块数据流没有明确的文档 | 每个 Repository 写入方法注明"这个文件的消费者是谁" |

### 3.3 沟通层面

| 问题 | 建议 |
|:-----|:------|
| 用技术术语回答产品问题 | 用户在说"排序不对"时，我问的是"升序还是降序"，而不是问"你看到的视觉效果是什么" |
| 过早进入解决方案 | 用户说"数据丢失"时我直接进了分页代码，没先问"你说的丢失是指完全空白还是少了一条" |
| 没有确认"什么算做完" | 改完说"好了" → 用户测了才发现不对。应该在改之前对齐验收标准 |

## 四、改进建议

### 对 AI 的建议（也是对我自己的反思）

1. **改 Bug 前三问：**
   - 这个 Bug 的**表象**是什么 → 我理解了
   - 这个 Bug 的**根因**可能有多深 → 我挖到了第几层
   - 这个修改**影响哪些模块** → 我检查了数据全链路

2. **每次修改前写验收条件：**
   ```markdown
   场景：用户有 6 条今日记录，新增 1 条后刷新页面
   预期：第 7 条出现在 feed 底部（默认可见区域）
   不验证：数据结构没变、排序没变
   ```

3. **不急着说"已修复"：**
   - 代码改完 → 跑测试 → 模拟场景 → 再确认

### 对工作流的建议

1. **Bug 修复流程优化：**
   ```
   报告 → 确认现象 → 追根因 → 写验收条件 → 修改 → 
   验证（场景+测试）→ 文档同步 → 提交
   ```
   禁止跳过"追根因"和"写验收条件"。

2. **区分迭代类型：**
   - 🔧 **Bug Fix**：最小改动，改完确认
   - ✨ **Feature**：设计+实现+测试独立周期
   - 🧹 **Refactor**：不动功能只改结构，单独提交

3. **用户说话的优先级：**
   - "不修改排序" → 先确认排序的视觉表现是什么，再确认代码里的排序变量是什么
   - "数据丢失" → 先确认是"完全消失"还是"不可见"，再找原因

## 五、可行的具体措施

### 5.1 技术措施

1. **分页相关测试增强**
   - 测试 totalToday > pageSize 的场景，确认 page 0 包含最新条目
   - 测试 load more 的前端顺序

2. **删除流程文档化**
   - 在 RecordController.deleteRecord 注明：此方法同时清理 records/ 和 cards/ 两个仓库

3. **Feed 数据处理流程记录**
   - 前端 `_cards` 列表维护规则：何时 add、何时 addAll、何时 prepend

### 5.2 工作流措施

4. **提交前 Checklist：**
   - [ ] 跑通了现有测试
   - [ ] 验证了 2 个以上边界场景
   - [ ] 确认数据流全链路
   - [ ] 同步了 api-spec.md（如果 API 有变化）
   - [ ] 同步了 feature-reference.md（如果行为有变化）
   - [ ] 更新了 issue-log.md

5. **每个问题至少追根到第三层：**
   ```
   第1层：为什么代码错了？
   第2层：为什么测试没发现？
   第3层：为什么这个场景没被考虑到？
   ```

## 六、总结

近期的 Bug 反复不是"代码写得差"的问题，而是**工作节奏**的问题——修得太快、想得太浅、确认得太少。

好消息是：**所有 Bug 最终都修到位了，没有遗留的副作用。** 这意味着方向是对的，只是过程可以更高效。

建议从下一次修改开始实践"改前写验收条件、改后跑场景验证"这个最小习惯。能在不改动工作流的前提下，把返工率降下来。
