# AI Native Context Structure

版本：v1.0

------------------------------------------------------------------------

# 1. 文档目的

AI Native Context Structure 定义 AI 原生软件项目中的上下文体系。

它解决的问题：

> AI 应该如何理解一个软件项目？

在传统软件开发中，项目知识主要依赖：

-   开发人员经验
-   代码结构
-   文档记录
-   历史沟通

但是 AI 参与研发后，仅依靠代码无法让 AI 获得完整项目认知。

因此，需要建立一套结构化 Context 体系，使 AI 能够：

-   理解项目目标
-   理解系统架构
-   理解设计约束
-   理解历史决策
-   理解当前工作状态

------------------------------------------------------------------------

# 2. Context 的定义

Context 是 AI 在执行任务时需要了解的信息集合。

它不是简单的文档。

它包含：

    项目知识

    +

    工程规则

    +

    历史决策

    +

    当前状态

    +

    运行信息

Context 的目标：

> 将隐含在开发者脑中的知识，转化为 AI 可读取、可维护的软件资产。

------------------------------------------------------------------------

# 3. Context 分层模型

AI Context 可以分为五个层次：

                    Project Context


                         |

            +------------+------------+

                         |

                  Identity Context

                  项目认知


                         |

                  Architecture Context

                  系统结构


                         |

                  Decision Context

                  历史决策


                         |

                  Execution Context

                  当前状态


                         |

                  Runtime Context

                  运行信息

------------------------------------------------------------------------

# 4. Context 类型

## 4.1 Identity Context

定义项目是什么。

包含：

-   项目目标
-   产品定位
-   核心能力
-   用户对象
-   边界范围

示例：

``` text
README.md

vision.md

scope.md
```

作用：

帮助 AI 理解：

> 这个项目为什么存在。

------------------------------------------------------------------------

# 4.2 Architecture Context

定义系统如何构建。

包含：

-   系统架构
-   模块关系
-   技术选型
-   数据流
-   外部依赖

示例：

``` text
architecture.md

modules/

dependencies.md
```

作用：

帮助 AI 理解：

> 系统如何工作。

------------------------------------------------------------------------

# 4.3 Convention Context

定义工程规则。

包含：

-   编码规范
-   命名规则
-   目录规范
-   提交规范
-   测试要求

示例：

``` text
conventions.md
```

作用：

帮助 AI 理解：

> 应该如何修改代码。

------------------------------------------------------------------------

# 4.4 Decision Context

记录重要工程决策。

包含：

-   为什么选择某方案
-   为什么拒绝某方案
-   技术取舍
-   历史原因

示例：

``` text
decisions.md

adr/
```

作用：

避免 AI 重复讨论已经确定的问题。

------------------------------------------------------------------------

# 4.5 Execution Context

描述当前项目状态。

包含：

-   当前目标
-   当前任务
-   进行中的修改
-   已知问题

示例：

``` text
workspace/

current.md

tasks/
```

作用：

帮助 AI 理解：

> 当前正在发生什么。

------------------------------------------------------------------------

# 5. 推荐目录结构

`.ai/` 可以作为一种默认约定。

示例：

``` text
.ai/

├── README.md

├── vision.md

├── architecture.md

├── conventions.md

├── decisions.md

├── dependencies.md

├── modules/

│   ├── module-a.md

│   └── module-b.md

│

├── workspace/

│   ├── current.md

│   └── tasks/

│

└── knowledge/

    ├── lessons.md

    └── known-issues.md
```

说明：

`.ai/` 并不是强制要求。

它代表：

> AI Context 的统一存储位置。

团队可以根据实际情况调整。

------------------------------------------------------------------------

# 6. Context 生命周期

Context 不是静态文件。

它应该随着项目演进。

生命周期：

    Created

    ↓

    Active

    ↓

    Reviewed

    ↓

    Updated

    ↓

    Archived

------------------------------------------------------------------------

## Created

新知识产生。

例如：

-   新架构设计
-   新技术选型
-   新模块建立

------------------------------------------------------------------------

## Active

正在影响项目。

例如：

-   当前架构规则
-   当前开发规范

------------------------------------------------------------------------

## Reviewed

定期检查有效性。

确认：

-   是否仍然正确
-   是否需要更新

------------------------------------------------------------------------

## Updated

项目变化后同步修改。

例如：

代码结构变化：

↓

更新 architecture.md

------------------------------------------------------------------------

## Archived

历史信息保留。

避免：

-   删除历史经验
-   重复踩坑

------------------------------------------------------------------------

# 7. Context 更新原则

## 7.1 重要变化必须同步 Context

以下变化应该更新 Context：

-   架构调整
-   技术替换
-   模块新增
-   重要问题解决
-   工程规则变化

------------------------------------------------------------------------

## 7.2 不记录所有信息

Context 不是日志。

应该记录：

有长期价值的信息。

例如：

应该记录：

    为什么选择某数据库

不应该记录：

    今天修改了三个文件

------------------------------------------------------------------------

## 7.3 保持结构化

AI 更容易理解：

明确结构：

    问题

    背景

    决策

    影响

而不是：

长篇描述。

------------------------------------------------------------------------

# 8. AI 使用 Context 的原则

AI 执行任务时：

推荐流程：

    加载相关 Context

    ↓

    理解项目约束

    ↓

    分析任务影响

    ↓

    制定方案

    ↓

    执行修改

    ↓

    检查 Context 是否需要更新

------------------------------------------------------------------------

# 9. Context 与代码关系

代码：

描述：

> 系统现在是什么。

Context：

描述：

> 为什么是这样。

两者关系：

    Code

    ↓

    Implementation


    Context

    ↓

    Reasoning

优秀 AI Native 项目：

代码和 Context 应该保持同步。

------------------------------------------------------------------------

# 10. 常见错误

## 10.1 只维护代码，不维护 Context

结果：

AI 只能猜测。

------------------------------------------------------------------------

## 10.2 Context 变成大量文档堆积

结果：

AI 无法找到重点。

------------------------------------------------------------------------

## 10.3 记录事实，不记录原因

例如：

错误：

    使用技术 A

正确：

    选择技术 A

    原因：

    解决问题 X

    限制：

    不适合场景 Y

------------------------------------------------------------------------

# 11. 总结

AI Context Structure 的目标：

不是创建更多文档。

而是：

> 将软件项目中的隐性知识转化为 AI 可以理解的软件资产。

AI Native 项目的基础：

不是更多代码。

而是：

    代码

    +

    上下文

    +

    知识积累

Context 是 AI 进入软件工程世界的入口。
