# 外部 2.0 规划汲取

> **来源**：ChatGPT 产出的《阿呆阿呆 2.0 规划 v0.1》（561 行，用户 2026-09-19 提供）。它依据的是项目同日的 `20260919-external-briefing-for-ai.md`（外发事实底稿），**不知道**项目内部已形成的若干结论（09-16 插件/冷启动讨论、09-17 接线盘点、09-18~19 交易结构重排）。
>
> **性质**：汲取件（只讨论、不实施，遵守 AGENTS.md 规则 7）。判定分三类——**采纳 / 已覆盖 / 不采纳或需改写**——另列它未覆盖、但必须先补的三个空洞。
>
> **一句话判定**：它替项目说清了「阿呆是什么」，但没说「阿呆明天做什么」；唯一比项目内部想得更深的一句是「聊天不是存在的理由，而是理解能力的出口」。

---

## 一、采纳（3 条）

### A1 · 聊天是「理解能力的验证器」，不是阿呆存在的理由

- **原文**（§八）：聊天不是核心产品形态，而是"阿呆理解能力的验证器"；"用户并不一定愿意每天打开阿呆聊天"。
- **为什么采纳**：它指出的是**度量口径错位**，不是功能问题。项目当前把 C0（每日对话卡片数）当作第一优先级指标，而 09-11~09-15 连续 5 天为 0；把"提升心跳"设为目标，会把产品推向"陪聊"，而"AI 陪伴"已在已否决清单里。内部此前的推理是"心跳 0 → 主动价值没成立 → 要提升心跳"，本件接受它的反向判断：**心跳不该是目标**。
- **采纳时必须补**：替代指标（否则 C0 悬空）。候选（待拍板，不预选）：① 主动送达被响应的次数（提醒/推送 → 用户是否产生行动）；② 用户对"阿呆对你的了解"的确认/否认次数；③ 非缺陷驱动的打开次数。
- **落点**：纯口径问题，不涉代码；若改判读方式，动的是 `ai-engineering/guard-context.sh` 的 C0 段（AI 工程层，可直接修订）。

### A2 · 插件是阿呆伸向现实世界的「手」，插件不定义阿呆

- **原文**（§一/§四）："插件负责把世界带进来，阿呆负责理解这个人"；"插件越多，不意味着阿呆越有价值"。
- **为什么采纳**：与项目 2026-09-17 的实践同向——撤 `project` 插件、待办收归 Kernel builtin，插件只剩 trading/learn。内部尺子（**通用 → 内核 builtin；垂直 → 插件**）比它更可操作，二者合并即可。
- **采纳时必须补**：它与 `framework-plus-plugin-model.md`（形态总纲）是"覆盖"还是"叠加"，必须先拍板（见 §五）。
- **落点**：总纲的表述层可吸收"插件不定义阿呆"这一句；`life` 的定位随之必须明确。

### A3 · 「个性化消化」是真正的差异点

- **原文**（§五）：重点不是"能不能解析一个视频"，而是"能不能结合对用户的了解，把外部内容转化成这个用户更容易消化的内容"；"不是内容摘要器，而是个人化内容消化器"。
- **为什么采纳**：这与项目内部最深的一条判断同源——`20260916-...` §七 的**表征适配 / 编码-解码错配**（"老师不能为一个人重讲一遍，阿呆可以"）。它独立推到同一结论，属交叉验证。
- **采纳时必须用内部更可执行的版本替换它的空表述**：
  - ❌ 不给用户写 prompt 的输入框（那是把最费力的一步留给用户，learn B 形态的死因）；
  - ✅ **调优 = 反馈沉淀**：评价写进 preference（已有 `POST /learn/cards/feedback` → `Memory.fromFeedback`），下次生成自动带上；
  - ✅ **不问用户"你喜欢什么方式"**（自我报告可靠性低），从行为推断 + 偶尔试探；
  - ✅ **顺序：先接表征的线，再上精美的皮**（"漂亮的无效"是最容易犯的错）。
- **采纳时必须补成本约束**：越个性化 = 越多页 = 越多 token；唯一解法是**精美/页序列一次性生成后只渲染**（既有形态：md 的 `## 卡片页` 段 + `POST /learn/cards/repages`）。

## 三、不采纳 / 需改写（3 条）

### R1 · 「让阿呆在用户不主动聊天时持续吸收、理解、沉淀」——需改写

**改写为**：吸收与沉淀是手段，**送达才是产品**。

理由：该表述的整条链（接收→理解→关联→消化→记忆→资产→观察→未来再被利用）全程被动；架构图里虽有 `OBSERVE → ACTION`，正文却**没有一句说明观察结果如何回到用户**。结果是"用户不来、它也不找"——而项目数据已证明这条路的天花板：连续 5 天 0 张卡。
**这是本件对规划最重的一条改写。**

### R2 · 「个人资产」被当成待建概念——需改写

**改写为**：资产多数已在跑，真问题是**出口**。

理由：`topic`、`evolvedTo`、`superseded`、`sentiment`、`lastConfirmed` 均已实现超过一个月，但用户侧零/弱出口（09-17 接线盘点 D 类 4 条，含"衰减在跑、用户不知道记忆在变淡"）。规划列出的八种"才成为资产"的东西里，多数**已经有字段和机制**。按它执行会把"建资产"当任务，而真实任务是"**把已有的资产讲给用户听**"。

### R3 · trading 被降级为「数据源」——需恢复对等地位

**改写为**：trading 当前的主动战场是**账本身可不可信**（对账/锚定/券商口径/丢行可见/两条铁律），不只是"贡献行为、规则、偏好"。规划把项目最花时间、也最影响信任的部分当成了已完成的输入。

### R4 · 三阶段划分是时间顺序，不是依赖顺序

**改写为**：每个阶段必须给出**可检验判据**（项目既有传统：验收锚点 + 铁律式约束）。例如 Phase 2 的验证问题"更愿意看、更容易理解、更容易记住吗"是好问题，但没有判据就无法验收。

## 四、规划未覆盖、必须先补的三个空洞

### 空洞 1 · 零数据第一步（新用户第一分钟做什么）

规划提出的验证题是"新用户把真实个人数据交给阿呆，能不能立刻感到被认识"，但**没有给出第一分钟的具体动作**。项目已核实：新用户插件默认全关、不能自助开，而 trading（要几个月流水）与 learn（要一次分享）都是存量型需求。

**内部已有方向**（`20260916-...` §五）：**托付 → 履约 → 信任**——"明天下午三点提醒我给妈打电话"，第二天真的响。技术上只差一环：**用户显式指定的时间 → per-user 定时提醒**（推送渠道/调度/AI 时间解析/`actionable`/`doneAt` 全部已就位，接线盘点 C 类）。

### 空洞 2 · 主动送达（观察结果如何回到用户）

这是规划的 `OBSERVE` 段缺失的落点，同时也是 §三-R2「资产出口」的同一个答案：**到期提醒、演变链回述（"我以前认为 X，后来改成 Y"）、确认动作日常化**。补上它，A1 的替代指标才有来源。

### 空洞 3 · 成功指标（放弃心跳之后用什么衡量"它懂我"）

A1 采纳后 C0 会悬空。必须先定"用什么替代"，否则指标真空会让下一次讨论重新滑回"提升对话数"。

> 附带（属工程层、非 2.0 范畴，但会限制 2.0 成立）：**ContextEngine 无预算与淘汰**——`kernel/context` 的 `policy`/`prompt`/`token` 三子包是空占位，`estimateTokens()` 只进日志；记忆已 3124 行/月。数据继续增长时，"理解"会**静默变差**而不是变好。

## 五、与形态总纲的关系（待拍板，进 `docs/` 的前置）

项目现有两份上游文档：`docs/architecture/product-roadmap.md`（唯一蓝图）与 `docs/architecture/framework-plus-plugin-model.md`（形态总纲）。本规划必须先回答它属于哪一种：

| 选项 | 含义 | 代价 |
|:--|:--|:--|
| **A 叠加** | 保留两份既有文档，把 2.0 的"Core 理解"作为第三份形态层加入 | 三份文档需划清边界，否则"阿呆是什么"出现三个答案 |

| **C 暂不进库** | 停在 ideas 区，等空洞 1-3 有答案后再升级为 RFC | 决策继续悬着，但不会污染真相源 |

## 六、一句话结论

**采纳它关于"阿呆是什么"的三条（聊天是验证器、插件是手、个性化消化是差异点），拒绝它关于"阿呆怎么活"的被动设定（吸收即价值），并把它回避的三个空洞补上——零数据第一步、主动送达、成功指标。补不上，2.0 就只是一个更精确的定义，而不是一个能跑的版本。**
