## 二、被推翻 / 被修正的作者声明（最有价值的部分）

1. **「清仓股丢行不再静默」→ 部分推翻（P1）**：后端确实上报（列数不足/非 6 位代码均带行号+原文+原因，`parsed.isEmpty()` 也带回明细），**但**
   ① **web 完全没消费**——`importSold()` 仍是 `Future<int>` 只取 `imported`，UI 仍 `_toast('清仓股导入 N 笔')`，正是本批声称要消灭的那句话；
   ② **整文件选错（表头认不出）全程静默**——`col == null` 分支把每行 continue 掉 → `imported=0, unparsed=0`，而另三条导入链（自选/资金/历史成交）在同类情形都是 fail-closed 400。
   ⇒ 本批交付物只在「服务端→JSON」这一跳成立，**用户可见面未变**。
2. **「int `unparsedRows` 保持兼容」→ 结论对、保障不成立（P1/P2）**：两数**恒等**（`unparsedRows()` 即 `unparsed.size()`，同一份 list）✓，
   但**契约零覆盖**——变异实测：把它改成数组 = 205 tests / 0 failed；把 sold+cash 两处透出整段删掉 = 同样 0 failed。
   「改类型会把 web 打挂」这句只对 web 成立（adai-app 内 grep 0 命中），而它**没有任何测试钉住**，属口头保障。
3. **「写路径不再落只读卡」（learn23）→ 部分推翻**：新 `locateWritable` 逻辑正确、8 组变异中「退回读定位」= 8 红（说明新定位确实承重）✓，
   **但修复前也没有任何写路径真的会写进只读卡**——把实现整段还原成批次前版本，相关 75 个测试只红 3 条且**全是文案断言**，
   「只读卡文件一字未动」这类核心断言全绿。⇒ 本批是**防御性重构**（REVIEW 已如实写「改前只靠 `requireWritable` 事后检查偶然拦住」），
   **不是可观察缺陷的修复**；真正的用户可见缺陷（同名 1 只读 + 1 产品时在只读卡上发起的写仍落产品卡）**仍在**，并已被新测试固化为预期行为。
4. **「探测不动熔断计数」→ 确认成立**，且提示里担心的「单线程调度器被 5s 探测阻塞」**前提不成立**（`SchedulingConfig` 早已 `poolSize=4`）。
5. **「web 发送按钮有内容才 enabled」→ 确认成立**：三入口（按钮/回车/图片）判据同一表达式，变异 3/2/1 红。
6. **「新增测试能捕获回归」→ 部分推翻**：M1 还原静默丢行 4 红 · M2 行号 off-by-one 3 红 · M6a 定位退回 8 红 · 前端 3 组 3/2/1 红；
   **但 HTTP 契约变异 0 红**（见第 2 条）。

## 五、教训（本批沉淀）

1. **「后端回了字段」不等于「用户看得见」**——P1-1 的根因是任务分派时把「前端消费」漏在范围外，而验收口径却按「用户可见」宣称。**凡用户可见目标，必须有一端端到端的验收点。**
2. **兼容性声明必须有测试钉住**——「保持 int 兼容」若没有断言，变异可随意破坏而全绿；口头保障在账本里等于没有。
3. **防御性重构要如实命名**——learn23 改前并无可复现的写穿路径（旧代码靠事后检查拦住），登记与汇报都不应说成「修了一个 bug」。
4. **守卫判据要看「哪一段」而非「全文」**——F6 因整份 REVIEW 正则命中即放行，让已归档编号长期挂在功能主轴；`ai-guard-context` 同类问题把功能数报成 40。
