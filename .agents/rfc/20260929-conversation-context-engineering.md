# 对话模式的上下文工程

> **触发来源**：2026-09-29 用户反馈「**用户反馈对话模式会丢失上下文，自查下**」，
> 自查后用户给出定性：「**目前关于对话模式，目前没有采用什么优秀的实践；我理解上下文交流，
> 目前应该有成熟的方案了吧，结合阿呆的记忆、插件等相关，我理解可以做一个调研，出个优化方案？**」
>
> **本件的定位**：① 把「像没看前文」的因果链钉到行号与生产数据（§一、§二）；
> ② 对标业界成熟做法，并明确**哪些不适用于本项目**（§三）；
> ③ 给出分层装配方案与分批实施（§四、§五）；
> ④ 给出可回归的验收判据（§六）与明确不做的事（§七）。
>
> **实施边界**：本文为**文档先行件**。获批前**不改任何代码、不动任何 `data/` 数据**。

---

## 一、现状事实（逐条钉到行号 / 生产数据）

### F1 「三层上下文」只有骨架，没有装配层——三个能力包是空的

`.agents/rfc/20260720-context-architecture.md` 早就定义了 Layer 1 当前对话 / Layer 2 阶段画像 /
Layer 3 领域上下文，并标注「已实现」。**实现的是"把三层的文本拼起来"，不是"按优先级分配预算"。**

项目为这三件事预留过位置，至今只有 `package-info.java`，**零实现**：

| 包 | 原本的职责（引自其 `package-info`） | 现状 |
|:---|:-----------------------------------|:-----|
| `kernel/context/prompt` | 「Prompt 模板、组装规则、注入策略」（按 Domain 不同） | **空包**；prompt 硬编码在 `ContextEngine.buildPrompt` 与 `DeepSeekAiClient.buildChatRequestBody` |
| `kernel/context/policy` | 「访问权限、数据范围、**时效控制**、上下文**优先级**、Domain 隔离」 | **空包**；时效目前只有「近 7 天」一个硬编码常量 |
| `kernel/context/token` | 「长度控制、内容压缩、优先级排序、**Token 预算分配**」 | **空包**；见 F5，连计量都是错的 |

**即：本件要做的不是发明新架构，而是把项目自己画好格子的那一层补上。**

### F2 「相关历史」实际是「最近 20 条」——72% 的对话模式请求都这样

`ContextEngine.compose` 组装上下文时调用 `loadRelatedRecords`（`ContextEngine.java:239-296`），
它有一个**回退分支**：当前记录**没有标签**时，不做标签关联，而是直接取**最近 20 条记录**
（`ContextEngine.java:242-267`，`MAX_RELATED_RECORDS = 20`，`ContextEngine.java:45`）。

为什么**对话模式下必然走回退**：用户提问时前端只提交 `content`，不带 `tags`
（`apps/adai-app/lib/services/api_service.dart:258-266`），而 AI 打标签发生在**回答之后**
（`QuestionAppService.finishAnswer`）——**所以提问这一刻 `record.tags()` 恒为空**。

生产实测（近 30 天 `adai-core` 日志，`ContextEngine` 组装行）：

| 指标 | 数值 | 含义 |
|:-----|:-----|:-----|
| 对话模式（`模式=CHAT`）请求总数 | **151** | 30 天 |
| 其中 `标签关联=22条` | **108（71.5%）** | 22 = 回退分支的 20 条 + 2 行标题——**满额注入最近 20 条记录** |
| 对话轮数 ≤ 5 轮 | **90（59.6%）** | 42×1 轮 · 26×3 轮 · 22×5 轮 |
| 对话轮数 = 1 轮 | **42（27.8%）** | 此时 messages 里只有 1 条用户输入 |

**结论**：六成对话不足 5 轮，其中七成请求把「最近 20 条与本话题无关的记录摘要」当成了
「相关历史」注入。**短对话时，真正的对话前文在整个输入里的占比趋近于零。**

### F3 检索层是死链路——朴素子串 + 整句当 query

`loadSearchResults`（`ContextEngine.java:304-336`）拿**当前记录内容的前 50 字整串**去搜索；
而 `SearchService.search` 的匹配是**朴素 `String.contains`**（`SearchService.java:60-73`），
**无分词、无 BM25、无排序、无 rerank**（结果按文件遍历顺序返回）。

于是：除非历史记录里**逐字包含**用户这句话，否则命中为 0。生产实测（近 30 天对话模式）：

| 搜索结果 | 次数 | 占比 |
|:---------|:-----|:-----|
| `搜索=0条` | **141** | **93.4%** |
| `搜索=5~7条` | 8 | 5.3% |
| 合计 | 151 | 100% |

**这一路注入 93% 的时候什么也没找到**——它没有帮上忙，却占着 prompt 的结构位置
（§F5 显示预算根本没把它算进去，所以连"占多少"都不知道）。

> **注**：`loadRelatedRecords` 取的「最近 20 条」来自 `recordRepository.findAll`，
> 其中**包含每场对话结束后由 `ConversationController` 落盘的 `type=conversation` 总结记录**。
> 即：一场对话的结论会以「总结记录 → 记忆 → 卡片轮次」**三种形式**同时出现在后续每一次提问里（见 §二 A3/A4）。

### F4 记忆注入是「近 7 天 + 按标签平铺」，与当前话题无关

`loadMemorySummary`（`ContextEngine.java:341-385`）取 `memoryService.recentActive(userId, 7)`
（`MEMORY_DAYS = 7`，`ContextEngine.java:46`；`MemoryService.java:448-453` 已按 Phase 2 排除
`superseded`），按标签聚合、**每标签最多取 2 条**，再单独拼一段「待行动事项」。

记忆模型本身不弱——`Memory` 已有 `kind` / `topic` / `superseded` / `evolvedTo` / `lastConfirmed`
（`Memory.java:11-35`，记忆进化 Phase 1-4），且 `20260923-rhythm-and-memory-temporality.md`
（**status: approved**）已批准补 **bi-temporal 有效期**。**但回读侧仍只有「7 天窗口」一个维度**：
不按话题检索、不按置信度排序、不做预算裁剪——「半年前被推翻的偏好」与「昨天的洞察」在
窗口内平权进入 prompt。

### F5 Token 计量是错的——算漏了对话历史与全部注入块

`ContextPackage.estimateTokens()`（`ContextPackage.java:79-84`）：

```java
int total = (identityRef != null ? identityRef.length() : 0)
        + (recordContent != null ? recordContent.length() : 0)
        + (prompt != null ? prompt.length() : 0);
return total / 2;
```

**漏算 `conversationHistory`（对话模式的主体）与 `relatedRefs`（20 条记录摘要）**，
且用「字符数 ÷ 2」粗估。生产日志里每行都打的 `预估 tokens=` **因此是失真值**——
它算的只是 prompt 字符串，与真正发给模型的内容无关。

**后果**：项目**没有 token 预算能力**——既不知道一次请求花了多少上下文，
也无法给任何一层设上限、做裁剪。这是「平铺拼接」得以长期存在的直接原因。

### F6 messages 结构对 prompt 缓存不友好

`buildChatRequestBody`（`DeepSeekAiClient.java:327-388`）的顺序是：

```
system ①  角色 + JSON 回执指令（固定）
system ②  background = 对话历史文本 + 20 条记录 + 记忆（每次都变）
system ③  从 prompt 截取的上下文（每次都变，且含 ② 的内容）
user/assistant 对话历史轮次（每次都变）
```

**固定的内容只有最短的第 ① 条，变动内容全部排在前面**——前缀不稳定，
按 token 计费的上下文缓存（KV cache 复用）难以命中。同时 ② 与 ③ 内容重叠、
对话历史又以「原始轮次」和「摘要行」两种形式各出现一次（§二 A3）。

### F7 可观测与测试的缺口

| 维度 | 现状 |
|:-----|:-----|
| 可观测 | 只有一行 `ContextPackage 组装完成 \| ... \| 标签关联=N条 \| 预估 tokens=M`——**无法回答「这次到底注入了什么、为什么、各占多少」**，也无回放手段 |
| 测试 | `ContextEngineTest`（316 行）**只覆盖领域路由与插件门控**；配额 / 优先级 / 去重 / 编排 / token 预算**零覆盖**（`ContextPackageTest` 亦同） |

### F8 数据规模与记忆画像——决定了「该用什么检索」

生产实测（2026-09-29）：

| 资产 | 规模 | 说明 |
|:-----|:-----|:-----|
| 记录（`rec_*.md`） | **393 条** | records 共 11 MB（含图片） |
| 对话卡片 | **86 张** | |
| 记忆条目 | **677 条** | memory 632 KB |
| 学习卡片 | — | learn 512 KB |

记忆的画像（677 条）：

| 维度 | 数值 | 解读 |
|:-----|:-----|:-----|
| `kind` = insight / **decision** / pattern / preference | 337 / **269** / 46 / 25 | **决策类记忆占 40%**——与 `20260923` 的「节律与时效」高度相关 |
| `superseded: true` | **285（42%）** | 进化（主题取代）**正在高频发生**；作废不删符合设计，回读侧已过滤 |
| `actionable: true` | 307（45%） | 其中 `doneAt` 非空仅 176——**「待行动」长期挂着的比例不低** |
| `lastConfirmed` 非空 | 456（67%） | Phase 4 的时效依据**只积累了三分之二**（另 1/3 从未被回读确认） |

> **取舍结论（进 §四）**：**这个量级完全不需要向量数据库**——393 条记录 / 677 条记忆，
> 即便每次提问对全量做一次关键词打分也是毫秒级。真正的缺口不是"检索不到"，
> 而是**现在根本没有打分与排序**（F2 只有时间序、F3 只有子串包含）。

### F9 路由层：判成陈述句的发言**不进对话**——近半数「带卡发言」如此

`RecordController` **只在 `QUESTION` 分支使用 `cardId`**（`RecordController.java:290-306`）；
一旦 `IntentRecognizer` 判成 `STATEMENT`，就走记录路径——**`cardId` 被丢弃、不建卡、阿呆不回应**，
且可能被 `RecordToTodoLinker` 自动转成待办。

生产实测（近 30 天）：

| 指标 | 数值 |
|:-----|:-----|
| 带 `cardId` 的请求 | **66** |
| 其中判为 `STATEMENT` | **31（47%）** |
| 这些 cardId 对应的磁盘卡片文件 | **0 个**（抽样 20 个逐一核对，20/20 均为 STATEMENT） |

> ⚠️ **排查提醒**：日志里的 `cardId` 与磁盘上的卡片文件**不是一回事**——前端为每条消息都生成了
> cardId（`main_page.dart:1059`），后端判为 STATEMENT 时**从不落卡**。本次自查一度据此怀疑
> 「31 张卡丢失」，逐一核对后**确认为误报**（31 = 31 条 STATEMENT）。**勿把日志卡数当卡片数**。

**用户体感**：在对话流里连着说话，第一句阿呆答了，**第二句它不吭声了**（只默默记下、
还可能自动生成一条待办）——2026-09-29 16:01 的两句即实测（`card_1790668870134`、
`card_1790668909715`，均 STATEMENT）。

**边界（不要误伤）**：对话态内续聊走 `ask-stream`（不经 `IntentRecognizer`），**不受此影响**；
受影响的是**不在对话态**时的输入——而"我是否还在对话里"对用户**完全不可见**
（与 **P1-前端4** 同族：web 已补可见性、app 端 `_syncActiveCard` 至今静默）。

## 二、问题定性：这不是 bug，是**装配层的缺失**

对照上下文工程的公开反模式，现在这一层踩了四条中的三条：

| # | 反模式 | 本项目的对应事实 |
|:--|:-------|:-----------------|
| A1 | **Context stuffing**（能拿到的都塞进去） | 20 条最近记录 + 最多 10 条搜索 + 7 天记忆 + 知识源 + 领域上下文 + 全部对话轮次，**无预算、无上限（除各自硬编码条数）** |
| A2 | **把「最近 N 条」当「相关 N 条」** | `loadRelatedRecords` 回退分支（F2）——**没有任何相关性判断，只有时间序** |
| A3 | **同一信息两种表示并存** | 对话历史既以 `user/assistant` 出现在 messages，又以「- [15:54] (question) 摘要」出现在两条 system 里 |
| A4 | **把摘要当事实来源** | 注入的 20 条全是 **AI 转述过的 summary**，原文细节已丢失；模型据此回答等于**二次转述** |

> **一句话定性**：现在的对话模式**不是「丢上下文」，而是「上下文被淹没 + 被无关内容带偏」**。
> 前文一直在（F2 的 1 轮对话除外），只是它在一堆「最近记录」里排不到应有的位置。

## 三、行业对标（成熟实践）

> 三路并行调研：① 多轮对话上下文工程；② 个人 AI 助手长期记忆架构；③ 检索注入策略与评测方法。
> 下表只保留**能直接改变本项目做法**的结论；★ = 有论文/厂商文档支撑，○ = 工程惯例（无公开对照数据）。

### 3.1 多轮对话上下文工程

| # | 结论 | 对本项目的含义 | 来源 |
|:--|:-----|:---------------|:-----|
| C1 ★ | **多轮对话本身就显著更难**：6 类任务平均下降 **39%**，机制是「早期轮次过早给出答案、被后续反复依赖——走错一步就回不来」 | 这是"像没看前文"最贴切的机制解释：**不是模型没读到，而是被前面的错误锚定带偏**——更要求前文干净、无干扰 | [LLMs Get Lost In Multi-Turn Conversation](https://arxiv.org/abs/2505.06120) |
| C2 ★ | **主题相关的干扰项比无关内容伤害更大**（context rot）；输入越长、性能**非均匀下降** | 20 条"最近记录"多数与当前话题**弱相关**——正是最坏的一类干扰 | [Chroma: Context Rot](https://www.trychroma.com/research/context-rot) |
| C3 ★ | 上下文的失败四分法：**poisoning / distraction / confusion / clash**；修法六种（RAG 选择、隔离、剪枝、摘要、卸载…） | A3/A4 属 **clash**（自相矛盾）——两份"同一事实的不同版本"共存时，掉 39 分那篇论文直接给了量化 | [How Long Contexts Fail](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html) |
| C4 ★ | 原则是找**最小的、高信号的 token 集合**（attention budget 边际递减），并**分节**（Markdown/XML 标题） | 支持 §4.2 的"配额 + 分节"，而不是"能塞就塞" | [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) |
| C5 ★ | **多条 system 消息的兼容性不一致**：Gemini 只支持一条（**最后一条生效、前面被覆盖**）；Qwen/Mistral/Gemma/Command-R 经 vLLM/LiteLLM 直接报 `System message must be at the beginning.` | 本项目现在**发 3 条 system**（F6）——既有兼容风险，也破坏缓存前缀 → **合并为 1 条、内部 Markdown 分节** | [pydantic-ai PR #6152](https://github.com/pydantic/pydantic-ai/pull/6152) · [pipecat issue #3362](https://github.com/pipecat-ai/pipecat/issues/3362) |
| C6 ○ | **摘要只应覆盖已被窗口淘汰的轮次**，不得与原始 messages 重叠；需要精确措辞时回读原文 | 直指 A3/A4 → §4.5 的"前文不得以摘要形式重复出现" | 同上（Anthropic） |
| C7 💰 | **缓存只认完全相同的前缀**。DeepSeek 按「缓存前缀单元」整段匹配、默认开启（见 §4.6）；而 OpenAI/Gemini 类有**最小长度门槛**（1024 tokens） | ⚠️ **不要为凑缓存去拼长上下文**——短对话（本项目 60% ≤5 轮）本来就不够门槛；缓存的正确做法是"**顺序摆对，顺带命中**"，不是"内容凑长" | [DeepSeek: 上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/) · [OpenAI Prompt caching](https://platform.openai.com/docs/guides/prompt-caching) |

### 3.2 个人 AI 助手长期记忆架构

| # | 结论 | 对本项目的含义 | 来源 |
|:--|:-----|:---------------|:-----|
| M1 ★ | 主流收敛为三层：**极小的常驻核心块**（有上限、可自编辑）+ **按需检索** + **原文可按路径回读**（Letta memory blocks：常驻且有 5000 字符上限） | 对应 §4.2 的 L0（常驻）+ L2（按需）；**"常驻"必须小且有上限** | [MemGPT](https://arxiv.org/abs/2310.08560) · [Letta memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks/index.md) |
| M2 ★ | **文件优先已被主流验证**：Letta MemFS 用 git 版控的 Markdown 当记忆、「目录即索引」（只把 `system/` 放进 prompt，其余按需打开）；Basic Memory 把 Markdown 定唯一真相源、数据库仅可重建投影 | **AdaiOS 的 File First 不用推翻**——我们缺的是"目录即索引 + 常驻块要有上限"，不是换存储 | [Letta MemFS](https://docs.letta.com/concepts/memfs/index.md) · [Basic Memory](https://neoneye.github.io/agent-memory-atlas/systems/basic-memory/) |
| M3 ★ | 写入策略两派：**只增不删、靠检索排序管时效**（Mem0 v3）vs **新事实让旧事实失效但不删**（Graphiti 双时态）；**共同底线：冲突不要静默二选一** | 与 `20260923` 的 bi-temporal 同向；本项目已有 `superseded`（42% 在发生）——**方向对，但回读侧没有把失效当成默认过滤** | [Mem0 how it works](https://docs.mem0.ai/core-concepts/how-it-works.md) · [Graphiti](https://github.com/getzep/graphiti) |
| M4 ★ | **最大的坑：抽取器只能修正它看得见的东西**（Khoj）——写路径若只把小范围记忆喂给模型，没被召回的矛盾记忆永远清不掉 | 本项目同病：`MemoryService.findTopicMatch` **只看近 30 天 + tags 重叠**（`MemoryService.java:456-476`）→ 更早/不同标签的旧记忆**永远无法被取代**。§4.3 需给写路径更宽的候选集 | [Agent Memory Atlas: Khoj](https://neoneye.github.io/agent-memory-atlas/systems/khoj/) |
| M5 ★ | **两臂召回**（Khoj）：近 N 天最新 K 条 **＋** 关键词/语义命中的历史 K 条，带日期注入并显式提示"不相关就忽略" | 对阿呆**零成本可落地**：把"最近 20 条"换成"两臂各 K 条"，比完整打分实现更简单、收益更直接 | 同上 |
| M6 ★ | **公开基准基本只测召回，不测纠正与遗忘**（LongMemEval 的 knowledge-update 也只考"答新值"；MemoryAgentBench 的"选择性遗忘"实为取序号更大的新事实） | §六 的评测必须**自己补**"纠正后旧值不再被注入"，并带 **no-memory 基线**与**等量随机剪枝的 placebo 臂**——否则无法证明"变好了" | [Agent Memory Atlas: Benchmarking](https://neoneye.github.io/agent-memory-atlas/benchmarks/) · [MemoryAgentBench](https://arxiv.org/abs/2507.05257) |
| M7 ⛔ | 明确**不要抄**：① 图数据库（Neo4j/FalkorDB，单用户下运维成本 >> 收益）；② 让模型直接 UPDATE/DELETE 用户文件（幻觉一次即丢数据）；③ 向量-only（人名/金额/日期/代码这类精确项，全文与标签优于向量）；④ 为省 token 删数据 | 写进 §七 | 同上 |

### 3.3 检索注入、预算与评测

| # | 结论 | 对本项目的含义 | 来源 |
|:--|:-----|:---------------|:-----|
| R1 ★ | **全量注入远差于聚焦注入**：聚焦 300 token 的输入在各模型族上显著优于 113k 全量；18 个模型**全部随输入变长而退化**，且**加一个无关项（distractor）就掉点**——无关内容不是中性的 | 现在「20 条最近记录 + 7 天记忆 + 知识源」平铺进 system，**不是"多给点没坏处"，而是实打实在掉点** | [Chroma: Context Rot](https://www.trychroma.com/research/context-rot) |
| R2 ★ | **关键信息位置比数量更重要**：中间最易丢（Lost in the Middle） | 对话历史现在被夹在两条 system 之后、且被重复文本稀释 → §4.6 的排序即为对症 | [Lost in the Middle (TACL 2024)](https://aclanthology.org/2024.tacl-1.9/) |
| R3 ★ | **「最近 N」≠「相关 N」**：跨会话记忆任务上，商业助手与长上下文模型掉 **30%** | F2 的「最近 20 条」正是这一个反模式 | [LongMemEval](https://arxiv.org/abs/2410.10813) |

| R9 ★ | 无向量库时：**BM25 召回 → 指纹去重 → 元数据硬过滤 → 线性加权 → top 4~6** | §4.3~4.5 的组合；**本项目的 frontmatter（type/tags/时间）是免费的一等检索信号** | ○ 工程惯例（同上组合） |
| R10 ○ | **重复注入比不注入更糟**：同一事实两个版本会让模型选错 | 直指 A3（对话历史以两种形式出现）→ §4.5 指纹去重 | ○ |
| R11 ○ | **预算惯例**：对话历史优先且**保真（近 6~10 轮原文）**；检索片段 ≤ 25~30%；记忆/画像 ≤ 15%；system 只留约束与输出契约；**明确"检索与对话冲突时以对话历史为准"** | §4.2 配额表；**注意公开文献没有硬性法则**，须用 §六 自测校准 | [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) |

## 四、优化方案（分层装配）

### 4.1 三条硬约束

| # | 约束 | 对应现状病灶 |
|:--|:-----|:-------------|
| **C1 前文优先** | 对话历史是最高优先层，**近 K 轮必须保原文**，任何其他层的注入都不得把它挤出预算；且**同一场对话的前几轮不得再以摘要形式重复注入** | A3 / A4（同一内容两种表示、摘要冒充前文） |
| **C2 相关 > 最近** | 任何进入 prompt 的条目都必须**过相关性打分**；**禁止**「时间序 top-N」直接注入 | A2（`loadRelatedRecords` 回退分支） |
| **C3 预算硬上限** | 每层有 token 配额，**按 token 截断而不是按条数**；超配额按分数淘汰 | A1（context stuffing）、F5（计量失真） |

### 4.2 分层与配额

把现在的「一个 prompt 平铺」拆成固定的五层，顺序即优先级：

| 层 | 内容 | 预算 | 取数方式 | 现状 → 目标 |
|:---|:-----|:-----|:---------|:------------|
| **L0 稳定前缀** | 角色 + 输出契约（JSON 回执）+ 能力边界 + 已启用插件清单 | ≤ 400 tok | 固定模板，**不含时间戳/随机 id** | 散落在 3 条 system 里 → 一条稳定 system |
| **L1 对话历史** | 当前卡片轮次；**近 K 轮原文**，更早的轮次可摘要（仅作导航） | 不设硬上限（但优先占用） | 卡片 `turns` | 已是原文全量 ✅ 保留；**从 system 里删掉重复的那份文本** |
| **L2 长期记忆** | 按相关性 × 时效 × 类型 top-K | ≤ 15% | 记忆检索（§4.3） | 「近 7 天 + 每标签 2 条」→ **按话题取 top-K** |
| **L3 检索片段** | **按需触发**，打分 top-k = 4~6，首尾摆放 | ≤ 25% | 记录检索（§4.3/4.4） | 「最近 20 条」→ **按需 + 打分** |
| **L4 插件知识** | 领域知识源（交易规则 / 学习卡）；**命中领域才注入** | ≤ 10% | KnowledgeSource | 每轮全量 → **命中才注入** |

> 配额口径来源：对话历史优先且保真、检索片段 ≤25~30%、记忆 ≤15%、system 最小化——
> 公开文献没有硬性法则，属**需自测的工程惯例**（见 §三）；本件建议**先用默认值上线，
> 用 §六 的回归用例校准**，不把它当真理。

### 4.2.1 按轮次分档——**最重要也很可能是收益最大的一条**

调研给出的 P0 建议，与本项目的数据高度吻合（**60% 的对话 ≤5 轮、28% 只有 1 轮**，F2）：
**短对话根本不需要 L2/L3/L4**——用户在第一轮问的通常是"直接问题"，此时注入 20 条无关记录
除了干扰没有任何作用（C2：主题相关的干扰项伤害最大）。

| 对话轮次 | 注入层 | 理由 |
|:---------|:-------|:-----|
| **≤3 轮**（本项目约 **45%**） | **只有 L0 + L1**（身份/契约/插件清单 + 当前卡片全部轮次原文） | 短对话靠前文就够；少注入 = 少干扰（P0 三条之一） |
| **4~9 轮** | L0 + L1 + **L2（记忆，两臂召回 K=3~5）** | 话题已成形，长期偏好开始有价值 |
| **≥10 轮** | 全层（+ L3 检索，按 §4.4 触发） | 长对话才需要外部补充；此时缓存也已成形 |

**收益**：短对话的输入从「1 条前文 + 20 条无关摘要」变成「1 条前文 + 身份/契约」——
**直接对症"像没看前文"**。代价：长问题的主动关联变弱（用户多问一句即可补上）。

### 4.3 怎么「取」：两臂召回（先做）→ 加权打分（增强）

**第一步（P0，几乎零成本）：把「最近 20 条」换成两臂召回**——这是 Khoj 的做法（M5），
用两条互补的臂各取 K 条，替代现在的单臂「时间序 top-20」：

| 臂 | 取什么 | 回答哪类问题 |
|:---|:-------|:-------------|
| **A 臂 · 近因** | 最近 N 天内的 **最新 K 条**记忆 / 记录 | 「我刚才说的」「今天提过」 |
| **B 臂 · 相关** | 用**补全指代后的当前问句**做**关键词/标签命中**取历史 K 条 | 「我以前说过」「关于 X 我怎么想的」 |

每条**带日期**注入，并在注入文本里写明优先级：「**与当前对话冲突时以当前对话为准；
引用旧信息时说明你记的是哪一条（带日期）**」。这一句同时解决 M3 的「冲突不要静默二选一」。

> 为什么先做这个而不是直接上打分：它**不需要新组件**，改的是取数逻辑（`ContextEngine.loadRelatedRecords`
> 与 `loadMemorySummary`），且比"打分"更容易验证好坏（§六 的回归用例）。

**第二步（P1，可选增强）：加权打分**（照搬 Generative Agents 的三因子，R8）：

```
score = w1 · 相关性(关键词命中数 / 标签重叠, 归一化)
      + w2 · 重要性(kind=preference/pattern 加权；decision 加权)
      + w3 · 时效衰减(exp(-λ·Δt)，λ 由 §20260923 的 bi-temporal 有效期给出)
      - w4 · 重复惩罚(与已注入内容指纹相同 → 直接淘汰)
```

- **相关性**：现在「标签重叠」只用于*找同主题*、**从不用于排序**；叠加**关键词命中**
  （问句与 `title/content/summary/tags` 的命中数）。§F8 已证明 393 条记录 / 677 条记忆
  在这个量级下**全量打分是毫秒级**，不需要索引结构。
- **时效**：接 `20260923-rhythm-and-memory-temporality.md`（approved）的 bi-temporal，
  **不重复造轮子**；`lastConfirmed` 已积累 67%（F8），可直接当权重因子。
- **权重要可配**：`application.yml`（`adai.context.*`），便于按 §六 调参，不写死常量。

### 4.3.1 写路径也要一起改（否则旧记忆永远清不掉）

调研点名的**最大陷阱**（M4）：**抽取器只能修正它看得见的东西**。
本项目同病——`MemoryService.findTopicMatch`（`MemoryService.java:456-476`）判定"同主题"的依据是
**近 30 天 + tags 重叠**：更早的、或标签没重叠但事实冲突的旧记忆，**永远无法被取代**，
会与新的正确记忆长期共存（正是 A3/A4 的 clash 来源）。

治法（与 `20260801` / `20260923` 衔接）：**给写路径更宽的候选集**——按标签/实体命中
（而不是按"本轮注入集"）找出**可能被推翻**的旧记忆，再让模型输出「新增 + 需失效的 id」，
失效 = **打标（`invalidAt` / `superseded`），不删文件**（M3 的底线：冲突不静默二选一）。

### 4.4 检索触发与 query 构造（默认关闭）

现在的检索是**无条件每轮执行**且几乎必然落空（93.4%，F3）。改为：

| 触发条件 | 判据 |
|:---------|:-----|
| 指代/省略 | 问句含「它 / 这个 / 那篇 / 上面说的 / 继续」等，且**近 3 轮未出现明确实体** |
| 话题漂移 | 当前问句与近 3 轮实体的重叠度低于阈值（TopiOCQA：约 28% 的轮次确实需要换话题） |
| 显式要求 | 用户说「我之前说过 / 找一下 / 上次那个」 |
| 模型主动取 | 保留一条轻量通道（后续可做工具化，本批不做） |

**query 构造**：优先**规则改写**——把指代替换为**最近 2~3 轮出现过的实体**，再拼上当前问句；
仅在"含指代且找不到实体"时才调一次 LLM 改写（成本可控）。
不要用「前 50 字整串 contains」（F3 的根因）。

### 4.5 去重：同一内容只进一次

给每段注入内容打指纹（`来源 + 内容哈希`，或对话历史用 `cardId + 轮次序号`），命中即淘汰：

1. **与 L1 对话历史去重**——同一场对话的前几轮**不得**再以「摘要行 / 总结记录」出现在 L2/L3；
2. **L3 内部去重**——同一文件只保留最相关的 1~2 段；
3. **与 L2 记忆去重**——记忆本身是记录的提炼，若同源记录已在 L3，取其一（默认保留原文，丢弃转述）。

### 4.6 顺序：**唯一一条 system + 历史在中 + 动态垫底**

这一步的主目的是 **C1（前文优先）与 C5（兼容性）**，缓存只是顺带的结果。

**现状有两个问题叠在一起**（`DeepSeekAiClient.java:327-388`）：

1. 发了 **3 条 system**，其中第 ②③ 条每轮都变（对话历史文本 + 20 条记录 + 记忆）——
   *兼容性风险*：部分后端只支持一条 system（Gemini 取**最后一条**、Qwen/Mistral 直接报错，C5）；
2. 变动内容排在 messages **最前面** → 按 DeepSeek 的「缓存前缀单元」规则
   （[上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)：**前缀必须完整匹配**才命中，
   官方"例一"显示多轮对话天然可命中），**前缀第二段就变了 → 从那里起全部失效**。

目标结构：

```
system            唯一一条 system：
                  角色 + 输出契约(JSON 回执) + 能力边界 + 已启用插件清单 + 长期画像
                  ← 逐字稳定（不得含时间戳/随机 id/按用户拼的文本）
user / assistant  对话历史轮次（逐轮增长 ⇒ 天然构成命中前缀，官方例一）
user              当前问句（其前附一段「本次参考」：记忆 TOP-K + 检索片段，仅在触发时）
                  ← 每轮都变，但因为排在最后，不破坏任何前缀
```

要点：

1. **合并成 1 条 system、内部用 Markdown 分节**（C4 的分节建议 + C5 的兼容性）；
2. 变化的记忆/检索**并入最后一条 user 消息**（而不是新增 system）——这样既保住前缀，
   又让模型把"背景"当成用户提供的信息而非系统指令；
3. **记录缓存命中**：DeepSeek 响应 `usage` 里返回 `prompt_cache_hit_tokens` /
   `prompt_cache_miss_tokens`——现在**一个都没记**（F7），补上即可量化（同时把 F5 的"假 token 数"换成真数）。

> ⚠️ **不要为了缓存去拼长上下文**：OpenAI/Gemini 类有 *1024 token 最小长度*门槛，
> 本项目 **60% 的对话 ≤5 轮**（F2），本来就不够门槛；DeepSeek 按"前缀单元"匹配，
> 短对话也可能命中，但**收益本来就小**。正确顺序是：
> **先把"少注入"做对（§4.2.1），缓存是摆对顺序后的副产品，不是理由**（C7）。

### 4.7 把三个空包填上（落点）

| 包 | 本件要落的东西 |
|:---|:---------------|
| `kernel/context/token` | `TokenBudget`（各层配额）、真实计量（含 `conversationHistory` 与全部注入块）、按 token 截断 |
| `kernel/context/policy` | 时效与数据范围（接 §20260923 的 bi-temporal）、注入优先级、**去重指纹**、检索触发判据 |
| `kernel/context/prompt` | L0/L2/L3/L4 的**模板与拼装规则**从 `ContextEngine` / `DeepSeekAiClient` 里搬出来，可 diff、可 A/B |

**不改 API 契约、不改前端**（`ContextPackage` 对外形状不变，仅内部装配与顺序变化）。

### 4.8 可观测与回放

- 把现在那行 `ContextPackage 组装完成` 扩成**每层用量**：`L1=…tok(12轮) L2=…tok(6条) L3=…tok(4条,触发=指代) L4=…tok`；
- 新增**上下文回放**：一次请求的完整装配结果可 dump（供排查"这次为什么这么答"）；
- 日志里打的 token 数**必须是真实计量**（F5 修正后）。

## 六、验收判据

**可量化（生产可观测）**

| 指标 | 现状基线 | 目标 |
|:-----|:---------|:-----|
| 对话模式中「无条件最近 20 条」占比 | **71.5%**（F2） | **0**（全部经相关性） |
| 检索命中率（非 0 条） | **6.6%**（F3） | 触发时才检索，命中率显著提升；**未触发时不上报"搜索=0条"** |
| 每层 token 用量 | **不可知**（F5） | 每次请求可见，且不超配额 |
| 真实 token 计量误差 | 现值**漏算历史** | 与调用方返回的 usage 比对，误差 < 5% |
| 缓存命中 token | 未记录 | 上线后可观测并逐步提升 |

**回归用例（批 2 的前置）**

- 建 **20~40 条**对话回归用例，每条标注「**必须引用的前文事实**」与「**不得出现的错误断言**」；
  建议配比：近期事实 15 · 跨月偏好 10 · **已纠正的旧事实 10（答案必须是新值）** · 应弃答 5
  ——最后一类是公开基准**普遍没测**的能力（M6）；
- 判分：**成对比较** + 换位跑 LLM-as-judge（避免位置偏置），二值判分；
- **必须跑三臂对照**（M6）：`全量注入（现状）` / `新装配` / **`no-memory 基线`**，
  并加一个 **placebo 臂**（等量随机剪枝）——**否则无法区分"变好了"与"上下文变短了"**；
- 门禁：进 `/ship`（与现有 `guard-*` 同级），**改了上下文装配必须过**；
- ⚠️ 多轮判分必须**把完整两轮对话放进同一个 judge prompt**（拆两次调用会让 judge 看不到上轮回答而误判，R13）。

## 七、取舍与不做

| 不做 | 理由 |
|:-----|:-----|
| **不引入向量数据库** | F8：393 条记录 / 677 条记忆——全量关键词打分为毫秒级，向量库的收益在万级以上，代价（依赖/运维/落盘形态）立即发生 |
| **不引入 cross-encoder rerank** | 需额外模型与算力；本场景用「关键词 + 标签 + 时效」线性打分即可（§4.3） |
| **不引入 Mem0 / Zep / Letta 等框架** | 它们的分层思想**作为对标采用**（§三），但引入依赖会破坏 File First 与单体边界 |
| **不做 HyDE / multi-query 扩展** | 依赖向量空间或成倍调用成本；单用户场景收益递减 |
| **不改 API 契约、不改前端** | 本件是**装配层内部**改造，对外形状不变 |
| **不做「模型主动取记忆」的工具化** | 属更远的事（需要工具调用通道），本件只保留它的位置（§4.4 最后一档） |
| **不让模型直接改写 / 删除记忆或记录文件** | 调研的一致警告（M7）：**幻觉一次就丢用户数据**。记忆的"失效"一律**打标不删**（`invalidAt` / `superseded`）；唯一例外是用户**显式**说"忘掉这个"——那也应落 tombstone 并防"下次再从原文抽回来" |
| **不为省 token 删除任何数据** | 时效衰减只做**排序信号**，不做删除依据；冲突时原文是唯一证据（§4.5 去重只是"这一次不注入"，不是"删掉"） |
