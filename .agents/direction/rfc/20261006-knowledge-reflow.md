# 知识回流固定流程

> **状态**：**`draft`**（待 adai 拍板，四处 ★ 见 §八）。
> **一句话**：给「一次开发/对话中得到的认知」一条**固定通道**——**AI 提议 → 人确认 → 按类型落盘 → 守卫验证**；**禁止 AI 自动写入 L2**。
> **为什么现在做**：`ai-context-engineering.md` **§4.5** 的标题就写着「**一次知识回流（对话 → L2）—— 待建**」，§七 硬规则 8「知识回流需人确认」标 ❌ 待建；2026-10-06 用户明确「**知识回流需要一个固定流程**」。

---

## 一、背景

**现状：沉淀是「靠自觉」的，没有通道。**

一次开发 / 对话里会产生若干**值得长期保留的认知**——坑、约定、决策、边界、依赖，以及 **AI 上下文本身**（角色 / 规则 / 流程 / skill 的改进）。今天它们只能：

- **靠人记得记**（自己往 `pitfalls` / `conventions` 里补）；
- **靠 AI 顺手记**（在 `change-log` 里写一句、或在会话里提一嘴）——**不保证发生**。

**后果**（本项目已实证）：
1. **好经验不沉淀** ⇒ 下次重新踩（`pitfalls` 里多条都是「复发信号已写、但当时没人回流」）；
2. **落点随意** ⇒ 同一认知进 `change-log`、`pitfalls` 还是 `conventions`，全凭当下判断；
3. **最危险的一条**：**AI 把未验证的假设写进项目知识** —— 这正是 §七 8 要防的（「禁自动写入 L2」）。

**已有相邻机制**（本 RFC 与之接上，不重复造）：

| 机制 | 干什么 | 与回流的关系 |
|:--|:--|:--|
| **归档**（`review-driven.md §5` · `workspace/_directory.md`）| 把**产物**（需求/设计/报告/账本）从在制品搬进知识库，**成为下次开发的基石** | **搬产物** vs 回流**提炼认知** ⇒ 两条并行通路 |
| **`ai-guard-sediment.sh`**（`ship.md §4`）| 收工时**检查有没有沉淀**（S1 坑/ADR · S2 REVIEW 出表 · S3 change-log）| **它查「有没有」，回流管「怎么产生」** ⇒ 回流是它的**上位** |
| **审核驱动主链**（`review-driven.md`）| 需求 → 设计 → 编码的过程契约 | 回流是它的**收尾延伸**（过程产生认知 ⇒ 回流沉淀认知）|

## 二、要回流什么（信号分类）

| # | 信号 | 典型形态 | 落点（唯一真相源）|
|:--:|:--|:--|:--|
| **S1** | **坑** | 「这么干会炸」/ 复发信号 | `rules/assets/pitfalls.md` |
| **S2** | **规范 / 约定** | 「以后一律这么写」 | `rules/assets/conventions.md` · `naming-spec.md` |
| **S3** | **决策** | 「为什么选 A 不选 B」 | `rules/assets/adr/`（架构）· `direction/rfc/`（方案）|
| **S4** | **边界** | 「禁止…」 | `rules/assets/boundaries.md` |
| **S5** | **依赖 / 契约** | 「谁依赖谁、接口长什么样」 | `ARCHITECTURE.md` · `knowledge/reference/contracts/` |
| **S6** | **AI 上下文本身** | 角色 / 规则 / 流程 / skill 的改进 | `rules/` · `toolkit/roles` · `toolkit/skills` · `mechanism/` |
| ~~S7~~ | ~~状态 / 事实~~ | 测试数 · 端点 · 环境 | `knowledge/reference/status.md` |

> **S7 刻意排除**：它**有机械对拍**（`ai-guard-align` A1/A2）⇒ 不需要人确认，走守卫即可。

## 三、流程设计（五步 · 核心）

```
① 会话中：AI 遇 S1–S6 信号 → 记入「临时候选区」(workspace/_meta/sediment-candidates-<日期>.md)
        ↓（不打断当前工作、不写 L2）
② 收工 / 会话结束：AI 输出「待沉淀清单」——每条：信号类型 · 一句话 · 建议落点 · 依据（文件:行）
        ↓
③ ★ 人确认门（硬约束 · 禁自动写入）：逐条 采纳 / 改落点 / 驳回
        ↓
④ 落盘：按 §二 的落点写入（显式路径 + 守卫）
        ↓
⑤ 验证：ai-guard-sediment.sh（收工时跑）+ 对应守卫（改代码则跑测试）
```

**为什么候选区要先落盘**：① 信号往往出现在「正在解决问题」时，先落盘**不打断工作**；② 清单**可追溯**（谁在何时提了什么、被采纳还是驳回）；③ 避免「会话结束才回忆」——**回忆一定丢东西**。

**触发时机**（★1 待拍板）：收工（`task-cadence ship`）· 会话结束 · 里程碑前 · 人显式说「回流一下」。

**与 `ship` 的关系**：`ship.md §4` 已有「决策沉淀（RFC 验收核验 + 沉淀检查）」⇒ 回流清单**并入这一步**，不新增步骤（保持「一条命令收工」）。

## 四、防线（什么情况下不写）

- **未验证的假设**：只观察过一次、没有复现 ⇒ **不写 L2**，留候选区标「待验证」；
- **一次性的**：只对该任务成立的取舍 ⇒ 进 `change-log`（批次摘要）即够，**不进规范**；
- **已有条目**：同型信号**并入既有条目**（`pitfalls` 加「复发信号」、`conventions` 加一条），不新开一段；
- **超出 AI 判断的**：涉及产品方向 / 价值观 / 对外承诺 ⇒ **升级给人拍板**，不在回流里定。

## 五、不做清单

- **N-01 不做「全自动沉淀」**：AI 直接写 L2 ⇒ 未验证的假设会污染知识库（§七 8 明确禁止）；
- **N-02 不做「把所有会话都回流」**：信号密度低，全量会让清单变噪音（**宁可少、不可滥**）；
- **N-03 不给每个信号建独立文件**：落点是**既有集中档**（pitfalls / conventions / ADR…），避免文件爆炸（防膨胀红线 §七 9）。

## 六、备选与理由（考虑过、未采纳）

| 备选 | 为什么不选 |
|:--|:--|
| **A. 全自动**（AI 直接写入 L2）| 违反「禁自动写入 L2」；未验证假设会污染知识库；出错难追溯 |
| **B. 纯人工**（人自己记）| **AI 明明有信号却不说** = 浪费；且人不可能记得住全部 |
| **C. AI 提议 + 人确认** ★ | 平衡点：AI 负责**发现与起草**（它看得到全过程），人负责**判断与准入**（价值观 / 方向）|
| **D. 只做「事后回顾」**（不设候选区）| **回忆一定丢东西**；且无法区分「当时想到」与「事后补脑」|
