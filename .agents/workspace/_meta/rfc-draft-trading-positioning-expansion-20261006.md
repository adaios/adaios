## 一、背景（为什么要扩容）

| 动因 | 内容 |
|:--|:--|
| 现状边界 | 当前 trading 的「理解」是从 **owner 自己的一套交易系统**长出来的——默认用户有规则，历史上甚至拿 owner 的 R1–R120 去判别人 |
| 直接用会怎样 | 别人一开箱，要么**一条规则都没有**（引擎空转），要么拿到的是**「别人的系统」**（越界 + 失真）——插件事实上只能 owner 自用 |
| 需求已提出 | `requirement.md` 问题/动机段已定稿：「**人人可用**：没有交易系统的人也能用」「**人人可制定规则**」；`decisions.md` **S2** 拍板「补一份 RFC（记定位变更 + 与 87 课知识库的关系）」 |
| 为什么是现在 | 交易插件重做（`design-final`）以 **U1 渐进重构**推进，每批保持可用；定位不定死，重构会把「owner 专属」的假设固化进新代码——**定位是编码准入条件之一**（`design-final` §13.3①） |

## 二、新定位

**一句话**：交易插件从「**owner 专属的建议引擎 / 交易记忆**」扩为「**人人可用的交易记录与照见**」——**有规则的人照纪律，没规则的人先看见自己**。

| 维度 | 旧（`20260902` 之前 / 之中） | 新（本 RFC） |
|:--|:--|:--|
| 用户 | owner（及用「adai 体系」的熟人） | **人人**——含**没有交易系统、只愿意如实记录**的人 |
| 默认值 | 引擎默认 = adai 内置判断体系 | **默认 = 空规则**；没规则时**只说事实、不给判断** |
| 规则的来源 | 自建 / 导入（owner 的体系） | 自建 / 导入 + **从用户自己的数据里长出来**（候选规则，带据） |
| 输出主语 | 「你」（`20260902` 已立） | 「你」**不变**（合规口径不动） |

**承接关系**：不改 `20260902` 的**输出形态**（照见 / 对照 / 陈述），只改**服务对象与默认值**。

## 三、与 87 课规则层（`os/trading-engine`）的关系

这是本次扩容的**合规关键**（对应 ★1）：

| 项 | 结论 |
|:--|:--|
| 87 课是什么 | `os/trading-engine/` 是 **owner 的规则层 · 私人财产**（owner **人工写就**的交易体系） |
| 与「你自己的规则」的关系 | **同构**——87 课与你自己的规则是**同一种东西**（规则层），区别只在**来源**：87 课 = **人工写就**的规则层，新用户 = 从**自己的数据长出来**。**正因为同构，才不能拿一个人的规则层当另一个人的默认值** |
| 怎么注入 | 经 `TradingKnowledgeSource` **只对 owner 注入**（owner 私有优先，`P1-3` 白名单） |
| 非 owner 怎么办 | **一律不注入 87 课**——**新用户的规则走「从自己的数据里长出来」**（候选规则 + 带据 + 用户认下） |
| 为什么 | ① **防越界**：把 owner 的体系当默认值去判别人，等于拿别人的尺子量你；② **防失真**：非 owner 的持仓/风格与 owner 体系不匹配，注入即误导 |

> **一句话边界**：「**我的规则层只服务我**」——owner 的 87 课不对任何非 owner 用户构成默认值或建议来源。

## 四、规则层的写入路径（对应 ★4）

扩容后「规则从用户自己的数据长出来」要落到**哪一层**，是本 RFC 必须写明的实现边界：

| 项 | 现状 / 边界 |
|:--|:--|
| 现状 | `promote` 对**所有** trading 用户开放——每个用户各自写**各自候选**；但**只有 owner 的候选**才有人工提升、进 `os/trading-engine/99-inbox/` |
| 提升边界（必须写明） | **提升动作只能提升 owner 自己的候选**，执行者 = **owner / admin**——**非 owner 的候选永不可能进 `os/`** |
| 两者待遇不同 | `os/trading-engine/` = **git 跟踪的私人财产**（版本化、可 review）；`data/{userId}/` = **不外流**（gitignore）——**同一个「规则」概念，在两处的可见性与版本化待遇不同** |

> **为什么单列一节**：扩容的新用户路径全部落在 `data/{userId}/`，而 `os/trading-engine/` 始终只是 **owner 的私人财产层**——两层**不混**，才不会出现「非 owner 的规则被别的用户读到」的越界（与 §三 同源）。这一节的两句边界是否认可，见 **★4**。

## 五、合规口径（沿用 `20260902` 的原则，不改）

**判断标准一条**：**输出主语永远是「你」，不是「市场」。**

| 能说（自我认知） | 不能说（荐股） |
|:--|:--|
| 「你过去 20 个案例胜率 X%，本次与你历史样本相似度 Y%，按**你自己的规则**，当前接近你的止损位」 | 「现在买 XX / 该止损了 / 到买点了」 |

**并明确两条硬边界**：

1. **不给具体品种 / 时机的建议文本**——`X-01`（下单/执行/预测/荐股）不进任何版本；
2. **建议类动作按钮从代码层消失**（`20260902` §五.3 已立），扩容**不例外**。

## 六、不做清单（**写进 RFC 即成为对外承诺**）

以下三项**明写不做**；**以后要做，须先改本 RFC**（对应 ★2）：

| ID | 不做 | 出处与理由 |
|:--|:--|:--|
| `N-01` | **规则的分享** | `requirement.md` 范围 · 先不做；**理由：分享 = 处分私人财产**（尤其那些**源自 87 课**的规则） |
| `N-02` | 「**周期**」层（周 / 月总结） | `requirement.md` 范围 · 先不做 |
| `X-02` | **用户端**出现行情 / 活跃市值的**导入入口**（归 **admin**） | `requirement.md` 范围 · 不做 |

> **将来若要做分享**：**必须先在 RFC 里回答两问**——① **哪些规则可分享**？② **87 课出身的规则算不算**？
> **注意**：`X-01`（下单/执行/预测/荐股）是永久不做，已在 `requirement.md` 单列，**不在本「先不做」清单内**。

## 七、与 `20260902` 的承接关系（逐条 · 对应 ★3）

> **一条主线**：本 RFC 与 `20260902` **不是两个孤立决定**——「**记忆 → 规则**」是**同一条线的两段**：`20260902` 管的是**记忆**（建议引擎 → 交易记忆），本 RFC 管的是**规则**（交易记忆 → 人人可用 + 规则自生长）；**两份合起来才是完整的交易主线**。

| `20260902` 的条款 | 本 RFC 怎么处理 |
|:--|:--|
| **核心定位**「不是记账工具，是交易记忆；建议引擎条款被取代」 | **承接**（继续有效）——本 RFC 在此之上**扩服务对象**，不推翻 |
| **五层记忆模型**（事件/模式/案例/规则/认知） | **承接**（继续有效）；扩容主要影响「④ 规则记忆」的**来源**（多一条「从数据长」） |
| **合规边界**（输出主语永远是「你」） | **承接**（继续有效，本 RFC §五 原样重申） |
| **工程纪律**（数字系统给 / 理解客观推导 / 红线长在形态里） | **承接**（继续有效） |
| **公开版种子语义**「默认 = 空规则 + 纯客观执行」 | **承接并升格**——`20260902` 把它写成「实施时拍板」，**本 RFC 把它定为扩容后的默认口径** |
| **数据职责分层**（个人数据归 web 用户 / 行情归 admin） | **承接**（继续有效，`X-02` 由此推出） |
| `20260815` 的「核心定位」条款 | 已被 `20260902` 取代；本 RFC **不重复处理** |

**是否取代某条**：**不取代**——本 RFC 是**增量**（交易记忆 → 人人可用 + 规则自生长）。★3 要人确认的正是这一点（若人认为应「取代 `20260902` 某条」而非承接，方向记录会自相矛盾，须显式改）。

## 八、备选与理由（本 RFC 考虑过、未采纳的路）

| 备选 | 为什么不选 |
|:--|:--|
| **A. 不动定位**，只做功能（多用户也能用） | 定位不定死则默认值不明：新用户一开箱要么空引擎、要么吃 owner 体系——**越界/失真的根因仍在**，S2 无法闭环 |
| **B. 给非 owner 也注入 87 课**（当「开箱即用」卖点） | 把 owner 私人财产层当别人的默认尺子 = 越界 + 失真，且放大荐股色彩；**合规红线级不可取**（★1） |
| **C. 整份 `supersede` `20260902`** | `20260902` 的输出形态 / 合规口径 / 五层模型**仍然有效**，整份取代会造成方向记录断代；正确做法是**承接 + 增量**（§七） |
| **D. 规则分享（`N-01`）一起做**（扩容即分享） | 分享 = **处分私人财产**（尤其 87 课出身的规则，与 §三 同源风险）+ 隐私面未定；`requirement.md` 已明写「先不做」，**写进 RFC 即承诺**（★2） |

## 九、★ 待 adai 拍板（四处 · 本稿不自行定）

> 四处均为**方向级**判断，**定错会让方向记录自相矛盾或形成对外承诺**——**必须由人拍板**。

- **★1 扩容边界**：**非 owner 一律不注入 87 课**——这是**合规红线级的决定**（§三）。
- **★2 不做清单**：§六 三项（`N-01` / `N-02` / `X-02`）**进 RFC 即成为对外承诺**，以后要做须先改 RFC。
- **★3 与 `20260902` 的关系**：**承接**还是**取代某条**——定错会让方向记录自相矛盾（本稿主张「承接 + 增量、不取代」，见 §七）。
- **★4 规则层的写入路径**：owner 新写 / 改的规则，是**只落 `data/{userId}/`（数据层）**，还是经**人工提升**回 `os/trading-engine/`（**私人财产层**）？——「**提升只能提 owner 自己的候选**」「**执行者是 owner / admin**」这两句**是否认可**？（§四）
