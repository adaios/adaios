# 提案 · 交付完备性机制（scope 对照表 + 守卫 + 出门判据）

> **一句话**：上游每一站都审「产物」，但「从设计里裁剪本批该做什么」是一个**动作**——无产物、无审查、无判据。本提案给它装上三样东西：**显形产物（scope 表）· 机械判据（守卫）· 出门条件（判据升级）**。
> **绑事故**：`REVIEW.md` **P1-交易101**——交易插件重做前端整体未交付且未声明，一路绿灯过审 / 合并 / 上线（2026-10-06 部署后用户追问「web 端就这点变化？」时查实）。
> **门禁合规**（`review-driven.md` §8 硬规矩 2）：① 新判据绑真实事故 ✅（P1-交易101）；② 走「提案 → 守卫 → 人点头」——本文件即提案，守卫＝`ai-guard-scope.sh`（新）+ 既有 meta/structure，人点头＝**2026-10-06 用户拍板**（见 §五）。

## 一、病因（为什么一路绿灯）

| # | 洞 | 事实 |
|:--:|:--|:--|
| 1 | **编码段无「本批范围声明」** | 需求 / 设计都有产物+评审官；编码段开工无范围文件，「前端下批」的隐含裁剪无载体 |
| 2 | **审查对象是 diff，不是设计** | 三官深审输入＝工作树改动；前端没改＝不在视野。「§1–§13 全量实现核查」无机械判据、未执行 |
| 3 | **出口判据不含完备性** | `review-driven.md` §5 编码出口＝测试+无 P0/P1+pre-commit——全是对「已写代码」的要求 |
| 4 | **账本无「未交付项」栏** | LEDGER 只记「做完了的」，缺口在账本上不可见（**栏已补**，`60358acf`） |
| 5 | **发布按路径不按承诺** | 「web 改了 3 文件→web 要发」→ 上线；「端已发」与「端没功能」可同时成立 |
| 6 | **验收被事实上跳过** | 介入点③前置材料缺失（无逐条走查），收尾做的是「部署」而不是「走验收 1–11」 |

## 二、方案（六条 · 每条含机械判据）

| # | 改进 | 落点 | 关键判据 |
|:--:|:--|:--|:--|
| 1 | **scope 对照表**（开工计划态 → 收尾交付态，同一份文件） | `_templates/scope.md` + `review-driven.md` §3 | 条目覆盖设计 §6 全部条目；未交付/下批必填去向 |
| 2 | **守卫 `ai-guard-scope.sh`**（S0–S5） | `mechanism/guards/` + ship 前置 | S3「已交付」须**证据路径存在 + 关键词可 grep**——本例在 `apps/adai-web/` 零引用即当场 FAIL |
| 3 | **入口 / 出口判据升级** | `review-driven.md` §3（开工第一动作）+ §5（编码出口） | 无计划态表**不开工**；收尾无「交付态闭合 + 验收走查」**不进 ship** |
| 4 | **审核官从「审 diff」升级为「审声明」** | `review.md` 增量深审加节 | 抽查已交付真伪 · 未交付无遗漏 · **「用户真能用」**标准（端点存在 ≠ 界面可用） |
| 5 | **发布对拍**（承诺对账） | `ai-guard-release.sh` 加输出节 | 输出「已交付 N / 未交付 M + 去向」；M≠0 须显式确认 |
| 6 | **验收走查**（验收 1–11 逐条） | `review-driven.md` §4 介入点③前置 | **走不通＝缺交付物**→ 自动进 scope 表未交付栏 |

### 条 1 · scope 表（格式定死，守卫按此解析）

位置：`.agents/workspace/<分支名>/scope-<任务名>-<日期>.md`（模板 `_templates/scope.md`）；正文必须含一行 `> 基线：<设计稿相对仓库根路径>`。

| # | 条目 | 面 | 计划 | 状态 | 证据 | 去向 |
|:--|:--|:--|:--|:--|:--|:--|
| `R-05` | 三粒度分析 | web | 本批 | 未交付 | — | LEDGER 🟥 · 批 2 |

- `#`＝设计 §6 条目 ID（R-xx；特殊条目「资金层/择时/行情」）；`计划` ∈ {本批, 下批, 不做, 非本任务}；`状态` ∈ {已交付, 未交付, —}；
- `证据`＝`路径#关键词1,关键词2`（多个用 `;` 分隔）；走查类可写 `case:<说明>`（人工核，守卫豁免但不视为机械证据）；
- `去向`：状态=未交付 / 计划=下批必填；含 `LEDGER`→守卫查 LEDGER.md 含 🟥；含 REVIEW 编号→守卫查 REVIEW.md 有该编号。

### 条 2 · `ai-guard-scope.sh` 判据（S0–S5）

| 项 | 判据 | 级别 |
|:--:|:--|:--:|
| S0 | 防假绿：scope 表解析出 ≥1 数据行、设计稿 §6 解析出 ≥10 条目（解析失败宁可报错） | FAIL |
| S1 | 设计 §6 条目集 ⊆ scope 表 `#` 列集合（**每个条目都要有交代**，哪怕「非本任务」） | FAIL |
| S2 | `计划`/`状态` 枚举合法 | FAIL |
| S3 | 状态=已交付 → 证据非空 + 每条 `路径#关键词` 实测存在/命中（目录递归、文本文件） | FAIL |
| S4 | 未交付/下批 → 去向非空；含 LEDGER / REVIEW 锚点时必须可查 | FAIL |
| S5 | 统计：本批计划 N / 已交付 X / 未交付 Y（Y>0 提示，含逐条去向） | NOTE |

### 条 3–6 · 文本级改法

- **条 3**（`review-driven.md`）：§3 加「**开工第一动作**：`cp _templates/scope.md` → 填计划列，**无表不开工**」；§5 编码行改为「测试通过 + 审核无 P0/P1 + **scope 表交付态闭合（`ai-guard-scope` PASS）** + **验收走查已交** + pre-commit 多层全过」。
- **条 4**（`review.md`）：增量深审材料加 scope 表；判据加「声明真实性」三条（抽核 · 扫漏 · 用户真能用）。
- **条 5**（`ai-guard-release.sh`）：判定输出加「本批承诺对账」节（扫 workspace 全部 scope 表汇总）。
- **条 6**（`review-driven.md` §4）：介入点③「验收」加前置——**逐条走查表已交**（走通/走不通+证据；走不通→缺交付物→未交付栏）。

## 四、边界（如实声明）

- S3 的「用户真能用」只能机查到**代码引用级**（路径+关键词），界面可用性靠**验收走查 + 审核官**（人/官判）；
- 守卫不查「设计 §6 本身是否完整」——那是设计审核的职责；
- 首跑前 `ai-guard-scope.sh` 是**新守卫**：启用初期对存量任务不强制（只对含 scope 表的任务跑）。
