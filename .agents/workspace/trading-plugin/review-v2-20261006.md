## 二、战略级（1 条 · 未闭合）

**S1 · 「定位扩容」的 RFC 与 roadmap 条目仍未落盘**

- 位置：`design-v2` §13 交接表（「S2：补 RFC + roadmap 增 / 改 Trading 条目 → `.agents/direction/rfc/` · `product-roadmap.md`」）· 需求「问题 / 动机」· `product-roadmap.md:90`（L6 行）· `:96`（Trading OS 行）
- 问题：`review-v1` S2 的结论是「补 RFC + roadmap 条目」。v2 的处置是**登记给主会话、本分支不改**——这符合 `trading-plugin/LEDGER.md` 的分支纪律，**不是 v2 的缺陷**。但它意味着：**设计收敛的那一刻，路线级依据仍不存在**，「所有任务必须能回溯到路线」在合并前不成立。
- 建议：**不阻断本轮设计收敛**，但设为**编码准入条件**——`design-final.md` 归档前，S2 的 RFC 必须已存在（`ai-guard-roadmap.sh` 可作机械判据）。请主会话在合并同批完成。

## 三、P1（必改 · 2 条）

**P1-1 · `R-01` 的 app 两条输入（随手记一笔 / 截图入账）在四条链里没有落点，且 §5 把「截图入账」改判进通用记录**

- 位置：`design-v2` §3（①–④ 四条链**无一条以 Record / 截图为起点**）· §5 输入分流表 · §6 三端表（app 行「手动记一笔 / 截图入账」）· §9 去留表（**无 `/trade-log*`**）· §12（`R-01` → 「§3① §5（分流）」）
- 实测：`interfaces/TradingController.java:1253 / 1311 / 1329 / 1352 / 1395`（`/trade-log` 5 个端点）· `:1262-1266` 注释原文「**截图入账是交易动作**，候选确认落库后即权威数据，**不污染 Feed / 时间线**」· `interfaces/RecordController.java:251`（RFC 20260817：记录 → 当日候选）
- 问题：
  1. 四条链没有一条承接 Record；§5 只写一句「域侧**只被动消费** Record」——**用哪个端口、什么触发、字段如何映射进 `ledger`** 全没写 → `R-01` 的 app 半边是**游离功能**（有 UI 声明、无链路），§12 的追溯也追不到实处；
  2. §5 把「截图入账」并入 `POST /api/v1/records`，**与既有实现口径相反**：既有链路刻意让它**不进 Feed / 时间线**。改判会让**截图内容进 Record → Timeline → Feed**（并可能进记忆），属**隐私面与展示面的静默扩容**；且 §9 去留表**整块漏了 `/trade-log*` 这 5 个端点**——`review-v1` P1-3 要的「既有能力清单」仍不完整，而它正是 U1 的验收基线。
- 建议：① §5 拆两行——「随手记一笔 → `POST /api/v1/records`（既有 RFC 20260817 归集 → 当日候选 → confirm 落账，**保留**）」与「截图入账 → `POST /trading/trade-log/collect`（**域内动作，不进 Feed / 时间线**）」；② §3 补一条**记录链**，或明确「随手记一笔复用既有 Record → trade-log 链」并给出端口 / 字段；③ §9 补 `/trade-log*` 5 端点及其去留；④ §12 的 `R-01` 映射同步。

**P1-2 · `TradingContextContributor` 被当作「死代码」删除，但它的 `globalContext()` 是活的，且正在把成本价 / 金额 / 现金注入 AI 上下文**

- 位置：`design-v2` §8.1（「**死代码**（`supports()` 恒 false、`enrich()` 恒空）→ **删除**」）· §8.2 脱敏口径（「数量 / 金额 / 成本价不出」）· §9 去留表末行
- 实测：`kernel/context/engine/ContextEngine.java:647`（`loadGlobalContext` 对每个通过门控的 contributor 调 `globalContext()`）· `kernel/plugin/PluginRegistry.java:55`（该类映射 `PLUGIN_TRADING`）· `domain/trading/TradingContextContributor.java:67-101`（`supports()` 恒 false、`enrich()` 恒空——**但 `globalContext()` 输出「## 交易系统状态」：每票 现价 / 成本 / 盈亏%，末尾 总市值 / 浮动盈亏 / 现金余额**）
- 问题：`review-v1` 给的证据是「`:67` 有 `## 交易系统状态`」；v2 把它归纳成「死代码」是**误判**——死的只有 `supports` / `enrich` 两个方法。两条后果：
  1. U1 若照 §8.1「删除」执行，实际是**静默移除一条在跑的注入**，不是 v2 说的「删死代码」（与 `review-v1` P1-2 担心的「静默删掉却无人察觉」同型）；
  2. §8.2 的脱敏契约**在既有活链上第一天就破**——这条路径现在注入的正是需求明令不出的「规模」（成本价 / 市值 / 现金），除非改写成「只出结构（代码 / 比例），不出规模」。
- 建议：§8.1 该行改为「**活代码 · 现状违规**（注入成本 / 金额 / 现金）→ **改写为 §8.2 口径**」（沿用 §9 的「保留 · 改造」字样）；§8.2 明写「改造对象含 `TradingContextContributor.globalContext`」；把它列入 U1 对拍项（改造前后 prompt 差异可见）。

## 四、P2（应改 · 5 条）

**P2-1 · 规则真源未声明唯一性（`rules.yaml` 被同时当参数包与规则集）**

- 位置：`design-v2` §2.5（`rules` 模块「只存**文本 + 参数**」）· §4.1（`rules.yaml` 列为「规则集」）· §8.1（注入走 `knowledge.md`）· §9
- 实测：`data/adai/trading/rules.yaml` 现为**参数包**（`TradingRuleSettingsRepository` 读写，自身注释「真相源：`os/trading-engine/knowledge/context/`」）；规则**正文**在 `os/trading-engine/knowledge/context/rules.md`（537 行）与 `os/trading-engine/04-rules/*.rules.md`
- 问题：用户规则文本**住在哪个文件**、`os/` 的 R1–R120 与用户自建规则**谁优先**、owner 既有规则**迁不迁**——§2.5 / §4.1 / §8.1 三处没有对齐，违反 P24「唯一真源并对外声明」。
- 建议：§4.1 加一行「用户规则文本 = `rules.yaml`（**唯一真源**，参数与文本同文件分节）；`os/` 的 R1–R120 = **知识**（只读注入，**非**规则真源）」+ 声明 owner 既有规则的搬迁 / 并存口径。

**P2-2 · §5 端点表与 §9 去留表未逐条对齐（「保留」与「新增路径」冲突）**

- 位置：`design-v2` §5（导入行 `POST /trading/import`「一次全收」）· §9（导入行「**保留 · 改造**」，列的是既有 5 个端点 `/trades/import` `/positions/import` `/imports/cash` `/sold/import` `/watchlist/import`）
- 问题：§9 说保留，§5 给的是一个**新路径**。是「新增聚合端点（旧端点继续在）」还是「迁移到新端点（旧的 breaking 下线）」未说明 → U1 的迁移基线与前端改动清单对不上。
- 建议：§5 端点列注明二选一——「新增聚合端点，既有 5 端点保留至 v…」或「replace + 迁移表」。

**P2-3 · ★V2 的 B 方案与 §11.1 自相矛盾（打码位置决定端上拿不到保真值）**

- 位置：`design-v2` ★V2（选项 B「端上『点一下显形』，**本地解开，服务端出保真值**」）· §11.1（「打码与脱敏都做在『**出**』的边界（DTO 序列化层 + `ContextContributor` 层）」）
- 问题：§11.1 已定「出参即打码」→ 端上只有打码值 → B 要求「服务端出保真值」，**两个契约不能同时成立**；真要显形只能再请求一次（那其实是 C）。B 是**不可实现项**，不该与 A / C 并列。
- 建议：删 B；在 A / C 之间取值。**裁决见 §六：取 A。** 若确有可读性诉求，用「比例 + 区间」缓解（与 §11.1 口径一致）。

**P2-4 · ★V3 把「已定稿需求拍过的取值」重新变成未决 → 等于把定稿退回重开**

- 位置：`design-v2` ★V3（A 出比例 / B 只出区间 / C 脱敏分母）· 需求「约束 · 隐私」（定稿原文：「代码 · **比例** · 价格 · 规则文本 · 形态**可以出**」）· v2 开篇（「需求 …（2026-10-06 人拍板定稿，**硬约束**）」）
- 问题：需求已定稿并拍板「比例可出」，v2 自己也声明需求是硬约束；★V3 把两个**收紧**选项（B / C）并列等人拍板——这不是「两个方案都行」的取值，而是**改需求**。把它当设计未决，等于替人把已定的决定重开。
- 建议：**不必升人**——按定稿需求取 A（直接出比例）。若要加严（防反推），那是**需求修订**：走人的动作改需求，改完设计再跟。请在 v3 把 V3 从 ★未决移除并写明依据。

**P2-5 · 三端呈现表缺「空态 / 首次引导」列，而验收 1 是全需求最重的验收**

- 位置：`design-v2` §6（只答「哪端 / 怎么摆」）· 需求「验收标准」1（空账号新用户、**不填任何规则**、**全程不需要看文档**）· 需求「边界与异常 · 新用户」· REVIEW `P2-交易81`
- 问题：全文没有一处答「**第一次打开看到什么**」——空账号首页、零规则时的分析页、要交哪两类文件如何被知道。设计把 `P2-交易81` 交给「验收 1 覆盖」（§13），但**空态本身没有设计**。
- 建议：§6 增一列或增一节「空态与首次引导」（需求已给口径：没数据「只说事实」、零规则「不拿别人的规则替他判」）。

## 八、收敛判定

**❌ 不收敛 → 进 v3。**

- v1 的 13 条：**逐条核过，v2 的落点真实存在**（§7 / §8 / §9 / §10 / §11.4 都建起来了），无挂空；
- 不收敛只欠三件：**P1-1 / P1-2 修好**（都在 v2 自己新引入 / 误判）+ **V1 一次人拍板**；
- P2 五项在 v3 一并收（其中 **P2-3 / P2-4 是我不需要人拍板的裁决**，请直接落设计）；
- **编码准入条件**：S2 的 RFC 与 roadmap 条目必须已存在（战略级，可由主会话在合并同批完成）。

> 一句话：v2 把 v1 的账**基本还清了**——分层、注入契约、去留表、术语表都立起来了；剩下的两处不是「没写」，而是**写错了**：一条输入链被漏掉、一条活着的注入被当成死的。**修这两处 + 人给 V1 一个数**，就能收敛。
