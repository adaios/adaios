## 三、战略级

**S1 · L6「交易反哺」闭环被砍，无 RFC、蓝图未更新**

- 位置：`design-v1` §1 归属、§8.4；需求「范围/不做」；`VISION.md:128-144`；`product-roadmap.md:90`；实测 `TradingController.java:1708`（`POST /trading/reviews/{date}/promote` → `os/trading-engine/99-inbox`）、`AdminController.java:423`（conflicts）
- 问题：L6 的官方定义与 VISION 的闭环终点是「复盘 → 反哺交易知识库 / Knowledge」，roadmap 明写 L6 含 `promote/conflicts ✅ 完整`。需求把「理解」下沉 trading 域、不进 kernel，设计的 R-01–R-13 与六模块**都没承接 promote/conflicts 与 87 课知识注入**，「不做」表也未登记。等于**静默砍掉闭环终点**，而三处定义文档仍说有。
- 建议：二选一——**(a)** 设计中把「复盘 → promote → `os/trading-engine`」作为 L6 一环保留（受插件门控）；**(b)** 开 RFC 显式记录「L6 收窄为域内理解、不再反哺知识库」，并同步改 VISION / product-architecture / roadmap 三处。**无论哪条，先补 RFC 再进编码。**

**S2 · 交易插件「定位扩容」未进蓝图**

- 位置：需求「问题/动机」；`VISION.md:169/192`；roadmap §3.2 Trading OS
- 问题：目标用户从「有交易系统的人（纪律工具）」扩到「人人可用、从数据里照见自己」——这是 L6 的**定位变更**，属方向级决策，但 roadmap / RFC 无对应条目，违反「所有任务必须能回溯到路线」。
- 建议：补 RFC（新定位 + 目标用户 + 与既有 87 课知识库的关系），roadmap 增/改 Trading 条目。

## 四、P1

**P1-1 · 「计划/待办」跨域二义 → 关插件后仍会提交易（违反 §8.3 + B6）**

- 位置：design §1（kernel 行写「计划类待办链（唯一例外）」）· §2（`plan` 列为 trading 横切）· §4（`plans/` 落 `data/{userId}/trading/`）· §8.3 · §9；需求「可配置」；已实现的 P2-交易73 落 `data/{userId}/todos/`（kernel builtin，**不**随插件门控）
- 问题：两个「计划」概念混用——trading 的 `plans/{date}.json`（随插件、`R-11`）与 kernel 待办 `todos/`（**关不掉**）。kernel 待办无法随插件关闭，于是「关了 trading → 不再提你的交易」在「**交易来源的待办**」上被破坏。
- 建议：明确「交易来源写入 kernel 待办」时打 `source=trading` + 记录 id，ContextEngine / 推送侧对 `source=trading` 做「**插件关闭即过滤**」闸门；`R-11` 次日计划明确落 trading `plans/`，**不回 kernel**。

**P1-2 · 「理解 → Context」注入链路在设计里缺席，既有贡献者去留未声明**

- 位置：design §3②（止于画像/候选）、§8.3（只写关插件不注入）；实测既有 `TradingContextContributor.java:67`（## 交易系统状态）、`MarketContextContributor.java:49/64`、`TradingProfileContributor.java:23`
- 问题：数据流闭环要求域理解能进对话；设计 T7「分析现算不落盘」后，**账/理解以什么产物、经哪个 Contributor、按什么触发进上下文**，全没写；U1-A 全量重写会**把三个既有 Contributor 一并删掉却无人察觉**。
- 建议：补一节「**理解 → Context 注入契约**」：开插件时注入哪些字段/形态（与 §8.1 脱敏口径一致）、触发条件、条数上限；并列出既有 Contributor 的**去留**。

**P1-3 · 既有能力回归面未列清单，U1 拍板缺依据**

- 位置：design §9 U1；roadmap §3.1 L5/L6（行情主动推送入 Feed ✅、知识反哺 ✅）；实测 `MarketAlertService`（`type=push` 入 Feed）
- 问题：现状已落地「行情主动推送 → Feed」「promote/conflicts」「87 课 KnowledgeSource 全链路」，设计的六模块与三端表都没提。**U1-A 会静默丢功能**；U1-B 也需说明哪些被替换。
- 建议：设计加「**既有能力清单 + 去留（保留/替换/删除 + 理由）**」表，作为 U1 的**必需输入**。

## 八、收敛判定

**不收敛**——有战略级 2 条 + P1×3。

> 一句话（审核者原话）：设计稿的分层与拒绝口径都清楚，但它把 **L6 的「反哺」那一半悄悄删了、也没留 RFC**，同时「计划/待办」与「理解→Context」两处归属没收敛——**这三件要人先拍板**，其余是补文档。
>
> 落地优先级建议：**先等 S1/S2 的 RFC 与人拍板，再动 U1（重做方式）**——因为 U1 定了才知道要不要为 promote/conflicts、三个 ContextContributor、Feed 推送写迁移或保留条款。
