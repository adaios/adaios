## 第二轮未决（V1–V3 · 2026-10-06 拍板）

| # | 决策 | **结论** | 理由速记 |

| **V1** | 提醒一天上限的条数 | **认可**：定时类 **≤4** + 异动类去重、**全局 ≤8/日**；**超限合并不丢弃** | "沉默是默认"；**合并**比丢弃好（丢了你就不知道发生过） |

## V2 的最终解法（2026-10-06 人已认可 · 给 v3）

审核官判「**V2=B（端上显形）不可实现**」——因为设计把打码做在**"出"的边界（服务端）**：**服务端没发数，端上就没得显形**。两个诉求（隐私 / 递手机显形）被压在同一层上了。

**解法：打码拆成两层**（人已认可）——

| 层 | 在哪 | 行为 | 服务谁 |
|:--:|:--|:--|:--|
| **① 显示打码** | **端上** | 数据到了端上，默认 `••••`，**点 👁 可显形** | **递手机**场景（**V2=B 活在这一层**） |
| **② 出边界脱敏** | **服务端** | 发给模型 / 分享出去的**根本不带**数量与金额 | **AI 红线**（需求「约束 · 隐私」） |

> v3 照此改写：**§8.2 / §11.1 的每条脱敏规则都要标清"属于第几层"**，别把两端混成一层。

## 第五轮拍板（2026-10-07 · 重构「可删」口径）

> **adai 原话补充**：「可以删，既然是重构，钱都都可以，后端有服务就行，假如删掉可能还会以另外的方式加上。」

- **结论**：交易插件重构中——**实现比设计多出来的前端元素**（列 / 信息带 / 入口）**可以删**；范围含资金、金额类展示。不必为"怕丢功能"而 UI 逐一保留。
- **边界**：**「后端有服务就行」**——能力保留在后端（服务 / 端点）；`uiux-discovery` §十一「功能一个不删」据此澄清为**能力不删 = 后端在**，不是 UI 元素不删。
- **心态**：**删 ≠ 永久失去**——"假如删掉可能还会以另外的方式加上"（需要时换形态回归），所以敢删。
- **影响**：`review-web-uiux-20261007.md` 的"多出来"项（P2-9 列预算 · P3-10 信息层等）差异决算方向更新为**以「删 / 按设计对齐」为主**，「保留」需有明确理由。
