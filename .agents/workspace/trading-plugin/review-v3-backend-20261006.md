# 设计审核 v3 · 交易插件重做（后端官 · code-backend-reviewer）

## 一、审核对象与方法

- **对象**：`design-v3-20261006.md`（70 行 · **增量稿**）+ `design-v2-20261006.md`（415 行 · **正文**）——按 v3 自述「正文仍看 v2」合看。
- **只审两件事**（v3 §四指定）：① 上一轮的战略级 / P0 / P1 是否**真闭环**；② 本轮**是否新引 P1**。
- **方法**：设计承诺 × **现状代码实测**（只读，未改任何文件）；凡标「实测」的都有 `文件:行号`。
- **对拍物**：`review-v2-backend-20261006.md` · `review-v2-20261006.md` · `requirement.md` · `decisions.md` · `data-format-freeze.md` · `services/adai-core/src/main/java/com/adaiadai/core/**`。

## 二、结论

**❌ 不收敛。** 无 P0。**战略级 2 条（S1 · S2）均未闭环**；v3 的 P1 表 6 行中 **2 行闭环**（后端 `P1-2` · 产品 `P1-1`/后端 `P1-5`）· **4 行部分闭环**（后端 `P1-1`/产品 `P1-2` · `P1-3` · `P1-4` · `P1-6`）；**新引 P1 × 2**。

| 维度 | 判定 |
|:--|:--|
| 数据安全（最高权重） | **FAIL**——§10 脱敏仍不成立（规则未枚举）+ 非 owner 反哺静默丢弃未回 |
| 分层依赖 | **PASS**（本轮无新增越层）|
| 数据流闭环 | **FAIL**——S1 闸门面不全（记忆 / 上下文注入面漏）|
| 健壮性 | 未评（v3 未涉写入路径改造）|
| 插件门控（B36） | **FAIL**——S1 |
| 测试覆盖 | **FAIL**——v3 只给了 1 条反向回归；§9 基线无对拍、闸门面无逐面验收 |

一句话：v3 **方向对、落点浅**——把上一轮点名的每一条都"写到了"，但**多条停在"登记口径"而非"可核对的产物"**；最要命的是**改动只在增量稿里、没有回写正文**，于是 v3 与 v2 对着干（§8.1 已更正 vs §9 仍写"死代码 · 删除"），而 §13 又拿 §9 当验收基线。

## 三、战略级

### S1 · 「关插件即过滤」的闸门扩面仍不全 → **未闭环**

v3 改法（`design-v3:30`）：闸门扩到 `Feed` / `Timeline` / 搜索 / 领域活动度。

- **v3 点名的 4 面，实测确为未门控**（这条改进是真的）：

| 面 | 实测证据 | 门控现状 |
|:--|:--|:--|
| Feed 记录折叠 | `application/FeedAppService.java:326`（`tradeDirection` 只认 `domain=trading` 的 record）| 只有行情（`:199`）与推送（`:210`）有门控，**record 无** |
| 时间线 | `kernel/timeline/TimelineProjection.java:60-61` | 无 |
| 搜索 | `kernel/search/SearchService.java:42` | 无 |
| 领域活动度 | `application/DomainActivityService.java:28-30` | 无 |

- **但漏了两个同样真实未门控的面**（正是 `review-v2-backend` S1 要求「记忆 / ContextEngine 需实测」的那一面）：
  1. **记忆 / 上下文注入面**——`kernel/context/engine/ContextEngine.java:356`（`loadRelatedRecords`，第 360 行 `recordRepository.findAll(userId)`）把最近记录摘要拼成「## 相关历史记录」注入 **AI 上下文**，**无任何插件门控**（该类的门控只覆盖 `ContextContributor` `:626-641` 与 `KnowledgeSource` `:590-598`，记录注入路径不在其中）→ 关插件后 AI 仍读到「买入 京东方A 1000股@5.20」。
  2. **kernel 记忆面**——`application/BriefAppService.java:232/259`（`## What AI understands about this user` 由 `memoryService.findByDate` 直供）**无条件注入**；而交易 record 会写记忆（`interfaces/RecordController.java:246` 的 `memoryPersisted`）→ 存量交易记忆关插件后照样进简报。
  3. 附：`interfaces/TradingController.java:1701`（`/trading/has-activity`）实测**确无门控**，v2 §9 那行仍写「补门控（**或**登记为只读例外）」——**二选一未定**。

- **判定：未闭环。** 面清单不全 = v2 §11.3「关了插件阿呆不再提你的交易」仍落不了地。
- **建议**：① 闸门表补两行（记忆 / 上下文注入面：`ContextEngine.loadRelatedRecords` + `BriefAppService` 的 memory 段；`has-activity`）；② 写明**过滤发生在读侧**（与「数据保留不删」配套）；③ 给逐面验收清单（4 → 6 面）。

### S2 · §9 验收基线仍不可靠 → **未闭环**（且 v3 自身计数有误）

v3 改法（`design-v3:31/33`）：§9 补后端官点名的 **11 组**缺失能力 + 注明「完整逐端点对拍留 backlog」。

- ❌ **「11 组」实际只有 10 行**：`design-v3:37-46` 逐行数得 `出入金 / 资金层 / 清仓情绪 / 候选入账 / 批量 / 推送控制 / 活跃市值 / 账户组合 / 建议留痕 / 查询` = **10 行**；`review-v2-backend` §七差异表为 **11 行**，**丢掉的正是「其他目录 `data/{userId}/trading/memory-cards/`」**。这是项目既有坑「**假精确**」的同型——**数量声明与内容不一致**，且落在"本该当基线用"的表上。
- ❌ **补的 10 行没有一行给「去留（保留 / 替换 / 删除）+ 理由」**。§9 的用途是 **U1 渐进重构的验收基线**（v2 §13）；`review-v2-backend` 的建议是"逐条补去留 + 给删除类加反向判据（有测试 / 有生产调用 / 有前端入口 → 不许默认删）"——v3 只补了"哪些能力存在"，**没补"哪些不许删"**。
- ❌ **「完整逐端点对拍留 backlog」与「§9 为验收基线」直接冲突**：一个**已知不完整**的表当基线 = 原 S2 的风险（实施期按表替换 → 静默丢功能）原样保留。
- **判定：未闭环**（不阻断设计方向，**阻断编码**——§13 已把 §9 定为 U1 基线与编码准入）。
- **建议**：§9 落成 **「端点 → 去留 → 理由 → 判据」** 四列；删除类必须给反向判据；对拍补全后再宣布"基线"。

## 六、专答：闸门扩面之后，「关插件」对存量数据是否自洽

**结论：方向自洽，但有三处没写清，实施期会变成不自洽。**

v2 §11.3 的承诺是「关 → 受控端点 403 + 账与理解都不注入 + 不推送；**数据保留不删**，重开即有」。v3 的闸门写法（"对 `domain=trading` 的 record 按插件门控"）看着是**读侧过滤**——若是，则存量与新增**一致地被隐藏**、**可逆**、**无需迁移**，与"数据保留不删"自洽。要让这条真正成立，必须补三件事：

1. **写侧要落成端点清单**（B36 要求按**端点**而非数据路径枚举）：关插件期间哪些写入口 403。现在 §11.3 只有"受控端点 403"这句抽象话；而 `RecordController.java:255` 的归集、对话动作 → 待办等路径**并非都随插件开关**——不写清，就会持续积累"看不见但存在"的 `domain=trading` 数据。
2. **记忆面必须一起过滤**（即 S1 的漏项）：record 会写 kernel `Memory`（`RecordController.java:246`），而记忆**无条件**进简报（`BriefAppService.java:232/259`）→ 只过滤 Feed / 时间线 / 搜索，存量交易记忆照样进 AI 上下文。
3. **把"关 → 开"写成一条验收**：读侧过滤 + 数据保留 ⇒ **重开即全部回来**。这条要作为断言写进验收（关插件 → 六个面都不含交易条目；重开 → 旧交易重新出现），否则"保留不删"与"过滤"的边界没人验，很容易被实现成"关插件顺手清掉"（那是 P0 数据丢失）。

## 七、给编写者的最小施工清单（按"能一次改完"排序）

1. **合并出 `design-final`**（或显式标注 v3 覆盖 v2）——修新引 P1-1；顺手把 §9 补回 `memory-cards/`、把"11"改对（新引 P1-2）。
2. **S1 闸门表补两行**（记忆 / 上下文注入面 `ContextEngine:356` + `BriefAppService` memory 段；`has-activity`）+ 写明**读侧过滤**与**存量可逆**；给逐面验收。
3. **§9 落成四列**（端点 → 去留 → 理由 → 判据），删除类加反向判据——S2 才算闭环。
4. **§8.1 的更正写到 §8.2 与 §9**（P1-1 收口）；顺手统一两个 contributor 的同名标题「## 交易系统状态」。
5. **§10 三件事**：脱敏规则**枚举**（含 `request.sections()`）· promote 落点**定死一种**（去"或"）· 补非 owner 的 403 / 自落口径（P1-3 / P1-4 收口）。
