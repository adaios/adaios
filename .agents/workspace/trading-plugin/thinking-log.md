# 思考记录 · feat/trading-plugin

> 人要的是**推理链**，不是结论堆。每条按「**看到 → 判断 → 选择 → 放弃的**」写。

## 2026-10-06 · 流程修复 + 目录重构（本轮）

### 1 · 目录为什么按「分支」切，而不是按「产物阶段」

- **看到**：容器里 `tasks/` 是**一个角度**，`requirements/` + `designs/` 是**另一个维度**——同一层两种切法，命名不自洽；用户直接问「是不是怪怪的」。
- **判断**：容器只能有**一个主键**，否则迟早对不上。分支天然是唯一主键（名字唯一、且「有想法才开分支」）。
- **选择**：`.agents/workspace/<分支名>/` 装这条任务的**全部**产物；模板进 `_templates/`、跨任务的进 `_meta/`。
- **放弃**：① 保留三目录再加汇总索引——绕不开两种切法，治标；② 按需求 id 分目录——一个分支可能做多个需求，会碎。
- **收敛判据**：**需要什么才有什么**——轻活只有一个 `LEDGER.md`，重活才有需求 / 设计 / 审核。

### 2 · B1（在制品不入清单 ⇄ 守卫要求登记）为什么选「改契约」

- **看到**：`_directory.md` 写「在制品本身不入清单」，而 structure 的 S2 双向校验、meta 的 M3 孤儿判据**都要求先登记**。
- **两个方案**：改契约认下登记 / 让守卫豁免动态在制品。
- **选择**：改契约。
- **理由**：S2 / M3 是**防漂移的硬闸**（清单 ⇄ 实际）；为文档里一句旧话给它开豁免，等于拆闸。反过来改一句话成本近乎零。
- **放弃**：给守卫加豁免——豁免会长成第二套规则。

### 3 · 12 条流程问题为什么一次改完，而不是继续「登记待交接」

- **看到**：原结论是「落点在 workspace 之外 → 登记，合并后由主会话改」；用户随后明确授权「都在当前目录修改」。
- **判断**：留给下一个会话，成本是**重读 + 重判 + 再改一遍**；而且中间态**自相矛盾**（有的文件已写「分支上不归档」，另一些还写着「归档 `docs/`」）。
- **选择**：本分支改完，逐条登记状态，跑守卫。
- **放弃**：只改一半——半改的契约比不改更危险（两处说法打架，后来人不知信谁）。

### 4 · 新角色为什么是一等公民，判据为什么是 13 条

- **看到**：主链只有「人签字」，**定稿前无人审**；结果是需求里混进设计、方向扩容没对路线，一直拖到设计审核才爆（A1 + A2）。
- **判断**：缺的不是「人签字」，是**签字前那一环**。
- **选择**：建 `docs-requirement-reviewer`（角色 + 清单 + 注册），判据取 **ISO/IEC/IEEE 29148** 的单条需求质量特性，再加本项目两条教训。
- **13 而不是 12**：A2 要求必须有「**路线对齐**」——需求要追得到 roadmap / VISION，改方向必须显式开 RFC。所以第 13 条是 ★。
- **理由**：需求阶段的错**返工最贵**（会放大到设计、编码、验收）。

### 5 · C1（交付判据）为什么写进每个角色，而不是只写流程

- **看到**：实测审核者**三次不落盘**，最后靠主会话代誊才保住追溯。
- **判断**：流程里写「要落盘」**没用**——子代理不读流程文件，只读**自己的角色定义**（那是它的真相源）。
- **选择**：交付判据写进**每个角色定义**（13 个）+ 流程 prompt 里再写一遍（双保险）。
- **放弃**：只改流程——已经证明无效。

### 6 · 这套在行业里叫什么（追问后补 · 2026-10-06）

**结论：主干是行业正统，有四十来年；缺的是 QA 那条中立线。**

| 我在做的 | 行业名 | 出处 |
|:--|:--|:--|
| 产作者 | Author / Producer | 通用 |
| 审核者（多官并行 · 不共享上下文 · 独立读） | Inspector / Peer Reviewer（independent reading） | Fagan 1976；IEEE 1028；ISO/IEC/IEEE 12207 |
| 对抗官 | Devil's advocate / Red team | Janis 1972；安全红队 |
| **（缺）盯流程 · 记问题** | **Moderator + Recorder**；**QA（过程）** | Fagan 1976；IEEE 730；CMMI OPF/SEPG |
| **（缺）分歧拍板** | CCB / Design Authority；四眼原则 | IEEE 1028；COSO 职责分离 |
| 人签字定稿 | Stakeholder sign-off | ISO/IEC/IEEE 29148 |

四条判读：

1. **作者不审自己**＝铁律；「不共享上下文」＝行业所谓 independent reading（会前各自读、各自记）。
2. **中立角色是 Fagan 的原始配置**——moderator（只跑流程）+ recorder（只记录）。**C1 那次「主会话代誊」＝角色混用**，不是勤快问题。
3. **QC 与 QA 是两回事**：8+3 官全是 **QC**（判产物）；「盯流程 / 记问题 / 推改进」是 **QA**。CMMI 叫 OPF/SEPG，Agile 叫 Scrum Master + 回顾会，SRE 叫无责复盘 + action item 闭环。
4. **数量不是重点、异质才是**——按**失败模式互补**派官（后端官跑出产品官抓不到的 6 条 P1 即证据）。

**自我迭代：能，但要外部信号。**

- 行业学名：PDCA/戴明环 · Kaizen · 回顾会 · **CMMI 5 级 "Optimizing"**（过程自改进本身就是一个成熟度等级）；SRE 无责复盘。
- AI 侧：Self-Refine / Reflexion / STOP / Voyager。
- **硬前提**：纯模型自评会漂移（朝「看起来更顺眼」而非「更对」）；有效自迭代都挂在**外部信号**上（编译 / 测试 / 守卫 / 真值 / 真实事故）。
- **我已经做对的那一步**：checklist 的「沉淀检查点（带上次发现）」＝**每条新判据绑定一次真实事故**。
- 拟固化的三条门禁：① 新判据必须绑事故；② 改角色走「提案 → 守卫 → 人点头」；③ **对抗官不参与自评**（会变钝）。

由此得**四条 delta**（已登记为待拍板提案，见 `_meta/process-issues-20261006.md` §四）：立「流程官」· 禁止 orchestrator 代誊 · 自迭代门禁 · 派官按失败模式互补。

- **建了流程官**：`roles/process-reviewer.md` + `checklists/process-reviewer.md`（P-01…P-10 + L1–L3），并注册进 `ai-sync-agents.sh`。定义里写死**中立**（不判内容）、**不代笔**、**三道自迭代门**。
- **QA-2 禁止代誊**：进 `review-driven.md` §7 反模式 + §8 硬规矩——他没落盘就**记一条问题**，不许替他写。
- **QA-3 自迭代门禁**：进 `skills-spec.md` §七（判据绑事故 / 改角色走「提案→守卫→人点头」/ 对抗官不自评）+ `review-driven.md` §8。

### 8 · 流程修复轮：把「派单」当一等公民（2026-10-06）

**触发**：用户明确「我要的是流程上的解决，目前任务是次要，我要跑通流程」。

**先算账**（v3 审核轮）：墙钟 ~21 分钟，**有效产出 ~4 分钟**（后端官 3–4 分钟就出了 127 行硬审）→ 有效率约 **1/5**。三个根因：

1. **同批并行 `spawn` 只有第一条的任务书送达**——后端那路白跑两轮；
2. **子代理不落骨架**——黑盒跑满 15 分钟，主链只能等到闸门才打断；
3. **主链 55 秒轮询干等**——这一段是我的问题，不是工具的。

**判断**：慢的不是模型，是**投递 + 可观测性 + 编排方式**。质量与速度不冲突——后端官本身就是「4 分钟 + 高质量」的反证。

**选择**：把协议**升为规范**，而不是留在任务笔记里：

- `rules/process/review-driven.md` **§9 派单协议**：串行派发 · 要回执 · 材料前置 · **第一动作先 `cp` 出文件** · 3 分钟闸门 · 主链不空等；
- **关键一招是「第一动作先落文件」**——10 秒内就有心跳，黑盒变白盒。它比"请早点落盘"这种请求强，因为它是**机械动作**，不依赖模型自觉；
- 模板 `_templates/dispatch.md`（照抄改）；流程官清单加 **P-11**（串行 + 回执）/ **P-12**（3 分钟闸门）；
- **单次失败成本上限：3 分钟**。

**放弃**：① 只记在任务笔记里（下次照样忘）；② 靠"提醒子代理早点落盘"（已证明无效）；③ 为赶时间自己代判（违反刚立的 QA-2）。

**验证**：用新协议**实跑一次**（单发 + 材料前置 + 先落文件 + 3 分钟闸门），以**实际落盘时间**验收。

**验证结果（同日）**：协议**闸门有效**（失败一次只损失 3 分钟，不再是 15–20 分钟），但**验证暴露了更底层的问题——投递整个不可靠**：

- 单发也丢、**连一行短 prompt 都丢**：本会话 **7 次派单只送达 1 次**，失败方一律回「只收到项目入口，没有具体指令」；
- 于是"第一动作先落文件"这条**根本没机会生效**——它不是被忽视，是**任务书没到**；
- **结论**：不能把流程的必经环节压在一个当前不可靠的通道上。→ 加 **§9.1 执行档位**：A 独立子代理（要回执）/ **B 主链按角色清单执行 + 文首标注"独立性降级"** / 禁止 C（不标注的代笔）。**流程永不阻塞，代价用"标注"换诚实**。
- 本轮据此走 **B 档**跑完：产品侧判定落在 `review-v3-20261006.md`，**文首已标"档 B · 主链执行 · 独立性降级"**，可被下一轮真审核官整篇替换。

## §8 为什么"修不了"（2026-10-06 · 三次对照实验）

- **看到**：用户追问「**为什么修不了**」。我上一轮说"消息通道修不了"——但**没说清是哪一层修不了**，这等于把话停在半空。
- **判断**：必须把"派单丢消息"从**现象**钉成**根因**，否则 A/B/C 档只是兜底、不是修复；而根因没钉死，`fork_turns="none"` 这类猜测就会被当成结论。
- **做**：串行三次实验——
  - **E1** `spawn_agent` + `fork_turns="none"` + 一句短指针 → **丢**（子代理只收到 AGENTS.md／技能／环境／协作规则）；
  - **E2** 对**已存在**代理 `followup_task` 补发同一句 → **仍丢**（回报逐字相同）；
  - **E3** `AGENTS.md` 加规则 **0c**（开工先看 `workspace/_meta/inbox.md`）+ 任务写进收件箱 → **通**（子代理零消息下自行读到、执行、落盘）。
- **结论**：`spawn` 与 `followup_task` 的 `message` **都丢载荷**，子代理只收"**系统提示级**"内容；而**子代理能读文件、且会主动读文件** → **文件系统是活通道**。
- **选择**：把**收件箱**升为**派单主通道**——写进 `AGENTS.md` 规则 0c 与 `review-driven §9` 第 0 条；`spawn` 的 message 只留"按 AGENTS.md 规则开工"。
- **放弃的**：继续在消息通道上做重试/补投工程（E2 已证无效）。
- **自省（要害）**：我说"修不了"**只对了一半**——我确实修不了 app，**但我能改流程的通道**；当时没往下想一层，把一个**可修的问题**说成了不可修的，这是这一轮最该记的教训。

## §9 走查怎么才不白走（2026-10-07~08 · 两轮走查 + 一次被纠正）

- **看到**：adai 连问两次「别的工具完成了，你审核下」；中间追问「为什么这次没有打开、鼠标点击的方式审核」。
- **判断**：审核的价值不在"我读完了"，在"**证据能不能被别人复现**"——所以这轮把管道做成可复用：本地起后端 + 按当前代码构建 web + 无头 Chrome + 登录态注入 + 语义树定位 + **固定视口**实拍。固定视口是关键：同一张表 1600 能看全、1280 就被裁，不定宽度的"我看过了"等于没说。
- **做**：三轮实拍（决算批回验 11 张 · 七批验收 11 张 · 更早 8 张），每次**先跑客观证据（测试 + analyze）再上真机**，结论与证据图一起入库。
- **结论（方法层三条）**：① **可量化的差异必须数出来**（列数 / 项数 / 宽度）；② **「测试全绿」与「页面能看」是两件事**——7 批里有 1 批测试全绿、页面上却根本没出现；③ **程序化点击 ≠ 真人鼠标**（hover / 连续缩放 / 手势覆盖不到），须如实声明。
- **自省（要害）**：**我第一次走查把「持仓表 16 列 vs 原型 8 列」判成了「结构一致」**——只看了"结构在不在"，没数列数；是 adai 一句「明显不一样」才改判（`review-web-uiux` v2）。教训：**走查分级必须建立在可数的事实上**，否则"一致"二字会替用户把问题盖住。
- **放弃的**：把两轮走查写成两份独立报告（内容高度重叠）→ 改为**累积单文件 + 轮次节**，并把这个例外写进 `review-driven §10`（历史节不许覆盖）。

## §10 规格是"事后补"还是"先有"（2026-10-08）

- **看到**：adai 问「按规格先行流程，应该留哪些文档？可以补齐么」——翻规范发现：**UI/UX 这轮压根没有规格**，决定散在 5 份文档里。
- **判断**：**先有决定、后补规格**已经发生（不可能回退），所以补出来的规格只能定位成"**收拢器**"、不能假装是"前置约束"——于是 `design-uiux` 里明写这句，并把"若与来源文档有字面差异，以已拍板决定为准"写进自评风险。
- **做**：补 `design-uiux`（规格）· `scope-uiux`（交付表，机械核 PASS：本批 7 条 = 6 交付 / 1 未交付→去向）· `review-driven §10`（体验走查段规范）。
- **结论**：**规范的价值在于"下次不用再补"**——所以 §10 写死了产物命名、轮次写法、出口判据、两条证据纪律。
- **自省**：这一轮真正的教训是「**决定落盘 ≠ 规格落盘**」——我们每天在 `decisions.md` / 批注 / 决算里记决定，但**没有人被要求把它们收成一份可对照的规格**，于是"规格先行"名存实亡。补的是文档，改的是这个习惯。
