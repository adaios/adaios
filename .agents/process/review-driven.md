# 审核驱动开发流程（review-driven）

> 主链：**需求 → 设计 → 编码**，**文档先行 + 双角色真对打**。定了需求文稿之后**人基本不参与**——全程只在 **4 个点**被叫。全图见 `docs/architecture/ai-context-engineering.md` §4.6。

## 1. 入口条件：需求已由人拍板定稿

- `workspace/requirements/<需求id>.md` 的「**定稿记录**」已由**人**填写。**没定稿不启动**（人的介入点 ①）。
- 定稿时**同时归档**到 `docs/rfc/` 或 `docs/features/`——`workspace/` 只留在制品。

## 2. 设计阶段（两角色真对打）

**两个独立 subagent，各自独立工作、不共享上下文**（真对打的前提）：

| 角色 | 真相源 | 产出（每轮一份）| 派法 |
|:--|:--|:--|:--|
| **设计文档编写者** | `roles/docs-design-writer.md` | `designs/<id>/design-v<N>-<YYYYMMDD>.md` | 每轮派一次 |
| **设计文档审核者** | `roles/` 里对应审查官（按需求性质选：`docs-product-reviewer` / `code-backend-reviewer` / `ux-interaction-reviewer` / `ai-context-reviewer`…）| `designs/<id>/review-v<N>-<YYYYMMDD>.md` | 每轮派一次 |

**轮次循环**：

```
v1: 编写者（读需求定稿）→ 审核者（读 design-v1）→ 判定
      ├─ 无 P0/P1 ────────────→ 收敛：出 design-final.md
      ├─ 有 P0/P1 ────────────→ v2: 编写者（读需求 + review-v1）→ 审核者 → 判定 …
      └─ ★ 取值取舍类 ────────→ 升级给人（人的介入点 ②）→ 按拍板继续
```

**轮次上限**（与 `review.md` 的「对抗官 ≤2 轮、第 3 轮升给人」同精神）：
- **≤3 轮**仍不收敛 → **强制升级给人**，连同**三轮分歧摘要**一起交（不许拿"再来一轮"拖着）。
- 每轮**必须新文件**（`v<N>` + 日期），**不覆盖历史**——可追溯性（v2 为什么这么改 ← v1 的审核文件）就靠它。

**审核者怎么审**：用自己的角色定义（`roles/*.md` 五段）+ 对应 `checklists/`；**问题分级沿用现有体系** P0–P3；**输出收敛判定**（无 P0/P1 → 收敛）。

## 3. 编码阶段（同样两角色）

| 角色 | 真相源 | 派法 |
|:--|:--|:--|
| **编写者** | `skills/code-api-writer.md` / `code-domain-writer.md`（建设技能引导）| AI 自主 |
| **审核者** | `roles/*`，按 `review.md` §3 的**派官表** | 至少一轮 |

- 编码阶段的审核**沿用增量深审**（`review.md`），**不另起一套**——本流程只规定"必须派、派谁、何时升级"，具体执行标准归 `review.md`。
- 出口：审核报「无 P0/P1」+ 测试通过 → 进 **`ship`**（`process/ship.md`）。

## 4. 人的介入点（仅 4 个）

| # | 时机 | 谁判断「该叫人」 |
|:--:|:--|:--|
| ① | **需求定稿** | 必须——AI **不自行宣布**（`requirements/_directory.md` 的硬约束）|
| ② | **设计阶段的取舍 / 分歧** | 三重保证：编写者标「★ 未决」· 审核者判「取值取舍」· **3 轮不收敛自动升级** |
| ③ | **验收** | 必须 |
| ④ | **发布** | 必须（原则 B8：外向动作须点头）|

> **两句话一起才成立**：「**除此之外不问人**」（否则退化成事事确认）＋「**该叫的时候必须叫**」（否则 AI 替人做了不属于它的决定）。

## 5. 出口判据（什么算过了）

| 阶段 | 出口条件 |
|:--|:--|
| **需求** | 人的「定稿记录」已填 + 已归档 `docs/rfc/` 或 `docs/features/` |
| **设计** | 审核报**无 P0/P1** → 出 `design-final.md` → 归档 `docs/architecture/` + ADR → 删 `designs/<id>/` |
| **编码** | 测试通过 + 审核无 P0/P1 + `pre-commit` **11 层**全过 |
| **收尾** | `cadence.sh ship`（显式路径提交）+ 任务账本「待归档」搬进全局账本（change-log / REVIEW / `_index`）|

## 6. 与既有流程的关系

| 既有流程 | 关系 |
|:--|:--|
| `review.md`（增量深审）| **被本流程复用**为"审核者"的执行标准；它的派官表**同时是编写前的约束清单** |
| `audit.md`（全量走查）| 里程碑级，**不在**本主链的日常循环里 |
| `ship.md`（收尾闭环）| 本主链**编码段的出口** |
| `cadence.md`（节奏触发）| 触发词层，与本流程正交（本流程由"需求定稿"触发，不由触发词触发）|

## 7. 反模式（别这么干）

- ❌ **一轮就宣布收敛**——没派审核者等于没审；收敛只能由**审核者**判定。
- ❌ **同一 subagent 既写又审**——失去独立性，等价于自评；必须是**两个独立 subagent**。
- ❌ **替人做取舍**——"两个方案都行"这类问题**必须**升级；自己定了就是这个模式最大的失败。
- ❌ **无限对打**——>3 轮不升级，把分歧摘要一并交人才是正解。
- ❌ **改旧轮文件**——破坏可追溯；新结论写新轮。
- ❌ **跳过 `workspace/` 直接改 `docs/`**——在制品就该待在制品区；定稿才归档。
