# 社会性（递出去那一刻）检查清单

> 用法：站在**旁边的人**的位置逐条问「他就在你旁边，会发生什么」。产出是**决策表**，不是 bug 清单——不要把它降级成技术问题。

## 一、暴露面

| # | 检查项 | 判定 |
|:-:|:-------|:----:|
| N1 | **锁屏通知正文逐类型过一遍**：会露出持仓/金额/成交/学习内容吗？（收盘小结等 alert 通知锁屏可见）| PASS/FAIL |
| N2 | 递手机/放桌上时，打开第一屏有没有不该被看到的（资产、持仓、记录）| PASS/FAIL |
| N3 | 共享屏幕 / 投屏 / 截图时，可见内容是否可接受 | PASS/FAIL |
| N4 | 通知渠道自身是否泄露（如第三方推送服务的标识、通知标题暴露产品性质）| PASS/FAIL |

## 二、他要付出什么（每一项都是拒绝的理由）

| # | 检查项 | 判定 |
|:-:|:-------|:----:|
| N5 | 逐项列出使用门槛：装 App / 加微信 / 关注公众号 / 注册 / 手机号 / 记密码——每项标注「能不能不给」 | PASS/FAIL |
| N6 | 邀请话术不让他以为是推销或「帮他做测试」 | PASS/FAIL |
| N7 | 费用归属清晰：他要不要花钱、花的是谁的钱、用超了怎么办 | PASS/FAIL |

## 三、隔离与退出

| # | 检查项 | 判定 |
|:-:|:-------|:----:|
| N8 | 多用户隔离：他确实看不到我的数据（账号 / `data/{userId}/` / 建议 / 推送各一份）| PASS/FAIL |
| N9 | 退出口存在且他能自己找到：登出 / 不想用了 / 数据怎么处理 | PASS/FAIL |
| N10 | 通知开关他可自己控制（不必来求你关）| PASS/FAIL |
| N11 | 出事时的话术与责任边界已想清楚（数据错了、推送没到、他问了你答不上来）| PASS/FAIL |
| N12 | 名字与体面：他愿意在同事面前打开、说得出这个名字 | PASS/FAIL |

## 输出口径

- 每条的**受体**（谁看到 / 谁付出）+ **场景**（什么时候发生）
- 触碰底线的（隐私外露、无法退出、被迫付出）→ 写入**必须拍板的决策表**，给选项与代价
- 禁止表述成技术问题：「推送正文过长」是错的写法，「锁屏会露出你持仓哪只票」才对
